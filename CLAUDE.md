# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Frontcache is a reverse-proxy / web-filter page-fragment cache for web apps written in any language. It sits in front of an origin app and serves cached page fragments, stitches together `<fc:include url="..."/>` fragments (optionally concurrently), and provides circuit-breaking/fallbacks via Resilience4j.

This repository is **the product source and its public documentation**, Apache-2.0: the Gradle build at the root (`frontcache-core`, `-server`, `-console`, `-agent`, `-tests`), the user-facing docs under `docs/`, the runnable examples under `examples/`, and the replay benchmark under `benchmark/`. **Frontcache Pro** (licensing, the cache warmer's orchestration, the console's cluster rate, and the Pro features still to come) is proprietary and lives in a **separate, private repository** that includes this build as a Gradle composite (`includeBuild('../frontcache')`) and plugs in through the two SPIs described under *Core architecture*. Nothing here depends on it, names it in code, or links to it. The design documents behind the invariants below are private too, which is why this file states each invariant in its own words rather than pointing at one.

## Build & test

Gradle is the only build. Artifact deployment (publishing `frontcache-core` + `frontcache-agent`, `frontcache-console-classes` and the two bundles to `s3://repo.eternita.co/maven2`, public-read) is handled by the `maven-publish` plugin in `build.gradle` — run `./gradlew publish` (or `./gradlew publishToMavenLocal` for a dry run). The legacy Maven `pom.xml` has been retired.

- Build all modules: `./gradlew build`
- Build/clean a single module: `./gradlew :frontcache-core:build`
- Unit tests (per module): `./gradlew :frontcache-core:test`
- Run a single test class: `./gradlew :frontcache-core:test --tests org.frontcache.SomeTest`
- Coverage report (JaCoCo): generated automatically on `check`; HTML under each module's `build/reports`.
- Remote-debug a test run: pass `-DDEBUG=true` (suspends on port 8001).

**End-to-end / integration tests** live in the `frontcache-tests` module. Run the suite with `./tests.sh` (at the repo root) — it cleans caches/logs, starts the two embedded Jetty servers and an e2e console (`:7090`, the Community console pointed at both nodes, so `CommunityEditionTests` can check it shows no Pro screen), runs the suite, then kills them. It is deliberately **not** wired into `check` / `build`, since those servers must be up first. **`tests.sh` runs `./gradlew -stop`**, which kills every Gradle daemon — including one serving a console `appRun` you have open. `frontcache-tests`' base classes, `TestConfig` and `FrontcacheStandaloneServer` are its **test fixtures** (`src/testFixtures`): the Pro repository's e2e suite extends them and runs these very webapps and `FRONTCACHE_HOME`s with the Pro jars on both nodes, so a change to a fixture's signature or to a home's files is a change to that suite too. `src/main` is only the combine servlets the webapps need, and `ExecWait` lives in `buildSrc`.

The e2e topology: test → FC standalone (`:9080`) → FC webfilter (`:8080`) → web app (`:8080`). Both servers run in embedded Jetty 12 via `org.frontcache.tests.FrontcacheStandaloneServer`. Integration tests run **sequentially** (`maxParallelForks=1`, `forkEvery=1`) because each test cleans the cache directory first.

**The per-platform bundles carry a jlink'd Java runtime, and its module set is a hand-maintained snapshot that has now gone stale twice.** `JLINK_MODULES` in `scripts/dist/build-runtime-bundles.sh` was computed with jdeps once and does not recompute itself, so a JDK module our own code newly reaches for is simply absent from the next bundle — and the resulting runtime **boots and serves**, failing only on the one code path that touches it: `java.net.http` went missing and took the console's realtime page for a release, then `jdk.management` went missing and made `FcNodeStats.getCpuProcessLoad()` (the console's "JVM CPU" column, and `frontcache_process_cpu_usage`) read as untracked on every embedded-runtime node, because `com.sun.management.OperatingSystemMXBean` lives there and **not** in `java.management`. Note the failure shape: the `instanceof` guarding that bean does not go false when the module is gone, it throws `NoClassDefFoundError`, which the code catches by design — a correct answer, and unfalsifiable from the outside. Three things guard it now: `--verify-modules` (jdeps over **our own jars only** — a JDK module our bytecode names is reachable by definition, whereas Spring asking for `java.scripting` from classes this console never loads is a judgement call, and a check that fails on those gets switched off), the `get-node-stats` CPU assertion in `smoke-test-runtime-bundles.sh`, and a one-time `WARN` from `FcNodeStats` naming the missing module. `java.prefs` needs no entry — `java.desktop` `requires transitive` it.

**Every source file carries the Apache-2.0 header, and `check` fails on a missing or wrong one.** `check` runs `license` (the hierynomus plugin, strict, on every subproject) over each source set plus `licenseLooseFiles` (a war's `fc-*.js` / `fc-*.css`, and `src/test/js`), so **a new file fails the build until `./gradlew licenseFormat` writes its header**. JSPs are deliberately unchecked: a JSP comment's line break is response output, and the e2e suite asserts page bytes. The vendored Bootstrap / jQuery keep their own headers and are listed in `NOTICE`. The copyright holder and year are `copyrightHolder` / `copyrightYear`; changing them is that edit plus `licenseFormat`. Every jar carries `LICENSE` and `NOTICE` in `META-INF/`. **Each bundle's `THIRD-PARTY-NOTICES.txt` is generated** (`generateLicenseReport`, jk1 plugin, over the war's and the launcher's libraries), and `checkLicense` — in `check`, and before `verifyDist` — refuses a bundled library that offers none of the licenses in `gradle/license/allowed-licenses.json`. A new dependency under another license is a decision for a person: never widen that file to make a build pass. **`verifyDist` refuses a bundle carrying Pro code**, by name (the Pro packages, the two plugin services files, `frontcache-pro*` jars, the Pro views and scripts) — at any depth, inside the war and every jar in it.

**CI** is `.github/workflows/build.yml`: `./gradlew build` and `./gradlew dist` (so `verifyDist` runs), then `./tests.sh`, on every push to `main` and every pull request. It publishes nothing.

Java 25 (via a toolchain: `languageVersion = JavaLanguageVersion.of(25)` and `options.release = 25` in `build.gradle`). Gradle wrapper is pinned to Gradle 9.7.0 (`gradle/wrapper/gradle-wrapper.properties`, the first release supporting JDK 25) — prefer the wrapper `./gradlew`.

## Versioning and release notes

**`version.properties` is the only version this project has.** It drives the Maven coordinates, the distribution archive names, the Docker tags and the installer's default `--version`. It is not in `gradle.properties`, which is git-ignored.

**Release notes go in `docs/release-notes/<the version in version.properties>.md`, and new work is APPENDED to that file.** That directory holds every published note, and `docs/release-notes/README.md` is its index — a row for the version is added when it is released, not before. The notes for the current version are a living document describing everything since the last *released* version — not a log written at release time. So when a change lands:

- read `version.properties`, and open `docs/release-notes/<version>.md`;
- fold the change into the section it belongs in, rather than adding a section per change. A rename joins the existing renames table and its count; an upgrade step joins the numbered list in **Upgrading**; a caller-visible change joins the **What to do** table;
- keep the file one release note. It is written for an operator deciding whether and how to upgrade, so it is organized by what they must do, not by what was committed.

**Never invent a version number.** A change lands in the version `version.properties` currently names — there is no "next release" to label it with. This applies to prose *and* to code: a javadoc saying "as of 2.11", a config comment saying "the pre-2.11 behaviour", a JSP comment saying "an edge older than 2.11". Those spellings are how the fiction spreads, and it is expensive to unwind — it once cost a full sweep of 26 files after work had been labelled two versions ahead of what `version.properties` said.

**Do not bump `version.properties` as a side effect.** Cutting a release is a deliberate act: the bump, a new `docs/release-notes/<new version>.md`, and the previous file frozen as history. A release is cut here and in the Pro repository at once, at the same version. Only do it when asked.

## Modules

- **frontcache-core** — all caching/proxy/include/resilience logic. Everything important lives here.
- **frontcache-server** — packages core as a deployable WAR + standalone Jetty (embedded Jetty 12, `:9080`). `build` finalizes by copying the WAR to `server/frontcache-base/webapps/ROOT.war`.
- **frontcache-console** — Spring MVC web UI for realtime stats / cache management (embedded Jetty 12 via `ConsoleJettyServer`, `:7080`; Gretty is gone). **Two screens per rules file, and the split is the point**: a top-level tab shows what the node PARSED — the rules in evaluation order with hit counts — and a Configs tab shows the file as it sits on disk, where a commented-out rule or a line the parser skipped is visible. Guard is `/guard-rules` + `/guard-configs`; bots is `/visitor-types` (**moved out of `/bot-configs` in 2.9.0** — `VisitorTypesController`, `visitor_types.jsp`, backed by `get-bots`) + `/bot-configs` (the raw `conf/bots.conf`, `get-bots-config`). `/bot-configs` was repurposed rather than left pointing at the moved screen, so a bookmark lands on the same file it always described. The console-side class names moved with the screens: `BotConfig`/`BotConfigsCaller` now mean the raw file, and the parsed model is `VisitorTypesConfig`. **The console authenticates as of 2.9.0** — one user, no roles, `user`/`password` in `frontcache-console.conf`, enforced by `ConsoleAuthFilter` mapped `/*` (not the container's own BASIC or FORM: both resolve a *role* through a container realm, which would mean a second credential file for the bundled Jetty launcher and someone else's realm config for a foreign container). **A browser signs in on a login page and carries a session; everything else still presents `Authorization: Basic`** — `curl`, the console image's `HEALTHCHECK`, anything already automated — and `ConsoleAuthenticator` is the one place either shape is compared. **What the login page changed is the refusal, not the check**: `WWW-Authenticate` sent to a page navigation opens the browser's native dialog on top of the page, so an unauthenticated request is a `302` to `/login?next=…` when `Accept` contains `text/html` and the unchanged `401` + challenge otherwise. `Accept` picks the *shape of the refusal* and never authorizes anything. **The filter never creates a session** (`getSession(false)`) — the console answers whatever can route to its port, and `getSession(true)` there allocates a session per scanner probe; `POST /login` is the only place one is created, after invalidating any existing one. **`ANONYMOUS_PATHS` is an exact-match set of four** (`/login` plus the login page's stylesheet, logo and favicon) and **must never become a prefix match**: `WebMVCConfig` maps `addResourceHandler("/**")` to a classpath location, so any path no controller claims falls through to a resource handler, and the test that pins this asserts the negative (`/static/js/console.js` is still refused). Adding exclusions at all was a reversal of the original design, made only for the login page, and `login.jsp` is deliberately standalone — no `inc/header.jsp`, whose jQuery and Font Awesome come from CDNs a console on an isolated network cannot reach, and nothing on the page discloses the version, the edges or whether the default password is still set. `<tracking-mode>COOKIE</tracking-mode>` is load-bearing: without it the container falls back on URL rewriting and the first post-login redirect carries `;jsessionid=<session id>` into the URL bar, the history and any front door's access log. **`Secure` on the cookie is `session-cookie-secure`, a config key rather than a detection** — the attribute is per-context while `X-Forwarded-Proto` is per-request, and defaulting it on means a plain-HTTP console accepts the password and returns to the login page. Sessions are in-memory: a restart signs everyone out, which is how a changed password takes effect. **Sign out is POST-only** (a `GET /logout` is prefetchable and embeddable) and session-only — a Basic caller has nothing to end, which is why a Basic-only console could have no logout at all. **No credentials means authentication is off, warned at `WARN` on every startup** — the console is a monitoring tool and an upgrade must not take it offline, but the silence is what made the `site-key`→`api-key` rename a hazard, so it warns; `user` without `password` is the one case that refuses to start, since that can only be a typo. On such a console `/login` is not a page either: it redirects away rather than rendering a form that ignores what is typed into it. The bundle ships `admin`/`admin`, so the default-password warning is load-bearing. `SameOriginFilter` runs after the auth filter and rejects cross-origin state changes — it is what covers `POST /login`, the one endpoint served without a credential. A `CharacterEncodingFilter` runs **before** both: without it POST bodies decode as ISO-8859-1, so a non-ASCII password works over Basic (that header is decoded UTF-8 explicitly) and fails through the form with no error anywhere, and the Configs editor writes mojibake to a node's disk. **All three filters need `<async-supported>true</async-supported>`** or `DashboardStreamProxyServlet.startAsync()` fails and only the realtime page breaks. An expired session is handled in JS at the two places that poll — a `401` from `/edges-status.json` sends the page to `/login`, and `fc-dashboard.js` probes once per `EventSource` error because `EventSource` never exposes the status and would retry a `401` forever. **Every Configs tab now renders a raw file, and is editable** — `resilience.properties`, `guard-rules.conf`, `bots.conf`, `dynamic-urls.conf` and `fallbacks.conf`, each read through its own `get-*-config` action and the servlet's `readConfigFile`, and written through the one `set-config` action. One `ConfigFileController`, one `config_file.jsp` + `inc/config_file_editor.jsp`, one `EdgeConfigFile`, one `ConfigFileCaller` — the five near-identical copies of each are gone, and the five URLs (`/hystrix-configs` included) are unchanged. **`EdgeConfigFile` is a class with getters and must not become a record**: JSP EL resolves `${edge.url}` through JavaBeans accessors, so a record fails at render time with `PropertyNotFoundException` and at compile time with nothing. **An edge is identified by URL, never by `FrontCacheClient.getName()`** — that name strips the scheme and everything from the first colon, so `localhost:8080` and `localhost:9080` (the e2e topology) collide; keying the fan-out by it used to drop a tab, and with a Save button on the tab it would send an edit to the wrong node. **Editing requires an authenticated console** (`config-editing` in `frontcache-console.conf`, default true, forced off with no `user`/`password`) mirroring the node's own rule (see `set-config` below); `POST /save-config` so `SameOriginFilter` covers it, and "Save to all nodes" confirms first because config files legitimately differ per node — the e2e fleet's deliberate differences are the example. Dynamic URLs and Fallback Config are the two with no parsed screen left over: `get-dynamic-urls` and `get-fallback-configs` still return their collections on the wire, and the e2e suite still pins them, but the console stopped rendering them — a pattern list or a three-column entry table without the file's comments does not say WHY a URL is never cached or what a fallback is for, and a commented-out line is invisible in it. **`get-fallbacks-config` (the file) and `get-fallback-configs` (the parsed entries) are one letter apart** and mean different things; the older plural counts entries, the newer one belongs to the file name.

  **The realtime page with no plugin is the Community page, and `fc-dashboard.test.js` pins it.** A console plugin may group edges into clusters and show a cluster's request rate on every card (the Pro plugin does, from `frontcache.console.clusters`): it installs a factory through `FcDashboard.setClusterFactory`, and the server names each stream's cluster through a `DashboardStreamContributor`. Without one, `clustersOf` returns `{}` and every stream renders unclustered; a Community console that finds a `clusters` block in its config ignores it and WARNs once at startup. Two things the core keeps for the plugin's sake: **cluster membership is by URL, canonicalized** through `FrontcacheService.canonicalEdgeURL` (`getDashboardStreamList` appends a trailing slash and `urls` has none), never by `FrontCacheClient.getName()`; and `FcCommandKeys.LEGACY_COMMAND_KEYS` has copies outside Java — the `order` block in `fc-dashboard.css`, and the plugin's — so a renamed command key is renamed there too. `frontcache-console/src/test/js` holds **the only JavaScript tests in the repo**, run by `:frontcache-console:jsTest` (`node --test`, wired into `check`, **skipped when node is absent** so a JDK stays the build's only prerequisite).

  The realtime monitor is **our own code** as of 2.7: `webapp/WEB-INF/static/js/fc-dashboard.js` (dependency-free — no d3, jQuery or underscore) plus `DashboardStreamProxyServlet`, which relays an edge's SSE stream to the browser because the console is a different origin. **Circuit-card order is CSS, not DOM order**: `fc-dashboard.js` inserts cards alphabetically and `fc-dashboard.css` pins the five known commands in the order a request travels (`Input-Request`, `Include-Request`, `Cache-Hit`, `Cache-Miss`, `Cache-Bypass`). Every superseded spelling is listed at the position of the name that replaced it — the console reads a mixed fleet, so an un-upgraded node must not shuffle the row — and `.fc-circuit` carries a default `order: 9` so a command the CSS does not name trails the five instead of leading them, which is what the initial `order: 0` did. The checked-in Netflix dashboard (`webapp/resources/hystrix/`) and the copied `com.netflix.hystrix.dashboard.stream` servlets are deleted. **The stream JSON did not change and must not**: the console is deployed separately from the nodes, so it reads a mixed fleet, and the `HystrixCommand` type literal is pinned indefinitely for external Turbine. Unlike the vendored renderer, nothing throws on a missing key. The proxy only contacts edges in the console's own edge list and appends the stream path itself — the Netflix original fetched any URL the caller named and attached the API key to it.

  `DashboardStreamProxyServlet` is **non-blocking at both ends**: `java.net.http.HttpClient` with `BodyHandlers.ofPublisher()` upstream (the JDK's own — deliberately not a second HTTP stack in the war; the blocking Apache client stays for the console's short request/response calls) and Servlet async with a `WriteListener` downstream. The two are joined by **demand**, so backpressure runs end to end: a chunk is requested from the node only once everything received has been written to the browser. Unlike the node's stream this relay never drops — a dropped chunk would cut an SSE frame in half — and demand is what bounds the memory instead. Demand is gated on the queue being empty, **not** on `isReady()`: the stricter version can hang, since `onWritePossible()` fires only on a not-ready→ready transition. An idle reaper ends a relay after 10s of silence, replacing the old socket timeout, because an `EventSource` on a quiet connection never reconnects by itself. The console's `fc-logback.xml` filters stdout at WARN (was ERROR, which hid both the allowlist refusal and the reaper).
- **frontcache-agent** — thin standalone HTTP client (`FrontCacheAgent`, `FrontCacheAgentCluster`) for app code to invalidate cache remotely. Minimal deps (httpclient5 only). Its public API is `String` in, `String` out and never exposes an HTTP type, which is why it could move to HttpClient 5 with the rest of the project without breaking any customer source.
- **frontcache-tests** — the end-to-end / integration suite (HtmlUnit + embedded Jetty 12), the Community one. Not published; run via the repo-root `tests.sh` — see the Build & test section.
- **Frontcache Pro is not here.** It is a set of jars built in a separate, private repository — a node module, a console plugin, and the license-file library they share — that plug in through `org.frontcache.module` and `org.frontcache.console.plugin` (see *Core architecture*). That repository includes this build as a Gradle composite, so it compiles against this tree: a change to a public type in either SPI, to `FrontCacheClient`'s generic `call*` methods, to `frontcache-core`'s test fixtures (`StubNode`) or to `frontcache-tests`' fixtures and homes can break it, and it refuses to build against a `version.properties` other than the one it pins. **Package names are split across the two** — `org.frontcache.license` (only `BuildInfo` is here), `org.frontcache.warmer` (only `WarmRequest`), `org.frontcache.io` and the console's `service` / `model` / `web.controllers` — which is legal on a class path and lets a Pro class reach a package-private core member, so a package-private member in those packages is not as private as it looks.
- `examples/` (jsp/php/spring, front-door, log-analytics), `benchmark/` and `scripts/` (dist, docker, and dev: `deploy-build-remote.sh` / `update-frontcache-code-remote.sh`, which push this working tree's server to a host over ssh - `--war-jar` adds a jar to the deployed war's `WEB-INF/lib`) are auxiliary; the docs are under `docs/` (see *Docs and examples* below).

## Core architecture (frontcache-core)

Request flow centers on **`FrontCacheEngine`** (singleton via `getFrontCache()`), reachable two ways:
- **`FrontCacheServlet`** — standalone reverse-proxy mode (forwards to a configured origin host/port).
- **`FrontCacheFilter`** — servlet-filter mode embedded in the origin app's container.

Both delegate to `FrontCacheEngine`, which orchestrates three pluggable subsystems:

1. **CacheProcessor** (`org.frontcache.cache`) — interface defining `processRequest`, `putToCache`, `getFromCache`, invalidation, and `doSoftInvalidation`. Implementation is chosen at runtime from the `front-cache.cache-processor.impl` property via reflection in `CacheManager`; default is **`L1L2CacheProcessor`** (L1 = Ehcache in-memory, L2 = Lucene on-disk index under `FRONTCACHE_HOME/cache/l2-lucene-index`). Other impls (same `org.frontcache.cache.impl` package): `InMemoryCacheProcessor`, `NoopCacheProcessor`. Cache TTL sentinels: `NO_CACHE=0`, `CACHE_FOREVER=-1`.
2. **IncludeProcessor** (`org.frontcache.include`) — scans cached responses for `<fc:include url="..."/>` markers and resolves them, sync (default) or `async`. Default impl `ConcurrentIncludeProcessor` resolves includes concurrently. JSP tag equivalents in `org.frontcache.tags`.

   **The non-bot client type is `guest`, renamed from `browser` in 2.9.0** (`FCHeaders.REQUEST_CLIENT_TYPE_GUEST`). The *value* moved, not just the constant, and it is a wire/config contract in four places, none of which fails loudly: `<fc:include client="guest">` and `maxage="guest:30d"` in page markup, the `client-type:guest` guard predicate, the client-type column of both request-log lines, and — because `WebResponse` is stored in L2 as Gson JSON — the `expireTimeMap` keys of **every entry already in a Lucene index**. There is no alias for the old spelling: an existing L2 entry has no `guest` key, so `FCUtils.isWebComponentCacheableForClientType` logs an error and returns false, which means that URL calls the origin and is never re-cached (the save path requires it too) until the entry is invalidated. **Flush the cache when you upgrade** — `invalidate` with `filter=*` — and grep pages and `guard-rules.conf` for the old token.

   **`maxage` takes one TTL per client type as of 2.9.0** — `maxage="bot:30d, guest:1d"`, parsed by `WebResponse.setExpireTime`. There is one rule and the older prefix forms are the same rule with one entry: **a client type the value does not name is `NO_CACHE`**, so the map starts NO_CACHE for both keys and each entry overwrites its own. The three malformed cases are deliberately not alike: a duplicate type warns and the **first wins**; an unknown type **inside a list** is ignored, leaving its type uncached, because a list is an explicit request for a split and "cache for everyone" is the one outcome the author did not ask for; an unknown prefix as the **whole value** (`browser:30d`) still caches for both, which must not change — it is what an un-updated pre-2.9.0 page produces. The raw string is a **wire contract** passed through untouched (`CommonTests.clientTypeSplitTtl` asserts it byte-for-byte on the live header and the stored entry): the header is read with `collStr.iterator().next()`, so anything that splits it on the comma silently yields `bot:30d` and guests stop being cached. Nothing else moved — no new `expireTimeMap` key, so this is **not** a flush-the-cache upgrade — but **nodes upgrade before pages**: an older node splits on the first colon, fails to parse `30d, guest:1d`, and caches for neither type.

   **Two live TTLs share ONE entry**, since the cache key has no client-type dimension and must not gain one (it would double origin renders, which is the feature's whole benefit). So whichever client type re-renders resets both stamps: the shortest TTL sets how often the origin renders, the longer ones say who never has to trigger one. That is the point, not a compromise — but it also broke the eviction branch, which used to `removeFromCache` on any expiry. That was safe only while differing TTLs implied one of them was `NO_CACHE` (and a `NO_CACHE` type never reaches the expiry check). An entry is now dropped only once `getExpireTimeMillis()` — `max(T_bot, T_guest)`, the predicate `purge()` already used — is in the past. **The block is duplicated in `CacheProcessorBase.processRequest` and `IncludeProcessorBase.getIncludeFromCache`; fixing one only is how this regresses.** No e2e test can catch it: there the origin is up, so the refetch puts a wrongly deleted entry straight back. It is visible only when the write back is refused — a fallback, a 5xx, an empty body — which is what `TwoLiveTtlEvictionTest` and `IncludeTwoLiveTtlEvictionTest` construct.

   **As of 2.9 an include carries two URLs, and confusing them is the one silent failure here.** The *public* URL is what the entry is keyed, request-logged and fallback-resolved on; the *fetch* URL is what goes on the wire. Before 2.9 they were one string, so a cache-missing include was fetched against the `Host` header — out to the CDN and back in at the front door of the node already serving the page. `front-cache.include-fetch-target` (default `origin`, `edge` restores the old path) moves only the fetch, via `FCUtils.rebaseURL`; `FCUtils.canonicalizeURL` stays the single normaliser for both — two normalisers was itself a bug, one that split the request count. Because the loopback no longer arrives at the front door, `IncludeProcessorBase.fetchIncludeFromOrigin` now owns what the re-entering request used to do on its way through: `setUrl(publicURL)`, the `putToCache`, and the request-log line. Skip the cache write and every include becomes an uncached origin call, forever, with nothing in the logs to say so.

   **Filter mode is the exception that needs the marker.** There the origin *is* the app the filter is installed in, so the fetch re-enters this same Frontcache — and a re-entered request keys its own cache write on the `Host` it arrived at, which would put the fragment under a second key. `isLoopbackOriginFetch` therefore marks that fetch `x-frontcache-dynamic-request` so the re-entry serves without storing. Read `callerMarkedDynamic` **before** adding that marker: a caller marking its own call dynamic (the combine envelope) means "not cacheable", the marker added here means "we will cache it, you must not". The combine envelope gets neither the cache write nor a log line — `logCombinedInclude` writes one per member, which is the accounting that matches the page.

3. **Command wrappers** (`org.frontcache.resilience`) — every origin call is wrapped in an `FcCommand` (`FC_ThroughCache`, `FC_BypassCache`, `FC_Total`, etc.) for circuit breaking + metrics. **Netflix Hystrix is gone**: `FcCommand` runs on Resilience4j 2.x (`FcResilienceConfig` parses `conf/resilience.properties`, `FcResilienceRegistry` holds the breakers/bulkheads/time limiters, `FcThreadPools` owns the executors, `FcCommandMetrics` produces the dashboard numbers). Fallbacks resolved by `org.frontcache.resilience.fr` (e.g. `FileBasedFallbackResolver`, configured in `fallbacks.conf`). `FallbackResolver` is a reflection-loaded extension point (`front-cache.fallback-resolver.impl`): as of 2.7 it declares `getFallbackEntries()` returning a flat `Set` — the old `getFallbackConfigs()` `Map<domain, …>` was **removed**, not defaulted, so a stale implementation fails to compile rather than being silently ignored, and `FallbackResolverFactory` refuses an un-recompiled one at load rather than letting it `AbstractMethodError` on the first fallback. The servlets under `resilience/stream` serve the dashboard SSE stream, emitted by `FcDashboardJson`, at `/fc-dashboard.stream` **and** at the pre-2.7 `/hystrix.stream`.

   **As of 2.9 `FC_Total` has two command keys, not one.** It picks between them on the request type `init()` already computed: client traffic stays `Input-Request`, an include arriving at the front door becomes `Include-Request` (`FC_Total.commandKeyFor`). A command key owns its own bulkhead and breaker, so the two no longer share permits. `Include-Request` reads ~0 on a standalone node once includes are fetched from the origin; **that is the point, and it stays** — with one counter there is no way to distinguish "includes no longer reach the front door" from "includes reach it and are counted as client traffic again", which is the bug that started all of this.

   **The command keys live in `FcCommandKeys`, and 2.9.0 renamed four of them**: `Input-Requests`→`Input-Request`, `Include-Requests`→`Include-Request`, `Origin-Hits`→`Cache-Bypass`, and `Cache-Origin-http` + `Cache-Origin-filter` **combined** into `Cache-Miss`, and renamed the thread pool `OriginHitsPool` → `OriginPool` — one pool shared by `Cache-Miss` and `Cache-Bypass`, named after what it is for rather than after either command. The old pair named the *transport*, which is a deployment property, not what the command does — but combining them is a real change on a **filter-mode** node, the only place both were live: the filter chain serves the page's origin call and HTTP serves its includes (`fetchOverHttp` never uses the chain), so two breakers over one origin became one. Sharing is more correct — one origin, one breaker, seeing all the evidence — but the permits are shared too. `Cache-Hits`→`Cache-Hit` followed later, the last key left in the plural — spelling only, nothing about the command moved, and it inherits from `Cache-Hits` like the rest.

   **A command key is a config contract, so `FcResilienceConfig.COMMAND_KEY_INHERITANCE` is what keeps an un-edited `resilience.properties` working**: every new key falls back on its old name (`FcCommandKeys.LEGACY_COMMAND_KEYS`), property by property, legacy `hystrix.*` prefix included. Without it a renamed key lands on the built-in `THREAD` / `maxConcurrentRequests=10` / `timeout=1000` — for an origin call tuned to ten seconds that is an outage, not a metrics change. **It is walked as a CHAIN, not one hop**, because the split and the renames stack: on a pre-2.9.0 file `Include-Request` → `Input-Request` → `Input-Requests`, and only the last of those is in the file. `Cache-Miss` inherits from `Cache-Origin-http` (the key every mode used), so a node that tuned `Cache-Origin-filter` differently is the one case that must set `Cache-Miss` explicitly. **Pool keys have the same fallback** (`LEGACY_THREAD_POOL_KEYS`, one hop — there is no chain to walk), and there it matters more: a command key that resolves to nothing lands on a different number, a pool key that resolves to nothing lands on `threadpool.default.coreSize` or the built-in **10**, capping every origin call on the node. The e2e **filter** node's `conf/resilience.properties` is deliberately left on the pre-2.9.0 key names, alongside the legacy `hystrix.*` key prefix it already tests, so the suite fails if the fallback regresses.

   **`resilience.properties` can be reloaded without a restart as of 2.9.0** (`reload-resilience`, `FcResilienceReload`), and the reason it needs a class of its own is that re-reading the file applies *nothing*: `FcResilienceConfig` is a cached singleton, `FcResilienceRegistry` caches a breaker/bulkhead/limiter per command key, and `FcThreadPools` caches an executor per pool key and reads config only in `create()`. So the reload re-reads, then drops the cached Resilience4j objects, then re-applies pool geometry **in place** on the same executors. Two things it cannot do are reported in the response rather than left to be inferred: **dropping the breakers loses circuit state** and every rolling window the dashboard reads, and **`maxQueueSize` cannot be applied at all** — it selects the queue *type* at construction (`< 1` = `SynchronousQueue`, which rejects rather than buffers) and a running executor's queue cannot be replaced, while `coreSize`/`maximumSize`/`keepAliveMinutes` can. Silently ignoring that last one is how an operator concludes the setting does nothing. `reapplyGeometry` also sets core and maximum **in the order that does not throw** — growing needs the maximum raised first, shrinking needs the core lowered first.

   As of 2.7 that stream is **Servlet 3.1 async with non-blocking output** — `doGet` accepts and returns, so no thread is dedicated to a viewer (both `web.xml`s therefore need `<async-supported>true</async-supported>`). Writes are gated on `ServletOutputStream.isReady()` so a stalled reader cannot stall the shared publisher thread; each subscriber has a bounded queue that drops its *oldest* frame. Two non-obvious invariants, both silent when broken and both covered by `FcStreamSubscriberTest`: `offer()` must also drain, because `onWritePossible()` only fires on a not-ready→ready transition and a drained-while-ready connection is never called again; and the `maxConcurrentConnections` slot is released from `Subscriber.close()` (CAS-guarded, exactly once) rather than a `finally`, since the request no longer outlives the connection. **The per-drain `out.flush()` is load-bearing** — without it the container aggregates frames and delivers them in ~3-second bursts, which no test that merely asserts "frames arrive" will catch; `theFirstFrameArrivesWithinAPublishTick` is what does.

   The Hystrix rename landed in 2.7: package, config file and endpoint all moved. What deliberately did **not** move, because each is a wire/config contract rather than an internal name — `/hystrix.stream` (kept indefinitely), the `hystrix.command.*` / `hystrix.threadpool.*` property prefixes (accepted alongside `resilience.*` indefinitely), `RequestContext`'s `"hystrixError"` context key, and the `HystrixCommand` / `HystrixThreadPool` JSON type literals the dashboard dispatches on.

Other key pieces:
- **`FCConfig`** — static config loader. Resolves `FRONTCACHE_HOME` from `-Dfrontcache.home` or `$FRONTCACHE_HOME`, then loads `frontcache.properties` plus `dynamic-urls.conf` (URL patterns never cached). It no longer parses `bots.conf`: `FCConfig.getBotUserAgentKeywords()` delegates to `BotClassifier`, so one file has one reader. **`init()` runs from the static initializer and nowhere else** — the call in `FrontCacheEngine.getFrontCache()` is commented out, so the `reload` action re-reads neither `frontcache.properties` nor `dynamic-urls.conf`; the action's name overstates what it does. What `reload` does is rebuild the engine — guard rules, fallbacks, the HTTP client, and `bots.conf` via `BotClassifier.reload()` — and **until 2.11.0 it took the node down instead**: `stop()` called `FCConfig.destroy()`, which nulled the properties nothing re-reads, so the rebuild threw `NullPointerException` and left no engine. With that gone the same `stop()` still broke the node quietly, by destroying the cache and include processors that `CacheManager` / `IncludeProcessorManager` hand straight back to the next engine (disposed Ehcache, closed Lucene writer, shut-down executors). So **FCConfig and both processors are process-wide and outlive an engine**: `FCConfig.destroy()` no longer exists, and `stop(shutdown)` destroys the processors only on a real shutdown (`FrontCacheEngine.destroy()`), never on `reload()`. `FrontCacheEngineReloadTest` pins both. `reloadDynamicURLs()` (the `reload-dynamic-urls` action) is the one live reload, and `dynamicURLPatterns` is `volatile` and **replaced wholesale, never `clear()`+`addAll()`d** — the old in-place mutation was safe only because its single caller ran before any request existed, and a request thread reading a half-filled set caches a URL that must never be cached. `getWritableConfigFile(name)` returns the conf-dir path a management write targets, or **null, which means refuse the write** — `getConfigInputStream` falls back to the classpath, so the file the console is displaying may not be a file on disk at all.
- **`BotClassifier`** (`org.frontcache.bots`) — decides the client type from `conf/bots.conf`, replacing the nine-line User-Agent scan that was `FrontCacheEngine.getClientType()`. The file now takes **guard-rules syntax** (`<name> | <predicate> ; … | <bot\|guest> [| dry-run]`, first match wins) on top of bare keyword lines, and shares the guard machinery outright: `GuardRuleParser.splitFields`, `GuardPredicateFactory` (with a new `Scope`), `ClientIpResolver`, and the promoted `org.frontcache.core.Cidr`. New predicates `ua~`, `ua-contains:`, `client-ip:<cidr|@file>` are available to **both** files; `client-type:` and `rate:` are refused in bots scope — the first is circular, the second counts, and classification runs per include. Order is built-in `no-user-agent`, file rules, keyword rules, built-in `default`, so an explicit rule always beats a keyword; every rule carries a `LongAdder` hit counter and only the *deciding* rule counts (dry-run counts and continues), which is what makes a zero in the console's Hits column mean "shadowed". Three things to know: **`client-ip:` must resolve through `ClientIpResolver`** and never `FCUtils.getClientIP()`, or a client sending `X-Forwarded-For` puts itself inside any block the file names — including a `guest` exemption; **bare keywords are case-insensitive as of 2.9.0** (they were `String.contains()`, so a file listing `Googlebot` did not match `googlebot/2.1`), a deliberate change with no compatibility flag; and **the verdict vocabulary stays `bot`|`guest` and cannot grow** — it keys `WebResponse.expireTimeMap` in every L2 entry already on disk, which is what made the 2.9.0 `browser`→`guest` rename a flush-the-cache upgrade. The client type is not a judgement: it selects a behaviour profile (TTL, cache vs origin, whether an include resolves), and guard rules reading it back through `client-type:` are one consumer among several. Reload without a restart via `action=reload-bots`; `get-bots` carries `botRules` **beside** the unchanged `botKeywords`, since the console upgrades independently of the fleet. Classification happens in `FrontCacheEngine.init()` **before** the guard engine, and that ordering must not drift. **An `<fc:include>` would otherwise be classified on evidence its page did not have** — its socket peer is the sibling node, and an async include is resolved after the servlet request was recycled, so it may see no cookies at all; page and fragment would then read different branches of one `expireTimeMap` and the fragments would quietly stop being cached. So `FCUtils.includeDynamicCallHttpClient` sends `x-frontcache-client-type` on the include fetch and `FCUtils.propagatedClientType` adopts it **instead of** classifying — but only from a peer in `trusted-proxies`, only on a request that arrived as an include, and only for a value that is `bot` or `guest`; `isIncludedHeader` **drops** an inbound one so a client's claim is never relayed onward by us. Empty `trusted-proxies` (the default) means propagation is off and everything is classified on its own, which is why a `cookie:`/`client-ip:` rule wants `request-type:toplevel` until it is set — and a trusted nginx passing client headers verbatim must strip the header itself. Adopted requests are decided before the rules, so **no rule counts a hit for them** — deliberate, and the same reasoning as the rate limiter's `scope=toplevel`. The e2e **standalone** node's `bots.conf` uses the rule format and the **filter** node's is deliberately left bare-keyword-only, so the suite fails if reading a pre-2.9.0 file regresses. Not built: shadow mode and the `classify` explain endpoint. `ptr-verified:` (forward-confirmed reverse DNS) was **considered and dropped** — it is the only part needing a DNS cache, an executor and TTLs, and `client-ip:@file` catches the same impostors with a byte-prefix compare.
- **`RequestContext`** / `FCUtils` / `WebResponse` (`org.frontcache.core`) — per-request state, HTTP plumbing, and the cacheable response model. The origin host/ports and the node's domain are plain fields on `FrontCacheEngine`; `RequestContext.getDomain()` carries the domain per request.

**HTTP client: Apache HttpClient 5.3.1** (`org.apache.hc.*`), as of 2.8. The 4.5 branch ended at 4.5.14. Three things about the move are worth knowing because each is silent when broken. **Timeouts moved off `RequestConfig`**: socket read timeout is `SocketConfig.setSoTimeout` and connect timeout is `ConnectionConfig.setConnectTimeout`, both on the connection manager. `RequestConfig.setResponseTimeout` is *not* the old socket timeout — it bounds the wait for the response head, not inactivity per read — so `front-cache.http-client.socket-timeout` must never be mapped onto it, or the connection-leak fix it exists for silently reverts. **The retry strategy is constructed, not defaulted**: `new DefaultHttpRequestRetryStrategy(1, TimeValue.ZERO_MILLISECONDS)`. It does cover the stale-keep-alive `NoHttpResponseException` (which extends `IOException` directly, not the non-retriable `ConnectionClosedException`), but the no-arg constructor sleeps a full second before retrying. **Origin calls use `executeOpen(...)`**, not `execute(...)`: the `execute` overload returning an open response is deprecated in 5.3, and `executeOpen` is its replacement. Frontcache needs an open response it can close from a different thread than the one that opened it (`FC_BypassCache` → `RequestContext.releaseHttpClientResponse()`), so a scoped `HttpClientResponseHandler` cannot express what it does. No deprecated HttpClient API remains.

**The three reflection-loaded extension points take `org.frontcache.core.FcHttpClient`, not an Apache type** (2.8). `CacheProcessor.processRequest` / `doSoftInvalidation`, `IncludeProcessor.processIncludes` and `FallbackResolver.init` used to take `org.apache.http.client.HttpClient`, which meant every HTTP-library upgrade broke every third-party implementation. `FcHttpClient` is three methods — `fetch(url, headers, ctx)` (origin, resilience-wrapped, filter-mode aware), `fetchOverHttp(...)` (includes: always HTTP, never the filter chain) and `fetch(url)` (one-shot bootstrap, non-2xx is a return value not an exception) — implemented by `ApacheFcHttpClient`, which with the resilience commands is now the only place in core that knows an HTTP library exists. `FrontCacheEngine.getHttpClient()` still returns the Apache type; it is internal plumbing, not an extension point.

**One node serves one site.** Multi-domain support is retired: `front-cache.domains` and any `front-cache.domain.*` override make the node refuse to start (`FrontCacheEngine.rejectRetiredDomainConfig`). `front-cache.default-domain` (the **site's public hostname**) and `front-cache.api-key` (the management API's shared secret) are unaffected. Per-domain config directories (`conf/<domain>/`) are gone — `bots.conf`, `dynamic-urls.conf` and `fallbacks.conf` are read only from the top level, and a leftover `conf/<domain>/` holding one of them also refuses to start. `DomainContext` is deleted; the origin config lives on `FrontCacheEngine`. Nothing is domain-scoped any more: `CacheProcessor`'s methods, `FallbackResolver.getFallback`, `FrontCacheClient.putToCache` and `WebResponse` all lost their `domain`, Lucene has no `DOMAIN_FIELD`, and `invalidate` with `filter=*` empties the whole node (replicated entries included). `RequestContext.getDomain()` survives for request logging and the command group key.

**`front-cache.default-domain` is what Frontcache PUTS IN a URL it hands to a client**, and conflating that with the Host a request arrived under was a live bug until 2.9.0. A node is reachable under several names — the CDN's, an internal alias, its own, a bare IP — and guard-rule `${url}` / `${url:enc}` / `${host}` and `FCUtils.transformRedirectURL` used to echo whichever one arrived, so an origin's internal hostname reached browsers through the `return=` of a login redirect. They now read `RequestContext.getPublicHost()` (the domain, via `FrontCacheEngine.getPublicDomain()`, which maps unset/blank/the `FCConfig.DEFAULT_DOMAIN` placeholder onto null so `https://default-domain/…` can never be emitted; null falls back to the arriving host). **The distinction is the whole point and neither half may drift**: `getFrontCacheHost()` stays the Host that arrived, because predicates (`host~`, `host:ip`), the cache key and the URL column of both log lines depend on it — normalizing the log column in particular would make the fix unverifiable, since that column is the canary. The scheme has the same split: `getPublicProtocol()` is `front-cache.public-scheme`, else `X-Forwarded-Proto` from a peer in `front-cache.client-ip.trusted-proxies` (`ClientIpResolver.isTrustedPeer` — a client that could set it would choose the scheme of a URL we vouch for), else the connection; `getFrontCacheProtocol()` is deliberately left alone because the cache key is built from it. `front-cache.default-domain` is also an allowed redirect target on its own, and `GuardRuleEngine.sanitizeTarget` re-checks the host *after* placeholders expand — the load-time check in `GuardRuleParser` can only see the static string. Optional `front-cache.origin.forward-public-host=true` sends `X-Forwarded-Host` / `X-Forwarded-Proto` to the origin so the app builds public URLs itself.
- **`FcMetricsExport`** / **`FcMetricsServlet`** (`org.frontcache.metrics`) — optional Prometheus / OTLP export via Micrometer, driven by `front-cache.metrics.export` (default `none`). Bridges `FcCommandMetrics`, the Resilience4j registries, and the cache. Serves `/fc-metrics` **behind the API key** (`org.frontcache.core.ApiKey`, shared with `FrontCacheIOServlet` and — for how the credential is read — the SSE stream). Every caller sends `Authorization: Bearer <api-key>`: the agent, the console, `FrontCacheClient`, node-to-node replication and Prometheus (whose scrape_config cannot set an arbitrary header, which is what settled the form). The pre-2.7 `x-frontcache-site-key` header is still accepted, deprecated and warned about once, because frontcache-agent is embedded in customer apps and upgrades on their schedule. **`front-cache.management.port` is gone** (with `ManagementPort` and `FcDashboardStreamSecurityServlet` — the dashboard stream's `web.xml` now names `org.frontcache.resilience.stream.FcDashboardStreamServlet` directly): it compared `getServerPort()`, which the servlet spec derives from the Host header, so it was a *routing* hint a caller could satisfy at will and never an access control. The API key is the only one; confining management traffic to one connector is the reverse proxy's job.

  **The property is `front-cache.api-key`, renamed from `front-cache.site-key` in 2.9.0, with no fallback**: a config file still using the old name leaves the node with no key at all — management API, dashboard stream and `/fc-metrics` open — rather than failing. The concept was renamed everywhere it is spelled: `ApiKey`, `FCUtils.isAuthorizedApiKeyHeader`, `FrontCacheEngine.isNodeApiKey`, the agent/client constructor arg, the console's `apiKey` HOCON key (a console conf still saying `siteKey` refuses to start, since `Config.getString` throws on a missing key), the `frontcache-api-key.conf` classpath resource and Docker's `FC_API_KEY`. **Two spellings deliberately did NOT move**, both because they are fixed strings something older sends: the deprecated `x-frontcache-site-key` header, and the retired per-domain `front-cache.domain.<domain>.site-key` that `findRetiredDomainKeys` exists to detect. Series are `frontcache_*`, labelled only by command/event/quantile/pool/name/kind/state/result/tier and never by URL — the allowlist is asserted in `FcMetricsExportTest`.

  **Cache metrics** come from two places, on purpose: read outcomes from `FcCacheMetrics` (`org.frontcache.cache`), counted on the request path inside each `getFromCacheImpl` because that is the only point where the answer *and* the tier are both known; sizes from `CacheProcessor.getCacheStats()` (a `default` method, so a third-party processor keeps working), sampled at scrape time from state the process already holds — `IndexWriter.getDocStats()` rather than opening a `DirectoryReader`, since `getCacheStatus()` is built for a console page and is too expensive to scrape. `CacheStats.UNKNOWN` is distinct from zero: an untracked number gets no series at all rather than a gauge reading a flat zero. The exporter uses `CacheManager.existingInstance()` so a scrape never starts the cache.
- **`RequestLogger`** (`org.frontcache.reqlog`) — logs request/include perf either to a log or to HTTP response headers when `front-cache.log-to-headers=true`. **The column layout is read by position outside this jar** (`logs/frontcache-requests.log`), and [the 2.7.0 release note](docs/release-notes/2.7.0.md) pins it indefinitely, so a new column goes on the **end** — as client-type and user-agent did in 2016. **`client-type-rule`, added in 2.10.0, is the one exception and must stay one**: it names the deciding `bots.conf` rule (`RequestContext.getClientTypeRule()`, stamped by `FrontCacheEngine.setClientType`) and was inserted *immediately after* the client type rather than appended, because `bot "bingbot"` is one fact and a consumer that has to skip a user-agent to pair them eventually pairs them wrong — which moved the user-agent column, the fallback reason and the guard reason/status right by one in both log files. A bare-keyword rule's name is the keyword, and `Yahoo! Slurp` ships in `bots.conf`, so **the field must stay quoted** or the column count changes on exactly the lines an operator is reading when a crawler misbehaves. `RequestLoggerClientTypeRuleTest` pins the column numbers (including that the user-agent moved by one and no further), and `CommonTests.traceHeaderNamesTheRuleThatDecidedTheClientType` pins the engine→context→log wiring on both e2e nodes.
- **`FrontCacheIOServlet`** + `org.frontcache.io.*ActionResponse` — the management/admin API (dump keys, get-from-cache, invalidate, reload, patch, cache status, etc.). This is what `frontcache-agent` and the console talk to.

  **This is a wire format between separate deployments**, so every response change carries both shapes: the console upgrades independently of the fleet, in either order. As of 2.7 `get-bots` / `get-dynamic-urls` / `get-fallback-configs` return flat collections (`botKeywords`, `dynamicUrlPatterns`, `fallbackEntries`) *and* the pre-2.7 single-entry `Map<domain, …>` beside them, and `get-hystrix-configs`/`hystrixConfig` became `get-resilience-configs`/`resilienceConfig` with the old names still accepted. `ActionResponse`'s `@JsonIgnoreProperties(ignoreUnknown = true)` is what makes reading an unknown field free. An **unrecognized action returns a ping response, not an error** — so `FrontCacheClient` treats a ping as "this node predates the rename" and retries with the old action name. `LegacyDomainKeyedField` holds the translation; `ConsoleWireFormatCompatibilityTest` and `ResilienceConfigActionFallbackTest` are the contract.

  Config-file reads here must catch `Exception`, not `IOException`: `FCConfig.getConfigInputStream` signals "file absent" by **throwing**. Use the servlet's `readConfigFile` helper, which all four raw-file actions go through — two of them had shipped broken for exactly this reason.

  **`set-config` writes one config file and applies it — one action for all five, and `file` is a logical id, never a path.** `ConfigFile` (the enum) *is* the allowlist; a caller-supplied file name, even one checked for `..`, is how this becomes an arbitrary file write, so it is not accepted at all. `frontcache.properties` is deliberately not in the enum: it holds the api-key, `FCConfig` has no live re-read, and a typo in it is a node that does not serve. The operation lives in `ConfigWriteAction` with no `HttpServletRequest` in it (so the gates are unit-testable) and the servlet method is parameter extraction plus `ApiKey.isAuthorizedToWrite`. Four things about it are silent when broken: **`ApiKey.isAuthorizedToWrite` refuses an un-keyed node where `isAuthorized` allows it** — the third rule in that family, because an un-keyed node is usually un-keyed by accident (an upgrade that left `front-cache.site-key` in the file) and remote configuration of request handling is not what that mistake should enable; **submitted CRLF must be normalized to LF and a trailing newline must NOT be added** (form submission converts a textarea's line breaks, so the first Save would otherwise rewrite every line ending — and `FRONTCACHE_HOME_STANDALONE/conf/bots.conf` ends without a trailing newline, which is what makes the e2e round-trip test able to assert byte equality); **validation refuses the whole file on any parse error**, because every one of these loaders skips a bad line and keeps going, which is right at startup and wrong as a Save button's only feedback — `ConfigFileValidator` delegates to `GuardRuleEngine.validate` and `BotClassifier.validate` so the console refuses exactly what the node would refuse, and neither touches live state; and **a node that predates the action answers a ping**, which parses cleanly into `responseStatus=OK`, so `FrontCacheClient.setConfig` checks for it explicitly — reporting a save that never happened is the worst outcome available here. `apply=false` writes without reloading. Writes can be turned off per node with `front-cache.management.config-write=false`, which is the setting for a fleet whose `conf/` comes from git or an image. `ConfigFileStore` owns the mechanics: atomic replace via a temp file **in the same directory** (`ATOMIC_MOVE` across filesystems throws), and `conf/<file>.backup-<yyyyMMdd_HHmmss>` capped at 10, following `backup-index`'s naming.
- **`EdgeToken`** (`org.frontcache.core`) — `front-cache.edge-token`, added in 2.11.0, lets a second-layer node in a chain (browser → edge → second layer → app) tell its own edge from a client that reached it directly. One production second layer was serving 71% of its traffic to clients that skipped the edge's guard rules. **One token per chain, sent and accepted by every node.** Nothing configures a direction, which is why a filter-mode node's own include fetch (an HTTP origin call back into itself) carries it for free. Per-edge tokens were decided against; rotation is `.previous`, which is accepted but never sent. It enforces nothing by itself: `init()` computes `RequestContext.isEdgeTokenValid()` and the guard predicate `edge-token` reads it. Five things are silent when broken:
  - **`EdgeToken.stamp` sends only to `front-cache.origin-host`.** The commands that call it are not origin-only: with `include-fetch-target=edge` an absolute include, or a `fallbacks.conf` init URL, can name any host, and the secret must not follow them.
  - **`FCUtils.isIncludedHeader` drops an inbound `x-frontcache-edge-token`**, and `stamp` uses `setHeader`, so a client's copy is never relayed.
  - **The predicate is refused on a node with no token.** `!edge-token` would otherwise match every request, and a redirect from a second layer to the public host is a loop through the edge. The refusal also makes the console's Save refuse such a file.
  - **A redirect rule using it needs `method:GET`.** `checkNoSelfRedirect` probes with a token-less, request-less context, so a bare `!edge-token | redirect:…` reads as a self-redirect loop.
  - **The e2e rule lives on the standalone node**, because the filter node must keep shipping no `guard-rules.conf`. The sending half is proven by `common/edge-token/echo.jsp`, which prints what the app behind the filter node received.

  The same change fixed `GuardRuleParser.checkRedirectTarget` reading `https://host${uri}` as a host named `host${uri}`. `${` now ends the host, and `sanitizeTarget` still re-checks the expanded host.
- **`FrontCacheClient`** / `FrontCacheCluster` (`org.frontcache.client`) — in-core client for invalidating one node or a cluster.
- **Warm requests** (`org.frontcache.warmer.WarmRequest`) — the request-path half of a cache warmer, kept in the core because it is on the request path; the warmer that drives it (lists, runs, the console screen) is Pro. **A warmer warms through the node's own front door** — a loopback `GET` with the key base's `Host` — so it has no cache logic of its own; an in-process fetch-and-store would be a third copy of the duplicated eviction block. A warm request is recognised by `WarmRequest.resolve` in `FrontCacheEngine.init()`, **before** `setClientType` and the guard: a 256-bit in-memory token (`WarmRequest.token()`, public only so a module can read it through `ModuleContext.warmRequestToken()`) from a loopback peer, with mode and client type in two sibling headers. It then takes the run's client type (rule `warmer`, no bots.conf hit), skips the guard, runs under `Warm-Request` (inherits `Input-Request`, checked first in `FC_Total.commandKeyFor`), and reports `x-frontcache-warm-result`; the engine echoes the key it built as `x-frontcache-warm-key`, so a caller can tell when a container keyed on the connection rather than on `X-Forwarded-Proto`. Three things are silent when broken: **every `x-frontcache-warm*` header must be dropped by `FCUtils.isIncludedHeader`**, or the token lands in the origin's access log; **a soft-expired entry and an `async` include are resolved synchronously on a warm request**, in `CacheProcessorBase.processRequest` **and** `IncludeProcessorBase.getIncludeFromCache` (the duplicated-block rule again) and `ConcurrentIncludeProcessor`, or the warmer's pacing paces the front door and not the origin; and **`refresh` mode never removes before overwriting**. A warm request must not carry `x-frontcache-request-id`, which would stop includes resolving. `FRONTCACHE_HOME/warmer/warmer.sh` (a curl loop over a URI list) is the Community way to warm a cache, and needs none of this.

- **Module SPI** (`org.frontcache.module`, 2.11.0) — how a plug-in reaches a node: `FrontcacheModule` (found by `ServiceLoader`, one instance per process), `ModuleContext`, `ManagementAction` / `ManagementRequest`, `NodeMode`, and the registry `FrontcacheModules`. A module is named only by its jar's `META-INF/services/org.frontcache.module.FrontcacheModule`; the engine, servlet, filter, `FrontCacheIOServlet` and `FcMetricsExport` name no module. `ServiceLoader` uses the SPI interface's class loader, so a module jar must sit where frontcache-core does: the same `WEB-INF/lib`, or the same launcher class path. Silent-when-broken:
  - **`CoreBoundaryTest` keeps Pro code out of the core.** The compiler refuses a core class naming a Pro class (the Pro jars are not on this build's class path), so the test guards what it cannot see: a Pro class or the module services file **put back** into the core — the `license` package except `BuildInfo`, `warmer` except `WarmRequest`, `pro`, `WarmerActions` and the warmer/license responses, all of which would compile, since the packages are split. Its `ALLOWED` map is **empty** and must stay so; its check against the Pro sources themselves runs only when they are beside the core, so here it skips. `FcMetricsExportTest` asserts a node with no module exports no `frontcache_license_*` / `frontcache_warmer_*` series.
  - **Never on the request path.** No module hook in `FrontCacheEngine.init()`, the processors, guard or commands — a node with no module serves byte-for-byte what a node with one serves. Request-path behaviour a module needs is a core primitive with a module user (warm requests, above).
  - **A module cannot stop a node or shadow a core action.** Everything `FrontcacheModules` calls is wrapped; a module that throws in `start` is dropped until the next start. `FrontCacheIOServlet` consults module actions only in its `default:` branch, after every core name, and a name no started module answers is still a ping — which is how a Community node answers `warmer-*` / `get-license` (`CommunityEditionTests` pins it on both e2e nodes). **A ping is never an answer** to a caller of a module action: it parses into any response with `responseStatus=OK`, so `FrontCacheClient.isPing` is how a client tells "this node has no such module".
  - **`modeKnown` may come before the engine**, so it reaches every *loaded* module, not only started ones; **`bindMeters` likewise** (`FcMetricsExportTest` builds an exporter with no engine), so a module's meters must read state at scrape time. Module meters bind after the core's own, keeping the names `FcMetricsExportTest` asserts.
  - **`reload` calls `stop(false)` then `start` on the same instance.** Module actions are re-collected on every start, from that start's `ModuleContext`.
- **Console plugin SPI** (`org.frontcache.console.plugin`, 2.11.0) — the console's half: `ConsolePlugin` (`ServiceLoader`, read once by `ConsolePlugins` before either Spring context), contributing `rootComponents()` (services → root context, via `ConsolePluginRootConfig`, a bean in `spring-core-config.xml`) and `webComponents()` (controllers/advice → `WebMVCConfig`'s `@Import`), `NavEntry`s, realtime-page scripts and stylesheets (the `fcPlugins` servlet-context attribute, rendered by `inc/menu.jsp`, `inc/cache_menu.jsp`, `inc/header.jsp`, `realtime.jsp`), banners/footer lines (`ConsoleNoticeProvider` beans → `${consoleNotices}`, `inc/header.jsp` / `inc/footer.jsp`), and stream data (`DashboardStreamContributor`, applied by `IndexController`). A plugin compiles against `org.frontcache:frontcache-console-classes`, the console's own classes published as a library. Silent-when-broken:
  - **`ConsoleBoundaryTest`** fails when a Pro console class, view, script or services file is back in frontcache-console, when a core console class names a Pro class, and when a core JSP/JS/CSS names a Pro screen (`licenseSummary`, `cache-warmer`, `fc-dashboard-cluster`, …) — that last is text, which no compiler sees. Render plugin things from `fcPlugins` / `consoleNotices`, never by name. `ConsoleWithoutPluginsTest` boots both contexts with no plugin and pins every hook empty.
  - **A plugin class in a package the console scans is still ONE bean** — Spring keeps the scanned definition and ignores the import of a class it already has; a second bean would fail every `@Autowired` of it as ambiguous at console start. Keep the console's component-scan packages as they are: a plugin relies on them.
  - **No plugin can add an anonymous path** — its controllers are behind the `/*` filters, and `ANONYMOUS_PATHS` has no extension point. Keep it that way.
  - **Plugin config is read by the plugin's beans** from `FrontcacheService.getConsoleConfig()` (no `configure(Config)` hook); `configKeys()` exists only so `ConsolePlugins.warnUnclaimedKeys` can WARN when a console config sets `clusters`, `cache-warmer` or `usage-dir` with no plugin to read it.
  - **JSPs from a plugin jar**: a `WEB-INF/lib` jar's `META-INF/resources/WEB-INF/views/*.jsp` renders through a forward, with JSTL and `fcPlugins`, and stays unreachable directly (404). On the **container** class path (`appRun`-style launches) Jetty scans `META-INF/resources` only in jars matching `CONTAINER_JAR_PATTERN`, so `ConsoleJettyServer` appends the `frontcache.jetty.container-jars` system property to it. Without it a plugin's beans load and its pages fail at the forward. A plugin's static files are served from its jar's `META-INF/resources/static` at `/js/…`, `/css/…` — not `/static/**`, which maps to the war's `WEB-INF/static/` only.

## FRONTCACHE_HOME layout

Runtime config lives in a `FRONTCACHE_HOME` directory (each runnable module ships its own: `frontcache-server/FRONTCACHE_HOME`, and the tests use `FRONTCACHE_HOME_FILTER` / `FRONTCACHE_HOME_STANDALONE`). `conf/` contains: `frontcache.properties`, `bots.conf`, `dynamic-urls.conf`, `fallbacks.conf`, `fc-l1-ehcache-config.xml`, `resilience.properties`, `frontcache-console.conf`, `fc-logback.xml`, `frontcache.id`. The L2 Lucene index and logs are written under `cache/` and `logs/`; a node with the Pro jars also writes an instance id and usage log under `usage/`, which is gitignored and excluded from every bundle (a shipped `instance.id` would make every install start as a copied directory); a Pro customer's `conf/frontcache.license` is likewise never shipped, and `verifyDist` refuses both.

When running, the relevant JVM system properties are `-Dfrontcache.home=...` and `-Dlogback.configurationFile=.../conf/fc-logback.xml` (the console additionally needs `-Dorg.frontcache.console.config=.../frontcache-console.conf`, or the `FRONTCACHE_CONFIG` env var it prefers — without one of them it starts with **no edge list at all** and every screen is empty). The `appRun` tasks in `build.gradle` set these for local runs; the console's reads `frontcache-console/config/frontcache-console.conf`.

## Docs and examples

The user-facing documentation describes the **published** artifacts (`org.frontcache:*` from
`https://repo.eternita.co/maven2`, and the `pavlikovskiy/frontcache-{server,console}` container images),
not this tree's working state: a doc is right when it matches the release a reader can download.

**Three topologies**, numbered consistently across the whole doc set — **#1** filter inside a Java app,
**#2** standalone proxy in front of an app in any language, **#3** GSLB → N standalone edges → Java
origin that also runs the filter. Always refer to them by these numbers.

**Ports.** Standalone server 9080/9443, console 7080/7443, the filter examples 8080/8443. The recurring
trap, called out in five places on purpose: `front-cache.http-port` / `https-port` are the
**client-facing** ports (80/443 behind a TLS terminator), not the port Frontcache listens on, because
they drive redirect rewriting.

**The origin is in charge of caching**, through the `x-frontcache-component-*` response headers (and the
`http://frontcache.org/core` taglib for Java/JSP origins). The header contract is owned by
`docs/concept.md` and echoed in `docs/install-guide.md` (troubleshooting) and
`examples/frontcache-php/README.md`; when it changes, all three change.

### Running the examples

Each example runs with one command, against the **published** artifacts — never this tree (see below). All three filter-mode examples need **JDK 25** —
Frontcache is Java 25 bytecode and Jakarta EE 10 (`jakarta.servlet`), so it will not
load on an older JVM or in a `javax.servlet` container.

```bash
cd examples/frontcache-jsp && ./gradlew appRun          # embedded Jetty 12 :8080 -> /example/index.jsp
```
```bash
cd examples/frontcache-spring && mvn spring-boot:run    # Spring Boot 3.x :8080 -> /example
```

`frontcache-php` has nothing to build: copy the directory into a `DocumentRoot` and run a
downloaded `frontcache-server` in front of it (use case #2 — see its README).

The front-door example has an executable check of its own (it needs Docker, so CI does not run it):

```bash
cd examples/front-door && ./smoke-test.sh
```

It brings the two-container compose stack up on 8080/8443 against a stand-in origin and
asserts the five things the nginx template exists to get right (cache hit on the second
request, unbuffered `/hystrix.stream`, gzip on proxied responses, `x-frontcache-*` headers
surviving the hop, `ORIGIN_PATHS` bypass). `KEEP=1` leaves the stack up; `FC_IMAGE=…` pins a
different image. Run it after touching `render-nginx-site.sh`, `docker/`, or `vm/`.

Render the nginx config without installing anything:

```bash
FRONTCACHE_HOST=fc-server ORIGIN_HOST=origin.example.com examples/front-door/render-nginx-site.sh | less
```

Jetty in the JSP example is pinned to **12.0.38** deliberately: 12.0.30+ bundles ASM ≥ 9.9,
which is required to scan Java 25 (class file v69) bytecode. An older Jetty crashes the
embedded launcher during annotation scanning.

### Conventions that are easy to break

**A release touches the docs in twelve places.** The current version is hard-coded in [README.md](README.md),
[docs/install-guide.md](docs/install-guide.md) (26 occurrences), all four example READMEs,
[examples/frontcache-jsp/build.gradle](examples/frontcache-jsp/build.gradle),
[examples/frontcache-spring/pom.xml](examples/frontcache-spring/pom.xml),
[docs/downloads.md](docs/downloads.md) (which lists the *two* current versions — roll the older one out), and the front-door
`docker-compose.yml`, `.env.example`, and `smoke-test.sh`. Grep for the old version and
change every hit; `version.properties` drives the build, not the docs. The docs deliberately tell
users to **pin an exact version**, so keeping `latest` out of examples is part of the message.

**The 2.6.0 image rename is a documented breaking change.** Through 2.5.1 the plain
`frontcache-server` tag was nginx + Frontcache on 80/443 and `-slim` was Frontcache alone;
from 2.6.0 there is one image and it is what `-slim` was, so it publishes **9080**, not 80.
Any new container snippet must use 9080 and must not imply the image terminates TLS.

**The checksum idiom is intentional.** Download instructions compare hash fields with
`shasum -a 256 … | cut -d' ' -f1` instead of `shasum -c`, because the published `.sha256` may
be a bare hash with no filename. Don't "simplify" it back. Likewise the installer is
`curl` → verify → `sudo bash`, never `curl | sudo bash`.

**Docs may link into the source now; examples must not build against it.** Until the source was
published, docs could only *name* source files (`frontcache-core/.../FCHeaders.java`, "in the Frontcache
product source repository"), never link them, and a round of such links was removed for that reason.
Both repositories are one now, so a relative link from `docs/` into a module is fine — but the older
docs still use the naming convention, and converting them is a pass of its own, not something to
half-do in passing. **Examples are the opposite**: they must stay standalone-copyable and consume the
published `org.frontcache:*` artifacts. `frontcache-jsp` once declared `includeBuild('../..')` to
compile against the source; the removal is documented in
[settings.gradle](examples/frontcache-jsp/settings.gradle). Never reintroduce a composite build or a
relative path from an example into the build.

The wiki is disabled (`/wiki` 302s to the repo home), so its links were dropped and the doc footers
cross-link each other instead — don't reintroduce a wiki reference unless someone enables it. And
`git ls-remote` the repository before trusting any `blob/master/…` URL: its default branch is `main`.

**Nothing here needs credentials.** Every download, repository and image referenced is public
read; the docs say so explicitly. API keys and TLS material are always placeholders
(`CHANGE_ME`, `YOUR_API_KEY`, self-signed certs).

**Build output stays out of git.** `.gitignore` covers every `build/` and `target/`, `.gradle/`, and
the `FRONTCACHE_HOME/{cache,logs}/` of the examples and the e2e homes — running an example or the e2e
suite dirties none of those. `benchmark/requests/` (a replayable dump of real traffic) is ignored too.
