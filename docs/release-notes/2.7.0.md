# Frontcache 2.7.0 — release note

Docs index: [../doc-index.md](../doc-index.md) · All release notes: [README.md](README.md)

**Six changes in this release, and none of them changes how the cache behaves.** The names Hystrix
left behind are gone — 2.6.x removed the library but kept its package, config file and endpoint so that
upgrade needed no config edit, and this release finishes the job. The console's read-only config views
stop reporting a domain that no longer exists. The `FallbackResolver` extension point drops that
same domain from its signature. The metrics export gains cache series — hit ratio, entries,
on-disk size, evictions — which is additive and off by default like the rest of the exporter. The
console's realtime monitor is now Frontcache's own code instead of a checked-in copy of the Netflix
Hystrix dashboard. And that monitor's stream runs on Servlet async at both ends, so an open dashboard no
longer holds a container thread on the node or in the console. Nothing about caching, includes, circuit-breaking or the metrics
stream's contents behaves differently.

**Every string you might have in a config file, a reverse-proxy rule or a monitoring URL still
works**, and exactly one config file needs a hand edit: `conf/fc-logback.xml`, which a node running the
old one tells you about in its log. If you maintain your own `web.xml` rather than deploying the shipped
one, that needs [two lines](#the-dashboard-stream-no-longer-costs-a-thread-per-viewer) as well.

**If you wrote your own `FallbackResolver`, you have a code edit too** — one method signature — and
Frontcache refuses an un-recompiled resolver at startup rather than failing later, mid-outage. That is
the only change here that can reach anyone's source. Start with [What to do](#what-to-do).

---

## What was renamed

| | 2.6.x | 2.7.0 |
| --- | --- | --- |
| Java package | `org.frontcache.hystrix` | `org.frontcache.resilience` |
| Config file | `conf/hystrix.properties` | `conf/resilience.properties` |
| Config key prefixes | `hystrix.command.*`, `hystrix.threadpool.*`, `hystrix.config.stream.*` | `resilience.*` |
| Dashboard stream | `GET /hystrix.stream` | `GET /fc-dashboard.stream` |
| Fallback logger name | `org.frontcache.hystrix.FallbackLogger` | `org.frontcache.resilience.FallbackLogger` |
| Console stream proxy (console-internal) | `GET /resources/hystrix/proxy.stream?origin=<stream URL>` | `GET /fc-dashboard-proxy.stream?origin=<edge URL>` |
| `RequestContext` accessors | `setHystrixFallback` / `isHystrixFallback` / `getHystrixReason` | `setFallbackUsed` / `isFallbackUsed` / `getFallbackReason` |
| `FallbackResolver` method | `getFallbackConfigs()` → `Map<domain, Set<…>>` | `getFallbackEntries()` → `Set<…>` |

Property **names** inside the config file did not change — only the prefix. Command keys
(`Input-Requests`, `Cache-Hits`, `Cache-Origin-http`, `Cache-Origin-filter`, `Origin-Hits`), the pool
name `OriginHitsPool`, and every value you have tuned mean exactly what they meant before.

The endpoint is not a move but an addition: **one servlet, two paths.** `/hystrix.stream` keeps
answering, indefinitely — see [What kept its old name](#what-kept-its-old-name-and-for-how-long).

### The one required config edit

In `conf/fc-logback.xml`, the logger that routes fallback lines to `logs/fallback.log`:

```xml
<!-- was -->
<logger name="org.frontcache.hystrix.FallbackLogger" additivity="false">
<!-- now -->
<logger name="org.frontcache.resilience.FallbackLogger" additivity="false">
```

A logger name is configuration, not code, so this one could not be kept compatible. Skip it and
`logs/fallback.log` stays **empty** rather than erroring — which reads as "no fallbacks happened",
the worst way for a diagnostic log to fail. So the node detects it and warns once:

```
WARN  o.f.resilience.FallbackLogger - conf/fc-logback.xml still declares the logger
      'org.frontcache.hystrix.FallbackLogger', renamed in 2.7. Fallback TRACE lines are going
      nowhere and logs/fallback.log will stay empty. Rename that logger to
      'org.frontcache.resilience.FallbackLogger'.
```

The shipped `fc-logback.xml` in the 2.7.0 archive is already correct. An upgraded container keeps the
copy you edited, so this one is still yours to make there too.

### Renaming the config file

Both file names are read, new one first:

```
WARN  o.f.resilience.FcResilienceConfig - conf/resilience.properties not found - reading the legacy
      conf/hystrix.properties instead. Rename the file; the legacy name is read for one release only.
      The hystrix.command.* / hystrix.threadpool.* KEY prefixes inside it stay supported regardless
      of the file name, so renaming the file is enough.
```

That last sentence is the short version: when you do rename the file, **`mv conf/hystrix.properties
conf/resilience.properties` and stop** — rewriting the key prefixes inside it is optional and can wait
indefinitely. Do the `mv` once you no longer intend to roll back to 2.6.x, not on upgrade day; see
[Upgrading](#upgrading).

Three rules worth knowing:

- **If both files exist, the new one wins outright and the legacy one is ignored entirely** — they
  are not merged, and the node says which file it is ignoring. A union of two half-populated files
  with the same keys is config nobody can reason about at 3am.
- **Within one scope the new prefix wins; a more specific key always beats a less specific one.**
  So `resilience.command.Cache-Hits.*` beats `hystrix.command.Cache-Hits.*`, but
  `hystrix.command.Cache-Hits.*` still beats `resilience.command.default.*`. A leftover legacy
  *default* cannot override a per-command value you just wrote.
- **With neither file present, every setting falls back to its built-in default and the node logs a
  `WARN`.** Up to 2.6.x a missing file threw instead. That was never intentional, and a missing
  tuning file is not a reason to refuse to serve traffic.

## What kept its old name, and for how long

Everything here is read by something outside the Frontcache jar, so renaming it would break a
deployment rather than tidy a name.

| Kept | Read by | For how long |
| --- | --- | --- |
| `GET /hystrix.stream` | reverse-proxy rules, guard rules, external Turbine, the console | **indefinitely** |
| `hystrix.command.*` / `hystrix.threadpool.*` / `hystrix.config.stream.*` keys | your config file | **indefinitely** |
| `conf/hystrix.properties` file name | your config file | one release, with a `WARN` |
| `org.frontcache.hystrix.fr.*` in `front-cache.fallback-resolver.impl` | your config file | remapped on load, with a `WARN` |
| `"hystrixError"` request-context key | a plugin compiled against 2.6 | **indefinitely** |
| `get-hystrix-configs` action and its `hystrixConfig` response field, alongside the current names | the console, which is deployed separately | until no supported console predates 2.7 |
| `bots` / `dynamicURLs` / `fallbackConfigs` domain-keyed fields, alongside the flat ones | same | same |
| `"type":"HystrixCommand"` / `"type":"HystrixThreadPool"` in the stream JSON | the console's monitor, and any external Hystrix Dashboard or Turbine | **indefinitely** |
| The request log's column layout | whatever parses `logs/frontcache-requests.log` | **indefinitely** |

A reviewer grepping the 2.7.0 jar for "hystrix" finds no package, no config file, no endpoint and no
log prefix — ten classes still contain the string, and every one of them is a row in the table above.
The `get-hystrix-configs` action now serves the contents of `conf/resilience.properties` (with the
same legacy fallback), so the console shows you the file the node is actually using.

## If you run the container

The image seeds only *missing* config files into an existing `conf` volume, which is what normally
makes an upgrade deliver new files without touching an edited one. A **renamed** file breaks that
rule's assumption: to the seeder `resilience.properties` looks brand new, so it would have copied the
image's **defaults** in under the new name, left your tuned `hystrix.properties` beside it, and — since
Frontcache resolves the new name first — quietly replaced your circuit-breaker tuning with shipped
defaults.

The seeder knows about the rename and skips it while your old file is present:

```
    ~ NOT seeding resilience.properties - your hystrix.properties is still there and stays authoritative.
      hystrix.properties was renamed to resilience.properties. Frontcache reads it for one more release and
      warns; rename it when convenient - the keys inside it need no change.
>>> Config in /opt/frontcache-server/FRONTCACHE_HOME/conf: 8 kept, 0 seeded from image defaults, 1 skipped (renamed, legacy file present)
```

So your tuning is what runs. It deliberately does **not** rename the file for you — that directory can
be a hand-managed mount, and nothing else in the entrypoint writes to it unless you asked via
`ORIGIN_HOST`. Rename it yourself when convenient; a fresh volume gets `resilience.properties`
directly.

`conf/fc-logback.xml` is a file you have edited, so it is kept as-is and the logger rename above is
still yours to make.

## New: cache metrics in the Prometheus / OTLP export

Only relevant if you have `front-cache.metrics.export` turned on; it is still off by default and this
adds no work to an upgrade.

2.6.0 exported resilience data — circuit state, command outcomes, thread pools. That set has a blind
spot: **a page cache that has quietly stopped hitting looks perfectly healthy through it**, because
every origin call succeeds. These are the series that show it:

```
frontcache_cache_reads_total{result="hit",tier="L1"}   24.0
frontcache_cache_reads_total{result="hit",tier="L2"}  187.0
frontcache_cache_reads_total{result="miss",tier="none"} 41.0
frontcache_cache_entries{tier="L1"}                    38.0
frontcache_cache_entries{tier="L2"}                  4021.0
frontcache_cache_disk_bytes{tier="L2"}            15463219.0
frontcache_cache_evictions_total{tier="L1"}           112.0
```

Hit ratio:

```promql
sum(rate(frontcache_cache_reads_total{result="hit"}[5m]))
  / sum(rate(frontcache_cache_reads_total[5m]))
```

The `tier` label is what makes that number actionable. A 90% hit ratio served almost entirely from
`tier="L2"` means L1 is too small for the working set — the requests are hitting, but off disk. The
ratio on its own cannot tell you that, and a rising `frontcache_cache_evictions_total` confirms it.

`frontcache_cache_disk_bytes` answers "will the cache volume fill up", which the entry count does not:
entry sizes on a page cache vary by orders of magnitude.

Two details that matter if you build alerts on these:

- **A tier that is not tracked produces no series, rather than a zero.** The in-memory cache processor
  has no disk tier, so it emits no `tier="L2"` series at all. A gauge reading a flat zero would be a
  line you could alert on that measured nothing.
- **Scraping does not start the cache.** A node whose cache has not initialised yet reports the read
  counters (correctly, as zeros) and no size series, rather than having its Lucene index opened by the
  scrape.

Labels remain a small fixed set — `command`, `event`, `quantile`, `pool`, `name`, `kind`, `state`, and
now `result` and `tier`. Nothing is labelled by URL.

## The dashboard stream no longer costs a thread per viewer

**Same URL, same JSON, same cadence.** No config-file change — but one line to add if you maintain
your own `web.xml`.

`GET /hystrix.stream` (and `/fc-dashboard.stream`) used to hold one container thread for the whole life
of each connection — asleep in earlier releases, then blocked on a queue. At the default
`resilience.config.stream.maxConcurrentConnections` of 5 that is five threads, and at a tuned 15 it is
fifteen, taken from the same pool that serves your traffic, for as long as somebody leaves a dashboard
tab open.

It now runs on Servlet 3.1 async with non-blocking writes: the request is accepted and the thread goes
straight back to the pool. Frames are written when the connection is ready to take them, so a viewer on
a slow link falls behind on its own rather than holding anything up — that part is unchanged in
behaviour, just no longer paid for with a parked thread.

**If you deploy Frontcache with your own `web.xml`, that servlet declaration needs two edits** — and
they go together, so make them together:

```xml
<servlet>
    <servlet-name>FcDashboardStreamServlet</servlet-name>
    <!-- was org.frontcache.hystrix.HystrixStreamSecurityWrapperServlet -->
    <servlet-class>org.frontcache.resilience.FcDashboardStreamSecurityServlet</servlet-class>
    <!-- new in 2.7: without this the container refuses the connection -->
    <async-supported>true</async-supported>
</servlet>
```

The shipped descriptor already has both. Neither mistake shows up at startup — the servlet has no
`load-on-startup`, so both surface on the first request to the stream, as **HTTP 500** and a dashboard
stuck on "unable to read the metrics stream". (Missing `async-supported` makes `startAsync()` throw
`IllegalStateException`; a stale class name fails to load the servlet.) Nothing else in this release
touches a deployment descriptor, and filter-mode deployments that register only `FrontCacheFilter` are
unaffected either way.

**The connection cap behaves the same, and releases the same.** A closed dashboard tab returns its slot
within a tick, as before. If you had raised `maxConcurrentConnections` purely to allow more viewers, the
thread cost that made a low cap prudent is gone — though the cap still bounds the work each publish tick
does, so it is not free to raise without limit.

**The console's relay between the node and the browser was changed the same way**, so an open dashboard
costs no thread at either end. That has its own operational consequences — see
[the console's realtime monitor](#the-consoles-realtime-monitor-is-our-own-code).

## The console's config views return flat lists

**If you run the console and the nodes at the same version, there is nothing to do here.** Everything
below is about running them at *different* versions, which is normal — they are separate deployments and
cannot upgrade simultaneously.

Four management-API responses changed shape:

| Action | 2.6.x | 2.7.0 |
| --- | --- | --- |
| `get-bots` | `bots`: `{"default-domain": [...]}` | `botKeywords`: `[...]` |
| `get-dynamic-urls` | `dynamicURLs`: `{"default-domain": [...]}` | `dynamicUrlPatterns`: `[...]` |
| `get-fallback-configs` | `fallbackConfigs`: `{"default-domain": [...]}` | `fallbackEntries`: `[...]` |
| `get-hystrix-configs` → `hystrixConfig` | — | `get-resilience-configs` → `resilienceConfig` |

The domain key was a leftover: multi-domain support was retired in 2.6.0, so that map has held exactly
one entry ever since, and the console's pages had to match on the literal `"default-domain"` to find it.

**Both shapes are on the wire.** A 2.7 node emits the new field *and* the old one, so a 2.6 console
keeps rendering these pages unchanged. A 2.7 console accepts either, so it keeps working against 2.6
nodes — including the renamed action, which it retries under the old name when a node does not
recognize the new one. Mix versions freely in either direction.

In the console UI, **Hystrix Configs** is now **Resilience Configs** at `/resilience-configs`. The old
`/hystrix-configs` URL still resolves to the same page, so existing bookmarks and links keep working.

If you script against `/frontcache-io` yourself, read the new field and fall back to the old one; the
old fields are kept until no supported console predates 2.7.

**One bug fixed along the way, present since 2.6:** `get-guard-config` failed outright on any node
without a `conf/guard-rules.conf` — the file is optional — instead of reporting the file as missing. If
your console's Guard Configs page has been erroring, that is why, and it now shows an empty config
rather than failing.

## The console's realtime monitor is our own code

**The page looks and works the same.** What changed is what is behind it.

The console carried a checked-in copy of the Netflix Hystrix dashboard — 29 files, 359 KB: d3 v2,
a jQuery 1.7 copy, tinysort, `tmpl.js`, Netflix's logos, and the `hystrixCommand.js` /
`hystrixThreadPool.js` renderers with their five HTML templates — plus two servlets copied from
Netflix, one of which was mapped to nothing and had been dead since 1.x. All of it is deleted. The
monitor is now one dependency-free script (`static/js/fc-dashboard.js`, 17 KB) and one stylesheet, and
the stream relay is `org.frontcache.console.web.DashboardStreamProxyServlet`.

**The metrics stream's JSON did not change**, and could not have: the console and the nodes it watches
are separate deployments, so a 2.7 console has to read a 2.6 node's frames, and an external Hystrix
Dashboard or Turbine may be reading the same endpoint. The field names, the `HystrixCommand` type
literal and the `/hystrix.stream` path are all exactly as they were.

Three things you may notice:

- **A blank panel is much less likely.** The old renderer asserted 36 JSON keys and threw on the first
  one missing, which blanked the whole panel and left nothing but a browser-console error. The
  replacement renders a missing number as `-` and draws the rest of the card.
- **The stream proxy only contacts edges the console knows.** It used to fetch whatever URL was passed
  in its `origin` parameter — and attach your `siteKey` to the request. It now refuses anything that is
  not in `frontcache.console.urls` (or added through the Edges page), and appends the stream path
  itself. If you had scripted against `/resources/hystrix/proxy.stream`, the endpoint is now
  `/fc-dashboard-proxy.stream` and takes an edge URL.
- **An unreachable edge now says so.** A refused connection or bad DNS used to arrive at the browser as
  an empty `200`; it is a `502` now, alongside the `401` a wrong site key already produced.

### The relay holds no thread either

The proxy used to sit in a blocking read loop, so every open dashboard tab held one of the console's
container threads for as long as it stayed open. It is now non-blocking at both ends — the JDK's own
`java.net.http.HttpClient` upstream, Servlet async downstream — and the two are joined by demand, so a
viewer on a slow link slows only itself. **No new dependency**: that client ships with the JDK. The
console's `web.xml` already has the `async-supported` this needs.

Two things you will notice, and one you should check:

- **An edge that goes quiet is dropped after 10 seconds** rather than held open, and the browser
  reconnects on its own. This replaces the old HTTP client's socket timeout, and it matters more than it
  sounds: an `EventSource` on a merely-*quiet* connection never retries by itself, so without this the
  dashboard would sit on stale numbers with nothing to say it had stopped listening.
- **The console reports two things it never could before** — a proxy request aimed at a host outside its
  edge list, and a relay abandoned because an edge went silent. Both are `WARN`.
- **Check this if you customized `conf/fc-logback.xml`.** The shipped file filtered stdout at `ERROR`,
  which is why those two messages went nowhere. It is `WARN` now. If you run your own copy, change
  `<level>ERROR</level>` to `<level>WARN</level>` in the `STDOUT` appender's threshold filter.
  Measured cost of the lower threshold: three Tomcat XML-schema notices at startup and nothing after.

Nothing else in the console needs a config change.

## If you extend Frontcache in Java

The package rename is **binary- and source-incompatible**. For everything below except the last
bullet, recompiling against `org.frontcache:frontcache-core:2.7.0` is all it takes — the names moved,
the signatures did not. The one real signature change is `FallbackResolver`, which has
[its own section](#if-you-wrote-your-own-fallbackresolver).

- `org.frontcache.hystrix` → `org.frontcache.resilience`, and `org.frontcache.hystrix.fr` →
  `org.frontcache.resilience.fr`. This covers `FallbackResolver`, `FallbackConfigEntry`,
  `FcCommand`, `FcCommandException`, `FcEventType` and the `FC_*` commands. Class names are
  unchanged.
- `RequestContext.setHystrixFallback` / `isHystrixFallback` / `getHystrixReason` →
  `setFallbackUsed` / `isFallbackUsed` / `getFallbackReason`. The underlying context **key** is
  still `"hystrixError"`, so a plugin that reads it through `get()`/`set()` keeps working
  uncompiled.
- Three servlet classes were renamed, which matters only if your own `web.xml` maps the dashboard
  stream: `HystrixStreamSecurityWrapperServlet` → `FcDashboardStreamSecurityServlet`,
  `FrontcacheHystrixMetricsStreamServlet` → `FcDashboardStreamServlet`,
  `FrontcacheHystrixSampleSseServlet` → `FcSampleSseServlet`. Filter-mode deployments that only
  register `FrontCacheFilter` are unaffected. **That same declaration also needs
  `<async-supported>true</async-supported>` in 2.7** — see
  [the dashboard stream](#the-dashboard-stream-no-longer-costs-a-thread-per-viewer) for both edits
  together.
- If you use `FrontCacheClient` to read config: `getBots()`, `getDynamicURLs()` and
  `getFallbackConfigs()` still compile and still return the single-entry map, but are deprecated in
  favour of `getBotKeywords()`, `getDynamicUrlPatterns()` and `getFallbackEntries()`, which return the
  collection directly. `getHystrixConfig()` is deprecated in favour of `getResilienceConfig()`, and
  `GetHystrixConfigActionResponse` is now `GetResilienceConfigActionResponse`.

### If you wrote your own `FallbackResolver`

**This one does not just need a recompile — it needs a small edit.** `front-cache.fallback-resolver.impl`
is a real extension point, and its interface changed:

```java
// 2.6
Map<String, Set<FallbackConfigEntry>> getFallbackConfigs();
// 2.7
Set<FallbackConfigEntry> getFallbackEntries();
```

Return the entries directly; drop the map. The key was always the single domain this node serves, which
has meant nothing since multi-domain support was retired in 2.6.0. `getFallback()` and `init()` are
unchanged.

The old method was **removed** rather than kept as a deprecated default. A default would have let a
resolver that still overrides only the old method compile and load — and then be silently ignored,
which for a fallback resolver means serving the wrong content at the exact moment the origin is already
down. A compile error is the kinder failure.

If you drop in a 2.6-built resolver jar *without* recompiling, it would otherwise load fine and then
throw `AbstractMethodError` on the first fallback — during an outage. Frontcache checks for the new
method before constructing your resolver and refuses it at startup instead, with this in the log:

```
ERROR ... front-cache.fallback-resolver.impl=com.example.MyResolver does not implement
      getFallbackEntries(). It was almost certainly compiled against Frontcache 2.6 ...
      Recompile it against this release. Falling back to
      org.frontcache.resilience.fr.FileBasedFallbackResolver.
```

The node keeps serving, on the built-in file-based resolver, until you recompile.

## Upgrading

- **Archive / installer**: unchanged procedure. `install-frontcache.sh --version 2.7.0` carries your
  config across, and rollback is still a symlink flip. It knows about the rename: your
  `conf/hystrix.properties` is carried over and stays authoritative, and the bundle's shipped
  `resilience.properties` lands beside it as `resilience.properties.new` — the same `.new` treatment
  every other changed default gets, so nothing is silently discarded and nothing silently outranks
  your tuning.
- **Config**: no file changed shape. The only edit needed on day one is the logger in
  `conf/fc-logback.xml`. Renaming `conf/hystrix.properties` can wait — see the rollback note below
  for why waiting is the safer order.
- **Rolling back to 2.6.x needs the old file name still present.** 2.6.x reads only
  `conf/hystrix.properties`, and it treats that file's absence as a hard error rather than falling
  back to defaults — so a node rolled back after you renamed the file **will not serve traffic**. So:
  upgrade first and leave the old name in place (2.7.0 reads it and `WARN`s), and do the rename once
  you no longer intend to roll back. That is what the one-release grace period is for. If you have
  already renamed it and need to roll back, rename it back as part of the rollback.
- **Cache**: the L2 index is pure cache and is unaffected; drop it or keep it.
- **Mixed fleets are fine.** 2.6 and 2.7 nodes can sit behind one load balancer and be monitored by
  one console. Nothing in this release changes anything on the wire.

What the renamed pieces look like in day-to-day use is in
[resilience-command-flow.md](../resilience-command-flow.md) and
[console-dashboards.md](../console-dashboards.md).
