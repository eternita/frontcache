# Frontcache 2.14.0-RC — release note

Docs index: [../doc-index.md](../doc-index.md) · All release notes: [README.md](README.md)

Everything that has landed since 2.13.0:

- **The standalone server no longer lets `X-Forwarded-For` choose the client's address.** The server bundle's launcher
  (`FrontcacheJettyServer`, which the bundles, the installer and the container image all run) installed Jetty's
  `ForwardedRequestCustomizer` with its defaults. Those defaults replace the request's remote address with the
  **leftmost** `X-Forwarded-For` entry (or RFC 7239 `Forwarded: for=`), from **any** peer - and the leftmost entry
  is whatever the client wrote. The node's resolver then took that value for the socket peer, found it untrusted
  and returned it, so the right-to-left walk over `front-cache.client-ip.trusted-proxies` that
  [guard-getting-started.md §5.1](../guard-getting-started.md) describes never ran. On a server-mode node behind a
  proxy, everything keyed on the client's address was keyed on a value the client chose:

  | | before | now |
  | --- | --- | --- |
  | `client-ip:` rules, `client-ip:@lists/…` | a client could step out of a block (or into one) | the address the trusted proxy saw |
  | `rate:` rules (`ip-flood`, a per-path limit) | a random `X-Forwarded-For` per request was a fresh bucket each time | one bucket per real client |
  | an evidence cookie bound to the address (`cookie-hmac:` with `ip`) | bound to the client's own choice | bound to the real address |
  | a `\| trap` rule's log reason, and a plugin banning on `guard.matched` | `honeypot#<anything the client wrote>`, and that address banned | the real address |

  Measured on a production node behind a loopback nginx with `trusted-proxies=127.0.0.1/32`: nginx passed
  `X-Forwarded-For: 10.0.0.5, <real>` and the node resolved `10.0.0.5`. The launcher still honours
  `X-Forwarded-Proto` / `-Port` / `-Host`, which is what it installed the customizer for - `https` / `443` behind a
  TLS-terminating proxy are unchanged. The forwarding headers still reach the node untouched; the resolver reads
  them. **Filter mode was never affected by this code**, but the same mistake can sit in the container in front of
  it - a Tomcat `RemoteIpValve` with no `internalProxies`, or Spring's `ForwardedHeaderFilter` ahead of
  `FrontCacheFilter`, rewrites the remote address from the leftmost entry in exactly this way. The e2e suite did not
  see it because its standalone node is a test fixture that never ran the launcher's connector;
  `FrontcacheJettyServerTest` now serves through that connector and the resolver together.

- **The plugin template and the example plugins moved to their own repository**,
  [eternita/edge-plugins](https://github.com/eternita/edge-plugins): `examples/plugin-template/` is now its
  `plugin-template/`, and `examples/plugins/debug/` and `examples/plugins/crawler-feeder/` its `plugins/debug/` and
  `plugins/crawler-feeder/`. Nothing about them changed but the place - they build against the published
  `org.frontcache:frontcache-plugin-api` and `-testkit`, as they always did, and a plugin copied from the old
  directory keeps building.

## Upgrading

- **A server-mode node behind a proxy with `front-cache.client-ip.trusted-proxies` empty: set it BEFORE you upgrade.**
  Until now such a node saw each client by its leftmost `X-Forwarded-For`, by accident, and its per-IP rules looked
  as if they worked. From this release it sees what the documentation always said it would: the socket peer, i.e. the
  proxy - so every visitor is one client, and a rule like `ip-flood | rate:200/10s` refuses **the whole site** within
  seconds (the log reads `ip-flood#127.0.0.1`). The node `WARN`s about a rate rule with no trusted proxies at startup.
  The usual value behind a local nginx is `127.0.0.1/32,::1/128`.
- **Then check it**, from outside, with a header of your own: a request carrying `X-Forwarded-For: 203.0.113.1` must
  show **your** address, not `203.0.113.1`, wherever the node reports the resolved one - a `| trap` or `rate:` rule's
  log reason (`<rule>#<address>`), or a `client-ip:` rule naming your own address.
