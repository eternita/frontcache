# Frontcache 2.10.0 — release note

Docs index: [../doc-index.md](../doc-index.md) · All release notes: [README.md](README.md)

Everything that has landed since 2.9.0:

- **Every circuit card on the realtime monitor can show what the whole cluster is taking**, not just
  what that node is taking. Console-only, opt-in, one new config key. See
  [the cluster rate](#a-cluster-rate-on-the-realtime-monitor).
- **Fixed: "JVM CPU" read as `-` on every node running an embedded-runtime bundle.** A module was
  missing from the bundled Java runtime. **Deploy the 2.10.0 bundle to get the number** — see
  [JVM CPU](#fixed-jvm-cpu-was-blank-on-embedded-runtime-bundles).
- **The request log now names the `bots.conf` rule that decided each request's client type** — the
  `bingbot` behind a `bot`. One new column, beside the client type it explains, which **moves the
  user-agent column right by one**. See
  [the deciding rule](#the-request-log-names-the-rule-behind-the-client-type).
- **A node can warm its own cache from a URI list** — paced, pausable, resumable, and reporting what
  it stored — replacing the `warmer/warmer.sh` curl loop, with a console screen to run it from
  (**Cache → Cache Warmer**). See [the cache warmer](#a-cache-warmer-on-the-node).
- **Fixed: the console's cache screens would send the fleet's API key to any host a form named.**
  Cache View, Invalidation, Other, Replication and config editing now act only on an edge in the
  console's own edge list, as the realtime page and the Cache Warmer already did. See
  [the edge allowlist](#fixed-the-console-could-send-the-api-key-to-an-edge-it-does-not-have).

There is no cache flush, and nothing existing on the wire changed: the warmer adds management
actions, and a console of any supported version reads a node of this one as it did. The node-side
changes to watch are the request log's new column — nothing to configure, but **if something parses
those files by position, read that section** — and a new `Warm-Request` command key, which reads zero
unless a warm run is going. See [Upgrading](#upgrading).

## What to do

| If you… | Then… |
| --- | --- |
| run more than one edge in front of the same site | add `frontcache.console.clusters` to `frontcache-console.conf` — one line per group of interchangeable nodes |
| run one edge, or edges serving different sites | nothing. The realtime page renders as it did, minus the duplicate `Cluster:` line |
| upgrade the console but not the nodes, or the other way round | nothing. The total is computed in the browser from the frames a node of any version already sends |
| run nodes from a **per-platform bundle with an embedded runtime** (`frontcache-server-<version>-linux-aarch64.tar.gz` and friends) | deploy the 2.10.0 bundle to get "JVM CPU" back. Nothing else is affected |
| run nodes on your own JDK (the portable bundle, a container with a JDK, a war in your own container) | nothing. Those were never affected |
| parse `logs/frontcache-requests.log` positionally (ELK, a grok pattern, `awk`) | **add one column after the client type.** Everything up to and including the client type is where it was; the user-agent is now column 16 rather than 15 |
| parse `logs/frontcache-failed-requests.log` positionally | the same insert, in both of that file's line shapes — so the user-agent, the fallback reason and, on a guard line, the HTTP status all move right by one |
| read the client type with `awk '{print $14}'`, or anything anchored to the *left* of it | nothing. Columns 1–14 did not move |
| warm caches with `warmer/warmer.sh`, or a curl loop of your own | move to **Cache → Cache Warmer** on the console, or `action=warmer-start` — see [the cache warmer](#a-cache-warmer-on-the-node). The script still ships, and still works exactly as badly as it did |
| run a console with no `user`/`password` | the Cache Warmer screen shows lists and progress but offers nothing that starts a run or writes a list. `cache-warmer = false` in `frontcache-console.conf` does the same on an authenticated console |
| alert on, or sum, every `command` series in Prometheus, or watch the realtime page's card count | expect one more command, `Warm-Request`. It is zero except while a warm run is going, and it is what keeps warm traffic out of `Input-Request` |
| tuned `resilience.command.Input-Request.*` | nothing. `Warm-Request` inherits it, per property, down to the pre-2.9.0 `Input-Requests` spelling |
| run a node with no `front-cache.api-key` | the warmer's reads work; starting a run or writing a list is refused. The same rule as `set-config` |
| drive the console's Cache View / Invalidation / Other / Replication / config-save forms from a script, naming an edge that is **not** in the console's edge list | add that edge to `urls` in `frontcache-console.conf` (or on the Edges page) first. The page now shows "Unknown edge … not one of this console's edges" and nothing is sent |

## A cluster rate on the realtime monitor

Every card on the realtime page carried two lines:

```
Host:    21.7/s
Cluster: 21.7/s
```

The same number twice — because it came from one node's frame, and a node reports itself as one host.
For the deployment that shape of panel was built for,

```
load balancer ──► fc-us ─┐
              ──► fc-eu ─┼──► filter node ──► app
              ──► fc-ap ─┘
```

the figure an operator actually wants — how much traffic the *site* is taking — was on the screen
three times and summed nowhere. It was arrived at with a calculator.

**Group the nodes and every card shows the group's total.** In `frontcache-console.conf`:

```hocon
frontcache {
    console {
        urls = ["https://fc-us.example.com:443", "https://fc-eu.example.com:443",
                "https://fc-ap.example.com:443", "http://filter.example.com:8082"]

        clusters {
            "Edge layer" = ["https://fc-us.example.com:443",
                            "https://fc-eu.example.com:443",
                            "https://fc-ap.example.com:443"]
        }
    }
}
```

Each member's panel then reads:

```
fc-us.example.com in cluster “Edge layer”, 3 nodes

   Input-Request        Cache-Hit            Cache-Miss
   Host:    17.5/s      Host:    55.9/s      Host:    12.7/s
   Cluster: 37.2/s      Cluster: 115.4/s     Cluster: 23.8/s
```

**The `Cluster:` line is the one that was already there — what changed is that its number is now
real.** It is every member of the group added up, rather than this node's own figure printed twice,
and it reads the same on all three panels at any instant: the members publish on their own clocks,
but a frame from any of them refreshes the line on all of them. Hover it for how many members are
currently counted and which they are.

### What it does not change

- **The page keeps its shape.** One panel per edge, in the console's edge order. A cluster adds one
  line per card and a few words to the panel's heading; there is no extra panel.
- **Everything else on a card is still that node's.** The counters, the error percentage, the latency
  table and the sparkline are one node's numbers, because the panel is one node's. A request rate is
  the one figure that adds up exactly across nodes; latency percentiles, in particular, cannot be
  combined correctly without the histogram buckets — `front-cache.metrics.export` (Prometheus / OTLP)
  is where that lives.
- **No new load on the fleet, and no new connection.** The page already held an open stream per edge;
  the total is computed from the frames it is already receiving.
- **Nothing on a node.** No change to the dashboard stream's JSON, its field names or
  `/hystrix.stream`. The console reads a mixed fleet exactly as before — including nodes that still
  emit the pre-2.9.0 command key names, which are folded onto the keys that replaced them, so a
  half-upgraded cluster gives one `Input-Request` total and not two half-fleet ones.
- **A single-node panel now shows one rate line, not two.** The `Cluster:` line appears only where
  there is a cluster to add up. On an unclustered edge the second line only ever said "this is one
  node".

### Configuring it

- **Group only interchangeable peers.** In the topology above the filter node is *not* in the cluster:
  its traffic *is* the other three's, so including it would count every request twice.
- **Members are matched by URL**, with or without the trailing slash, and an edge may be in at most
  one cluster.
- **A mistake here is a startup warning, not a startup failure** — the console is a monitoring tool
  and an upgrade must not take it offline. A member that is not in `urls` is warned about and ignored;
  a URL claimed by two clusters keeps the first; a cluster the edge list leaves with one member shows
  no cluster line, since it would repeat the `Host:` line above it.
- **A member that goes silent stops counting within five seconds**, so the figure falls when a region
  drops out rather than freezing on that region's last frame. That member's own panel says
  `retrying …`, which is the explanation.

## Fixed: "JVM CPU" was blank on embedded-runtime bundles

The console's **Edges status** column showed `JVM CPU —` for every node running a per-platform
bundle, while heap, uptime, cache sizes and everything else on the same panel were correct. On a node
running on a JDK of your own the number was there. It was not the hardware, the architecture or the
node's config: the embedded runtime in those bundles was **linked without the `jdk.management`
module**.

`getProcessCpuLoad()` lives on `com.sun.management.OperatingSystemMXBean`, which is in
`jdk.management` — *not* in `java.management`, which the bundles did include. So heap and uptime, read
from `java.management` beans, worked; the CPU reading did not. What made it invisible is the shape of
the failure: the `instanceof` test guarding that bean does not evaluate to false when the module is
absent, it raises `NoClassDefFoundError`, and `FcNodeStats` catches exactly that and reports
"untracked" as designed. A correct answer to a question the runtime could not answer.

The same module backs Micrometer's `ProcessorMetrics`, so `frontcache_process_cpu_usage` was empty in
the Prometheus export on those nodes too.

**Three things changed:**

1. `jdk.management` is in the bundles' module set. Deploy the 2.10.0 bundle; there is no config
   change and nothing else about the node is different.
2. **A node now says so once, at `WARN`, on the first reading** — naming the missing module and the
   build that sets the list. Silence is why this shipped: one dash in one column of one screen is not
   loud enough to investigate.
3. **Two guards, because this is the second module the set has lost this way** (`java.net.http` was
   the first, and cost the console's whole realtime page for a release):
   the bundle build now asks jdeps what Frontcache's own jars need and refuses to build a runtime
   that does not cover it, and the release smoke test asks a booted server bundle for
   `get-node-stats` and fails if the CPU figure never becomes a real number.

**Only the embedded-runtime bundles were affected.** The portable bundles, the Docker images and a
war in your own container all run on a full JDK, where the module has always been present.

## Fixed: the console could send the API key to an edge it does not have

Every call the console makes to a node carries `Authorization: Bearer <api-key>`. The Cache View,
Cache Invalidation, Cache Other (dump keys, purge, backup) and Cache Replication screens, and a
single-edge Save on a Configs tab, took the edge URL from the submitted form and built a client from
it as given — so a crafted POST from an authenticated session could make the console hand the key to
any host it named. The realtime relay and the Cache Warmer screen already refused that; the rest now
share their rule: **an edge must be in the console's
current edge list** — trailing slash or not, and including edges added at runtime on the Edges page —
and the client is built from the configured spelling, not the caller's. An unknown edge is refused
before any connection is opened, and the page says so instead of reporting a purge that never
started. Replication also refuses the same edge spelled two ways as source and target.

Nothing changes for anyone using the screens as rendered: their drop-downs only ever offered
configured edges.

## The request log names the rule behind the client type

Every request-log line already carried the client type the node decided on — `bot` or `guest`. It
did not say *why*, so a line reading `bot` for a visitor, or `guest` for a crawler that is hammering
the origin, sent you to `conf/bots.conf` to work out by hand which of forty lines could have
matched. The line now names the one that did:

```
… front-cache-us-1 bot "bingbot" "Mozilla/5.0 (compatible; bingbot/2.0; +http://www.bing.com/bingbot.htm)"
```

Read as three columns: the client type, the rule that decided it, and the evidence. The value is

- a rule name from `conf/bots.conf`, or a **bare keyword line**, which is its own rule name
  (`bingbot`, `Yahoo! Slurp`);
- the built-in `no-user-agent` or `default` — `default` meaning no rule in the file claimed the
  request, which is the normal answer for a visitor;
- `propagated` — an include whose client type was adopted from a trusted peer (`front-cache.client-ip.trusted-proxies`),
  so *this* node ran no rule at all; the page's node logged the rule that did decide;
- `-` — no classification was recorded, which does not happen for a served request.

**Only the deciding rule is named.** A `dry-run` rule that matched and stepped aside is not in the
line — it stays at `DEBUG`, as before. That is the same rule the console's **Visitor Types** screen
counts in its Hits column, which makes the two cross-checkable from opposite ends:

```bash
grep -oE ' (bot|guest) "[^"]*"' logs/frontcache-requests.log | sort | uniq -c | sort -rn
```

(Matched rather than cut by field number, because a rule name may contain a space — which is why the
column is written quoted at all: `Yahoo! Slurp` is a keyword line in the shipped `bots.conf`.)

Three places have the answer: `logs/frontcache-requests.log`,
`logs/frontcache-failed-requests.log` — where a guard rule firing on `client-type:bot` now says which
bots.conf line put the request in that bucket — and the `x-frontcache-trace-request.*` response
headers under `front-cache.log-to-headers=true`, which is the only one of the three that answers
"why was I served the bot TTL?" without shell access to the node.

### What moved, and what did not

- **The user-agent column moved right by one**, in both log files and in all three of their line
  shapes — with it, the fallback reason and a guard line's HTTP status. 2.7.0 pinned this layout
  indefinitely and every column ever added to it has gone on the end, so this is a deliberate
  exception, made once: `bot "bingbot"` is a single fact, and a consumer that has to skip a user-agent to pair
  the two will eventually pair them wrong. The next column will go on the end.
- **Columns 1–14 are untouched**, so anything reading from the left — including `$14` for the client
  type — keeps working. It is a grok pattern that names every field, or one anchored on the end of
  the line, that needs the edit.
- **No new configuration**, and nothing to turn on. The rule name was already computed on every
  request; it was simply not written down.
- **No node, cache or wire change.** The client type itself, its vocabulary and every TTL decision
  are untouched.

## A cache warmer on the node

A node could always **write** a URL list — `dump-keys` saves every cached key to
`warmer/keys_<timestamp>.txt` — and nothing on the node could read one back. What there was for
that is `warmer/warmer.sh`, a `curl` loop with no pacing and no results, that sends every request to
the public hostname (so out through the CDN and back in at whichever node it picks) and gets its
client type from a `Googlebot` User-Agent your `bots.conf` may no longer believe.

**The node now runs the list itself**, and the console's new **Cache → Cache Warmer** screen is where
to run it from: every edge's state on one strip, its lists (edit a small one in place; preview, search,
download or upload a large one — up to 64 MB, streamed straight through to the node; copy one to every
edge; dump the cache's own keys into one), a **Check** that shows the keys the first entries will be
stored under before anything is sent, **Start**, live progress with a delay and concurrency you can
change mid-run, Pause / Resume / Stop, the failures as they happen, and **Resume from line N** after a
stop or a restart. The page holds no state of its own — close it mid-run and the run carries on.

Each entry is sent to the node's **own front door**
(`http://127.0.0.1:<port>`), so it takes exactly the path a visitor's request takes — same cache key,
same TTL, same includes, filter mode included — and the warmer has no cache logic of its own to drift
from the real one. Lists are the `*.txt` files in `FRONTCACHE_HOME/warmer/`; the format is one path or
URL per line, and `warmer/README.txt` has it.

```bash
# the same from a script: put a list on the node (the list is the request body, not a form field)
curl -H "Authorization: Bearer $KEY" --data-binary @top-pages.txt -H 'Content-Type: text/plain' \
  "http://127.0.0.1:9080/frontcache-io?action=put-warmer-list&name=top-pages.txt"

# check it first: the keys entries will be stored under, invalid lines, duplicates, an ETA
curl -H "Authorization: Bearer $KEY" \
  "http://127.0.0.1:9080/frontcache-io?action=warmer-preflight&list=top-pages.txt&keyBase=http://www.example.com"

# run it, 200 ms between calls, one at a time
curl -H "Authorization: Bearer $KEY" -d action=warmer-start -d list=top-pages.txt \
  -d keyBase=http://www.example.com -d delayMs=200 -d concurrency=1 http://127.0.0.1:9080/frontcache-io

curl -H "Authorization: Bearer $KEY" "http://127.0.0.1:9080/frontcache-io?action=warmer-status"
```

**The key base is the one thing to get right.** Only the path and query of an entry are used; the
`scheme://host[:port]` every entry is stored under is the run's `keyBase` (default
`front-cache.warmer.key-base`, else `<scheme>://<front-cache.default-domain>`, the scheme being the
one the console reached the node with). It must be what visitors' requests arrive with — behind a
TLS-terminating nginx that is `https://` on the bundled Jetty, which honours `X-Forwarded-Proto`, and
`http://` on a container that does not. Get it wrong and the run completes, reports every entry
stored, and visitors miss on all of them, so the preflight prints the keys the first entries will get
and warns when none of the keys already in the cache share that base.

Warm requests go to `http://127.0.0.1:<the port the management request arrived on>` unless
`front-cache.warmer.loopback-url` says otherwise — plain HTTP even for an `https` key base, whose
scheme is sent as `X-Forwarded-Proto`. The node reports the key it built for every warm request, and
**a run stops on the first entry keyed outside its key base** — which is what a container that ignores
`X-Forwarded-Proto` produces — naming both keys, rather than storing a list's worth of entries under a
scheme no visitor's request carries.

What a run does:

- **`fill`** (default) skips entries already cached and unexpired — re-running a half-finished list is
  cheap. **`refresh`** re-renders every page, and the old copy stays served until the new one lands.
  Includes are always filled, never refreshed: a shared header would otherwise render once per page.
  A refresh renews the node it runs on: if that node's origin is another Frontcache, the answer comes
  from *its* cache, so refresh a chain inner node first.
- **The delay reaches the origin**, not just the front door: a warm request resolves a soft-expired
  entry and an `async` include on its own thread, where a visitor's would hand them to the
  background. `delayMs` and `concurrency` can be changed mid-run with `warmer-update`, and a new
  delay applies to sleeps already in progress.
- **It backs off by itself.** Workers wait while the origin's (`Cache-Miss`) breaker is open, without
  counting the wait, and the run pauses itself after 20 consecutive failures
  (`front-cache.warmer.auto-pause-after-failures`) — twenty 404s in a row usually mean the list or the
  key base is wrong.
- **It is the operator's run, not the visitor's.** The client type is a run parameter (`bot` by
  default, sent with a `Frontcache-WarmerBot` User-Agent), not what `bots.conf` makes of `127.0.0.1`,
  and guard rules are skipped — both only for a request carrying a 256-bit token that exists nowhere
  but in the node's memory, from a loopback peer. The token is dropped before anything is sent to the
  origin.
- **It leaves results.** `warmer-status` reports counters (`stored` / `fresh` / `not cacheable` /
  `failed` / `invalid`), rate, ETA and the last 50 failures; failed and not-cacheable entries are
  written to `warmer/<list>.failed-<timestamp>.txt`, which is itself a list; a stopped run leaves a
  checkpoint in `warmer/.state/run.json` that `resumeFromLine` picks up — refused if the list has
  changed since, and never automatic.

Its own requests run under a new command key, **`Warm-Request`**, so a warm run does not read as a
traffic spike on `Input-Request` or take its bulkhead permits. It inherits `Input-Request`'s settings
when `resilience.properties` says nothing about it. Its origin calls go through `Cache-Miss` and the
`OriginPool` like any other — one origin, one breaker, one pool — which is why
`front-cache.warmer.max-concurrency` defaults to 4. With metrics export on there are two new series,
`frontcache_warmer_entries_total{result}` and `frontcache_warmer_running`.

**One run per node, and starting one needs a configured `front-cache.api-key`** — a 50,000-entry run is
50,000 origin renders ordered by one request. `front-cache.warmer.enabled=false` turns it all off
except status and lists; `front-cache.warmer.list-write=false` makes the lists read-only for a fleet
that deploys `warmer/` from git. The keys, with their defaults, are in the shipped
`frontcache.properties`.

**Mixed versions.** The console reports a node that predates the warmer as *"predates the cache
warmer"* on its edge strip rather than as a run that started, and an older console simply has no such
screen. The screen's controls need a console login, like the Configs editor: without `user`/`password`
— or with `cache-warmer = false` in `frontcache-console.conf` — it is read-only.

**Not in this release:** importing a list from the origin's sitemap.

## Upgrading

**Nothing is required.** A console upgraded to 2.10.0 with an unchanged `frontcache-console.conf`
behaves as 2.9.0 did, minus the duplicate `Cluster:` line on every card.

The one thing to check before a node upgrade is a log pipeline that reads either log file by
position: a column is inserted after the client type, so the user-agent and everything after it move
right by one — see [the deciding rule](#the-request-log-names-the-rule-behind-the-client-type).
Columns 1–14 are unchanged, so a pipeline that stops at the client type needs no edit.

Optional, and only if you run several edges in front of one site:

1. Add `frontcache.console.clusters` to `frontcache-console.conf`, as above, and restart the console.
   Watch the startup log: each member is logged, and anything the file gets wrong is a `WARN` naming
   the URL.

No cache flush, no node restart, no config change on any node.

If you warm caches with `warmer/warmer.sh`, nothing breaks — the script is unchanged — but the node
can now do it properly; see [the cache warmer](#a-cache-warmer-on-the-node). The one decision to make
before the first run is the **key base**: set `front-cache.warmer.key-base` (or
`front-cache.default-domain`) to what visitors' requests arrive with, and read the preflight's sample
keys before starting.

Separately, if your nodes run a **per-platform bundle with an embedded runtime** and you want
"JVM CPU" back on the console:

1. deploy the 2.10.0 per-platform bundle;
2. restart the node.

An older bundle keeps reporting the CPU field as untracked. Nothing else about it is affected.

**Verified:** `frontcache-core` 775 unit tests, `frontcache-console` 144 plus 31 JavaScript tests
(the cluster-rate arithmetic and the Cache Warmer screen), and the 213-test end-to-end suite, all
green. Every per-platform bundle was booted on its own embedded runtime, with no JDK on the host,
and the server bundles were checked to report a real JVM CPU figure.
