# Frontcache 2.8.0 — release note

Docs index: [../doc-index.md](../doc-index.md) · All release notes: [README.md](README.md)

**Three changes in this release.**

1. **Frontcache moved from Apache HttpClient 4.5.14 to 5.3.1.** Nothing about caching, includes,
   circuit-breaking, the management API, the dashboard stream or the metrics export behaves
   differently. No config migration, no wire format change.
2. **Guard rules can rate-limit per client IP** — one new predicate in `guard-rules.conf`. Nobody
   gets rate-limited until you write a rule, so this changes nothing on upgrade.
3. **`<fc:include>` fragments can be combined into one origin request** — one new attribute in your
   markup, and a handler you write at the origin. Nothing combines until you add both, so this too
   changes nothing on upgrade.

**If you deploy Frontcache and do not write Java against it, this upgrade is a drop-in.** Two
behaviour changes need no config edit and apply to every deployment — guard rejections are now sent
`Cache-Control: no-store`, and a filter-mode bypassed response no longer has its status overwritten
with 500 — and both are in [What to do](#what-to-do). Stop reading after that unless you want the
rate limiting or the include combining.

**If you implement one of the three extension points — `CacheProcessor`, `IncludeProcessor` or
`FallbackResolver` — you have a one-line source edit per method**, and the node refuses an
un-recompiled implementation at startup rather than failing later, mid-outage. That is the only
change here that can reach anyone's source. It is described in
[If you extend Frontcache in Java](#if-you-extend-frontcache-in-java).

Why the HttpClient move now: 4.5.14 is the **last** release of the 4.5 branch. It is
maintenance-only, and every future fix — security fixes included — lands on 5.x. Frontcache was going
to have to make this move; making it while nothing is forcing the schedule is the cheap version.

The two new features have a doc each, and those — not this note — are what to keep open while you
configure them: [guard-getting-started.md §5](../guard-getting-started.md) for rate limiting, and
[include-combining.md](../include-combining.md) for combining.

## What to do

| You have | Do this |
| --- | --- |
| A stock `frontcache-server` deployment | **Nothing.** Replace the artifact. |
| A stock `frontcache-console` deployment | **Nothing.** No console code changed. |
| `frontcache-agent` embedded in your app | **Nothing to your code.** The agent moved to 5.3.1 too, but its API is `String` in, `String` out — it never exposed an HTTP type. Your build picks up `httpclient5` instead of `httpclient` transitively. |
| `frontcache.properties`, `resilience.properties`, `fallbacks.conf`, `fc-logback.xml` | **Nothing.** Every key means exactly what it meant in 2.7, including `front-cache.http-client.socket-timeout` — see [Timeouts](#timeouts-mean-what-they-meant). The rate-limit keys are all new and all optional. |
| `guard-rules.conf` | **Nothing.** Every existing rule parses and behaves identically. A new `rate:` predicate is available if you want it — see [per-IP rate limiting](#new-per-ip-rate-limiting). |
| Pages with `<fc:include>` fragments | **Nothing.** Every include resolves exactly as it did. A new `combine` attribute is available if you want it, and it needs a matching handler at your origin — see [combining includes](#new-combining-includes-into-one-origin-call). |
| **Frontcache in webfilter mode**, serving anything that goes down the bypass path — a non-GET request, or a URL matched by `dynamic-urls.conf` | **Nothing to change, but a bug is fixed:** those responses were being sent with status **500** whenever the app wrote a small body through `getWriter()`, with the correct body attached. The app's own status is now preserved. If you have a monitor counting 5xx on POSTs, expect it to go quiet. |
| Any guard rule with a `reject:` action, **or the two built-in rules every node runs** (`uri-too-long` → 414, `bad-request` → 400) | **Nothing to change, but know this:** those responses now carry `Cache-Control: no-store, no-cache, max-age=0, must-revalidate`. 2.7 sent it on guard *redirects* only and left rejections bare. If a CDN in front of you was heuristically caching a 414, it will stop. |
| Your own `CacheProcessor`, `IncludeProcessor` or `FallbackResolver` | One type change per method signature, then recompile — see [below](#if-you-extend-frontcache-in-java). |
| Java code calling `FrontCacheEngine.getHttpClient()` or `RequestContext.getHttpClientResponse()` | Recompile; the returned types are now the 5.x ones. |
| An app that also depends on HttpClient 4.5 | **Nothing.** They coexist — different Maven coordinates *and* different root packages (`org.apache.http` vs `org.apache.hc`). |

## If you extend Frontcache in Java

The three reflection-loaded extension points used to take an Apache `HttpClient` in their
signatures. They now take `org.frontcache.core.FcHttpClient`, which is Frontcache's own type.

| Interface | 2.7 | 2.8.0 |
| --- | --- | --- |
| `CacheProcessor` | `processRequest(String, Map, HttpClient, RequestContext)` | `processRequest(String, Map, FcHttpClient, RequestContext)` |
| `CacheProcessor` | `doSoftInvalidation(String, String, Map, HttpClient, RequestContext)` | `doSoftInvalidation(String, String, Map, FcHttpClient, RequestContext)` |
| `IncludeProcessor` | `processIncludes(WebResponse, String, Map, HttpClient, RequestContext, int)` | `processIncludes(WebResponse, String, Map, FcHttpClient, RequestContext, int)` |
| `FallbackResolver` | `init(HttpClient)` | `init(FcHttpClient)` |

**This is deliberate, and it is the last time these break for this reason.** The Apache type was
never something an implementation needed — the parameter existed only to be passed along to a fetch.
Leaving it in place meant every future HTTP-library upgrade would break the same four signatures
again. `FcHttpClient` is three methods, all of them "fetch this URL, hand back a `WebResponse`":

```java
WebResponse fetch(String urlStr, Map<String,List<String>> headers, RequestContext ctx);   // origin, resilience-wrapped
WebResponse fetchOverHttp(String urlStr, Map<String,List<String>> headers, RequestContext ctx); // includes
WebResponse fetch(String urlStr);                                                          // one-shot, bootstrap
```

If your implementation only *passed the parameter through* — which is what the built-ins did — the
edit is the type name and nothing else. If it called `client.execute(...)` itself, replace that with
`client.fetch(...)`; you get a `WebResponse` carrying status, headers and body, instead of managing an
entity and closing a response. Frontcache's own `FileBasedFallbackResolver` got shorter making this
change, not longer.

**A stale implementation fails at load, not in production.** As with `FallbackResolver` in 2.7, the
factories refuse a class that does not implement the current signature at startup, so you find out
when you deploy rather than the first time a fallback is needed.

## Timeouts mean what they meant

Worth stating explicitly, because it is the one place this upgrade could have silently changed
behaviour and did not.

HttpClient 5 removed the socket timeout from `RequestConfig`. It offers `setResponseTimeout` in the
same place, which looks like a rename and is not: response timeout bounds the wait for the response
head, while socket timeout bounds inactivity on *each* read, including reads of the body. Frontcache
depends on the latter — `front-cache.http-client.socket-timeout` is documented as *"keep it BELOW the
command timeouts so a slow origin is ended by the HTTP client (which releases the connection) rather
than by the command timeout (which cannot interrupt a blocking socket read)"*, and that is a fix for a
real connection leak.

**The property was moved to where 5.x keeps socket timeouts (`SocketConfig` on the connection
manager), not remapped onto `setResponseTimeout`.** `front-cache.http-client.socket-timeout`,
`front-cache.http-client.connect-timeout` and
`front-cache.http-client.connection-request-timeout` all mean exactly what they meant in 2.7. Your
tuned values carry over.

The same applies to the stale-connection retry. 2.7 retried an idempotent origin call once, with no
delay, because a pooled keep-alive connection closed by the origin throws `NoHttpResponseException` on
reuse. 5.x's `DefaultHttpRequestRetryStrategy` covers that case — but its default constructor
**sleeps one second** before retrying. Frontcache configures it with a zero interval, preserving 2.7's
immediate retry; the alternative would have put a one-second stall on whichever requests happened to
draw a stale connection.

## What else changed inside

None of this is visible from outside the process. Listed so that a stack trace or a heap dump makes
sense.

- **Package.** `org.apache.http.*` → `org.apache.hc.core5.http.*` and `org.apache.hc.client5.http.*`.
- **`RequestContext`'s stashed origin response** is now `ClassicHttpResponse` rather than
  `CloseableHttpResponse`. Both are `Closeable`; the two-party release protocol that stops a
  timed-out bypass call leaking a pooled connection is unchanged.
- **Origin calls use `executeOpen(...)`**, 5.3's supported way to get a response whose lifetime the
  caller owns. Frontcache streams a bypassed body to the client from a different thread than the one
  that opened it, so a scoped response handler cannot express what it does. **No deprecated
  HttpClient API is left in the codebase.**
- **Redirect handling** is `disableRedirectHandling()` where 2.7 installed a no-op `RedirectStrategy`
  in three places. Same behaviour: Frontcache relays the origin's redirect to the client after
  rewriting `Location` itself, and never follows one on the origin's behalf.
- **The keep-alive strategy** — honour the origin's `Keep-Alive: timeout=N`, default 10s — was pasted
  into three classes and is now one helper (`FCUtils.keepAliveStrategy()`) plus the agent's own copy,
  which cannot share it because `frontcache-agent` must not depend on `frontcache-core`.
- **Forwarded POST/PUT/PATCH bodies** now carry an explicit `ContentType` on the entity, because
  5.x's `InputStreamEntity` requires one. It is taken from the client's own `Content-Type`, and the
  origin still sees exactly one such header.
- **Dependencies.** `httpcore` + `commons-logging` + `commons-codec` → `httpcore5` + `httpcore5-h2` +
  `slf4j-api`. Same count, and `commons-logging` is gone — one fewer logging bridge in a project that
  routes everything through logback.
- **`FC_BypassCache` now records the status the app set** on the filter-mode branch. It never did,
  so `RequestContext.getResponseStatusCode()` answered its `500` default and `addResponseHeaders`
  stamped that over the app's own. It stayed hidden because it only bites while the response is
  still uncommitted: an app writing through `getOutputStream()` with a `Content-Length` has already
  been flushed, and `setStatus` on a committed response is a no-op — but an app writing a small body
  through `getWriter()` had not, and got a 500 **with the correct body attached**, which no test
  asserting on content would catch. Found by the combined batch, which is the first thing to take
  that branch with a writer-written body.
- **`callInclude` is split** into `getIncludeFromCache` and `fetchIncludeFromOrigin`. The combine
  path has to know which members missed before it can decide what to batch; the split is what keeps
  one definition of "a cache hit" for both paths.
- **`IncludeSupport.out()` writes its attribute values through one helper** instead of three pasted
  copies — one of which tested and streamed `includeType` while writing the `client` attribute, so
  a `Reader`-valued `client="…"` emitted the call type. Reachable only through the `rtexprvalue`
  path with a `Reader`, which is why it survived.

## What this unlocks

Not in this release, but the reason the ordering matters: **HttpClient 5 decodes brotli natively**
(`BrotliInputStreamFactory`, activated by putting `org.brotli:dec` on the classpath). 2.7 could not —
its `ResponseContentEncoding` knew only `gzip`, `x-gzip` and `deflate` and threw on anything else,
which is why Frontcache pins `Accept-Encoding: gzip` on every origin call.

That constraint is now removable — a later release can take it up. Nothing about encoding behaviour
changed in 2.8.0: Frontcache still asks origins for gzip and still never emits brotli.

## New: per-IP rate limiting

Guard rules — the checks that run before cache and origin, configured in `conf/guard-rules.conf` —
could reject or redirect a request on **what it is**: its URI, host, method, cookies, headers. They
could not express **how often it arrives**, which is the shape of the abuse that was left: a scraper
walking the catalogue, a credential-stuffing loop on a login page, one client re-requesting an
uncacheable search URL until the origin thread pool fills.

2.8.0 adds one predicate:

```
rate:<limit>/<window> [bucket=<name>] [scope=<toplevel|all>]
```

It is true once **one client IP** has sent `<limit>` requests inside the current `<window>`, and for
every further request until the window rolls over. Both numbers live in the rule, so
`reload-guard-rules` changes them without a restart:

```
# 100 requests per 10-second slot, per IP - ship it dry-run and watch first
ip-flood     | rate:100/10s                   | reject:429 Too Many Requests | dry-run

# tighter, on the expensive uncacheable path only
search-flood | uri~^/search ; rate:20/10s      | reject:429 Too Many Requests

# credential stuffing: only POSTs to that one page feed the counter
login-flood  | uri~^/login\.htm$ ; method:POST ; rate:10/1m | reject:429 Slow down
```

Nothing else about guard rules changed. It is a predicate, so the rest of the pipeline applies
unaltered: `allow` rules above it are still how you exempt a path, `| dry-run` is still how you ship
one safely, the rejection still writes one line to `frontcache-failed-requests.log` with the rule
name as the reason, and the console's Guard Rules screen renders a rate rule and its hit count with
**no console rebuild** — the condition travels as a string, as it always has.

### The one thing you must configure

**`front-cache.client-ip.trusted-proxies`.** Read this before you enable a rule.

Frontcache never reads `X-Forwarded-For` — or any other forwarding header — from a peer you have not
declared trusted. It cannot: every one of those headers is client-supplied, so a client sending its
own `X-Forwarded-For` would mint itself a fresh counter on every request and defeat the limiter
completely, while passing any test that did not try it.

The consequence is that with this key **empty**, the limiter keys on the socket peer — and in the
documented deployment, where TLS is terminated upstream and traffic is proxied to `127.0.0.1:9080`,
that is `127.0.0.1` for every visitor on earth. Your whole site would count as one client. Frontcache
`WARN`s at startup and on every reload when a `rate:` rule is loaded and this key is empty; it does
not refuse to start, because a guard misconfiguration should degrade to "Frontcache as usual" rather
than to an outage.

```properties
# whatever actually terminates the client connection: the local nginx, your CDN's egress
# ranges, sibling Frontcache nodes
front-cache.client-ip.trusted-proxies=127.0.0.1/32,::1/128,10.0.0.0/8

# read only from a trusted peer, and walked RIGHT TO LEFT - the leftmost entry is whatever
# the client wrote, the rightmost non-trusted one is what the last proxy we trust observed
#front-cache.client-ip.header=X-Forwarded-For
```

`FCUtils.getClientIP()` — the thirteen-header scan behind the client-IP column of the request logs —
is **unchanged**, so your ELK pipeline and saved Kibana searches are untouched. The two resolutions
can legitimately disagree, which is why a rate-limit rejection logs its reason as
`<rule>#<address>`: "which address was actually counted?" is the first question anyone debugging a
429 asks.

### What the numbers mean

- **The window is a fixed slot, not a rolling period.** `100/10s` permits 100 requests in a slot and
  resets at the boundary — which also means up to 200 across one boundary, by construction. It still
  stops a client sending thousands per second, which is the job. If burst tolerance matters more than
  the average, shorten the window rather than lowering the limit: `20/2s` is the same sustained rate
  with a tenth of the burst.
- **The limit is per node, not per fleet.** Each node counts what it sees, in memory. Behind *N*
  edges, `100/10s` is a fleet limit of roughly `100 × N` for a client whose requests spread — so
  configure `limit ≈ fleet_target / N`, and re-check it when you resize the fleet. There is no shared
  counter, deliberately: a network hop on the request path of a component whose purpose is surviving
  the origin being down is a bad trade.
- **One address is one counter.** No prefix or subnet grouping, so a shared-NAT office or a CGNAT
  pool is never limited because of one user behind it. The cost is stated plainly: an IPv6 client
  holding a `/64` can rotate addresses and evade the limit entirely, and so can a rotating IPv4 pool.
- **Includes do not spend a visitor's budget.** A page stitched from twelve `<fc:include>` fragments
  costs its visitor one request, not thirteen — the default `scope=toplevel` counts client requests
  only.
- **Counts survive `reload-guard-rules`.** Editing an unrelated rule during an attack does not hand
  every attacker a fresh window. They reset on restart, and when a rule's limit or window changes.

**What it is not:** a WAF, bot management, or a defence against a distributed botnet. Under
`100/10s`, ten thousand hosts are still permitted a hundred thousand requests per ten seconds. It
stops one loud client, which is the traffic this exists for.

### The 429

Guard rejections now carry `Retry-After` when the matching rule can compute one — for a rate rule
that is the seconds until the client's window rolls over, which RFC 6585 expects on a 429 and which a
well-behaved crawler acts on. All guard rejections, rate-limited or not, now also carry
`Cache-Control: no-store` (see [What to do](#what-to-do)): a cached 429 would pin a client to a
rejection long after its window ended.

### New in the metrics export

Guard counts used to be reachable only through `get-guard-rules`, i.e. by the console and nothing
else — so "is this rule firing?" and "is my new dry-run rule about to refuse real visitors?" could not
be alerted on. With `front-cache.metrics.export` on, they are now series:

```
frontcache_guard_actions_total{name="ip-flood", result="rejected"}
frontcache_guard_actions_total{name="ip-flood", result="dry-run"}
frontcache_guard_ratelimit_takeovers_total{name="ip-flood"}
```

`result` uses the log's own vocabulary — `rejected` / `redirected` / `dry-run`, plus `allowed` for
exemption rules — so a Grafana panel and a Kibana panel name the same event with the same word. This
covers every guard rule, including the two built-ins, not only rate rules. Sizing a new limit before
it acts is then a query rather than a log grep:

```promql
sum(rate(frontcache_guard_actions_total{result="dry-run"}[5m])) by (name)
```

**No series is labelled by client address.** A per-IP label on a page cache is the same unbounded
cardinality mistake that URLs would be; the address goes in the log, where retention bounds it.
`frontcache_guard_ratelimit_takeovers_total` rising with traffic is the one sizing signal to watch —
it means `front-cache.guard-rules.rate-limit.slots` is too small for the address space being seen.

### New properties, all optional

| Key | Default | What it does |
| --- | --- | --- |
| `front-cache.client-ip.trusted-proxies` | *(empty)* | CIDRs whose forwarding headers are believed. **Required behind a proxy** — see above |
| `front-cache.client-ip.header` | `X-Forwarded-For` | which header, when the peer is trusted |
| `front-cache.guard-rules.rate-limit.slots` | `262144` | slots per bucket, 8 bytes each — 2 MB |
| `front-cache.guard-rules.rate-limit.max-total-slots` | `4194304` | ceiling across buckets; a rule that would exceed it is skipped with an error |
| `front-cache.guard-rules.rate-limit.enabled` | `true` | emergency off switch — every `rate:` predicate returns false, rules stay visible in the console |

Counters are a fixed array sized at startup, not a map keyed by client address: the key space is
attacker-chosen, so a map is a memory-exhaustion primitive. Undersizing costs accuracy, never a
wrongly refused visitor. Two smaller additions come with it: a `request-type:` predicate
(`toplevel` / `include` / `include-async`), and `FrontCacheEngine.existingInstance()` for Java
callers that want the engine only if one exists.

## New: combining includes into one origin call

A page split into `<fc:include>` fragments costs the origin one request per fragment whenever they
are not cached. For an origin whose data access is **batched at page level** — one `IN (…)` per
entity type, one search query for the whole grid — that multiplies backend work by the number of
fragments, because each fragment re-enters the same batch machinery with a set of size one.

The measured case that prompted this: a 15-cell search grid that costs **1 Solr + 5 SQL as one
page** would cost **15 Solr + 75 SQL as 15 cell fragments**, because the batch loader behind it
issues five queries whatever the size of its input set. Asking it for one id costs what asking it
for fifteen costs.

2.8.0 lets the edge aggregate the **cache-missing** includes of one page into a single origin
request, and lets the origin answer them together:

```html
<fc:include url="/fc/search-item.htm?id=1" combine="true" />
<fc:include url="/fc/search-item.htm?id=2" combine="true" />
<fc:include url="/fc/search-item.htm?id=3" combine="true" />
```

Empty cache: **one** origin request carrying all three. With `id=2` already cached: one request
carrying two. All three cached: none, exactly as before. Each fragment is still cached individually,
under the same key it would have had, with its own `maxage` and its own invalidation tags — so
nothing about invalidation, expiry or the cache's shape changes.

### This is opt-in twice, on purpose

It is **not** a transparent edge optimisation. It needs the attribute in your markup *and* a handler
at your origin that understands the request. An origin that has the attribute but not the handler
renders correctly — the edge detects it and falls back to individual fetches — and gains nothing.

### The contract

Full specification in [include-combining.md](../include-combining.md) §4 and §5; it is
short enough to summarise.

**Request.** One GET to the fragment's own path:

```
GET /fc/search-item.htm?fc-combine=1&fc-parts=2&fc-part-0=id%3D1%26lang%3Den&fc-part-1=id%3D3%26lang%3Den
```

`fc-combine` is the protocol version and its presence is what makes the request a combined one;
`fc-parts` is the member count; `fc-part-{i}` is member *i*'s complete original query string,
percent-encoded as a single value. Indexed rather than repeated so the origin never depends on its
container preserving parameter order, and carried as a *value* so no include URL can smuggle a
parameter into the combined request or into a sibling member. `fc-` is a reserved parameter prefix:
an include whose own query uses one is never combined.

**Response.** A JSON envelope, positional against `fc-part-{i}`:

```json
{"v":1,"parts":[
  {"q":"id=1","status":200,
   "headers":{"Content-Type":["text/html;charset=UTF-8"],
              "x-frontcache-component-maxage":["10d"],
              "x-frontcache-component-tags":["coin|coin-1"]},
   "body":"<div>…</div>"},
  {"q":"id=3", "…":"…"}]}
```

with `x-frontcache-combine: 1` on the response — **the only signal the edge has that the origin
understood the request**, so an origin hand-writing this JSON must not forget it. Each part's
`headers` are read exactly as a single include's response headers are: `x-frontcache-component-maxage`,
`-tags`, `-refresh` and `-cache-level` mean what they always meant, and no `maxage` still means not
cacheable. `status` defaults to 200 and a non-2xx part simply falls back. `q` is an optional echo of
the member's query, verified when present — it costs one field and catches the whole class of "the
handler returned its results in a different order", which otherwise renders a page where every cell
shows another cell's content and looks like nothing at all.

Unknown fields are ignored at both levels, so the edge and the origin can be upgraded in either
order.

### Writing the origin handler

For a JVM origin, `frontcache-core` ships both halves of the contract so the two ends cannot drift —
`org.frontcache.include.combine.CombineRequest` and `CombineResponse`:

```java
List<Map<String, String[]>> parts = CombineRequest.parseParameters(request);
if (null == parts)
    return renderSingle(request);              // an ordinary single-fragment request

Map<Long, Coin> coins = dao.getByIds(idsOf(parts));   // ONE batched query - the entire point

CombineResponse out = new CombineResponse();
for (Map<String, String[]> part : parts)
    out.addComponent(CombineRequest.queryOf(part), render(coins, part), "10d", "coin-" + idOf(part));
out.writeTo(response);                          // sets the content type, the header and the body
```

A non-JVM origin implements roughly thirty lines: decode *n* values, batch, emit JSON.
[include-combining.md §6.2](../include-combining.md) has a **complete PHP endpoint** — one file
serving both the single-fragment and the combined shape — along with the three PHP-specific traps,
the first of which is that `$_GET['fc-part-0']` works precisely because the contract's parameter
names are hyphenated and not dotted. That example was run, and its envelope is a fixture in the
parser's own test suite, so it is pinned against the parser rather than merely written down.

**If your handler answers a batch with a loop over your single-item code path, this feature buys you
nothing** beyond the saved round trips. The saving is the batched query, and only your origin can
make it.

### What happens when something goes wrong

| | |
| --- | --- |
| Origin has no combine handler | Detected by the missing response header. Members are re-fetched individually and the page renders. The group is then remembered as unsupported for a minute, so an origin that never gains a handler costs one probe per group per minute rather than one per page view — and a rolling deploy converges within that minute. |
| Envelope malformed, part count wrong, or a `q` echo out of order | Rejected whole. Every member of that batch falls back through `fallbacks.conf`, keyed on **its own** URL, so fallback entries written for single includes keep working. Logged at ERROR and counted. |
| Batch times out, circuit opens, origin 5xx | One `Cache-Origin-http` command failed, so members fall back individually — the same path a timed-out single include takes today. |
| One part carries a non-2xx status | That member falls back. Its siblings render normally and are cached normally. |

The batch is sent with `x-frontcache-dynamic-request: true`, which is the existing signal that makes
**every** Frontcache node on the path bypass its cache and forward. That matters in the usual
`edge → webfilter → app` topology: the combined URL carries whichever members happened to miss, so
caching the envelope would mean one useless entry per subset, at two nodes.

### Metrics

Three counter families, exported with `front-cache.metrics.export` on
([console-dashboards.md](../console-dashboards.md)):

```
frontcache_include_combine_batches_total{result="ok|unsupported|error|failed"}
frontcache_include_combine_members_total{result="cached|combined|individual|fallback"}
frontcache_include_combine_errors_total{kind="parse|count|echo"}
```

The first two give the number the feature exists to raise — average fragments served per origin
request, which nothing else in the process can produce. The command metrics count origin calls but
not how many fragments each carried, and the cache metrics count hits while a batch *is* the miss
path:

```promql
rate(frontcache_include_combine_members_total{result="combined"}[5m])
  / rate(frontcache_include_combine_batches_total{result="ok"}[5m])
```

**`frontcache_include_combine_errors_total` is the one to alert on.** Every value of its `kind` is
an origin that says it implements the contract and does not, and there is no other signal for it:
the page still renders, out of fallbacks, and every other meter reads healthy.
`batches_total{result="unsupported"}` is the softer version — markup switched over, handler not
deployed.

The four member buckets are exhaustive — every combine candidate lands in exactly one — so
`cached + combined + individual + fallback` is the number of combinable includes the node has seen.
Both label keys were already in the cardinality allowlist, so this adds no new label vocabulary and
no series is labelled by URL.

### Configuration, all optional

| Key | Default | What it does |
| --- | --- | --- |
| `front-cache.include-processor.impl.concurrent.combine` | `true` | kill switch. Combining only acts on includes that ask for it, so `true` changes nothing for markup that does not |
| `…combine.max-batch-size` | `30` | members per origin request; a longer group splits into several, issued concurrently |
| `…combine.max-url-length` | `2000` | second cap, on the encoded query — a batch past a proxy's request-line limit comes back as a 414 that looks like nothing else |
| `…combine.unsupported-ttl` | `60000` | how long "this origin has no combine handler" is remembered, per endpoint, in ms |

### Also worth knowing

- **A group down to one missing member is not batched.** The origin does the same work either way,
  and the ordinary include path reaches it in one hop instead of two. This is the steady state for a
  page whose fragments are nearly all cached.
- **Async includes are never combined.** Nothing waits for one and its content never reaches the
  client, so batching buys nothing and would give it a shared deadline it does not have.
- **Duplicate URLs on one page are de-duplicated** within a batch: one part, both placeholders.
- **One batch takes one thread-pool slot, one circuit-breaker sample and one time-limiter budget**
  where fifteen includes took fifteen of each. The flip side is stated plainly: one slow batch loses
  all of its members at once.
- **In the trace headers** (`front-cache.log-to-headers=true`) a combined member's line reads
  `include-combined` and carries the *batch's* elapsed time — so N members report N identical
  durations that do not sum to the page time, which is what the marker is there to explain.

### What it does not do

It does not reduce edge work — still N placeholders, N cache lookups, N log lines. It does not
change cache size or cache keys. And it cannot give a fragment access to something only the parent
request had: a cell that renders a value taken from the parent page's own query result still cannot
see it, batched or not.

## Upgrading

Replace the artifact. There is no config migration, no cache format change and no wire format change,
so **a 2.8.0 node and a 2.7.x node can serve the same site at the same time**, a 2.7 console can
manage a 2.8 fleet and vice versa, and rolling back is replacing the artifact again.

The one thing to redeploy together is anything you compiled against `frontcache-core`: an extension
point implementation must be recompiled for the version of the node it runs in, since the signatures
differ (above). That is a same-artifact concern, not a fleet-wide one.

If you add a `rate:` rule and then roll a node back to 2.7, that node logs an ERROR for the line it
does not understand and loads the rest of the file — one unknown predicate has never cost the whole
`guard-rules.conf`. So the config is safe to deploy fleet-wide ahead of the artifact; the nodes that
do not have it yet simply do not rate-limit.
