# Frontcache 2.12.0-RC — release note

Docs index: [../doc-index.md](../doc-index.md) · All release notes: [README.md](README.md)

Everything that has landed since 2.11.0:

- **The console can be served under a path of a larger site, and bound to one address.** Two new
  launcher settings: `FRONTCACHE_CONSOLE_CONTEXT_PATH` (e.g. `/ops/console`; default `/`) and
  `FRONTCACHE_CONSOLE_HOST` (e.g. `127.0.0.1`; default every interface) — the system properties
  `frontcache.jetty.context-path` and `frontcache.jetty.host` for anything that starts
  `ConsoleJettyServer` itself. The console's pages, scripts and redirects are context-relative, so a
  reverse proxy forwards the path unchanged. Nothing changes for a console started as before.
- **The console's edge list can be made read-only.** `edge-editing = false` in
  `frontcache-console.conf` removes the Edges screen's add / remove buttons and refuses
  `POST /add-edge` and `/remove-edge` with a `403`; `/` then also stops adding a local edge by
  itself on a console with none. For a console whose `urls` your own tooling writes: an edge added
  by hand was monitored and sent the api-key until the next restart silently dropped it. Default
  true — an existing config behaves as before.
- **Fixed: the console dropped an edge that shared a host name with another.** The Edges status
  numbers, the Visitor Types screen and the Guard screen listed one of two edges on the same host
  (`http://localhost:8080/` and `http://localhost:9080/`, say) and left the other out without a word -
  its status read as unknown, its tab was missing. They now tell edges apart by URL, as the Configs
  screens already did; a tab still shows the host name, with the edge's URL as its tooltip.
- **Fixed: a console session survived only as a name.** A signed-in session now carries the identity it
  signed in as, checked on every request, rather than a user name alone; one created by an older build
  is not one, and signs in again. Nothing to do.
- **The console's sign-in, permissions and edge access are a documented extension point** (for console
  plugins). Who may sign in, what each user may do and which edges each user reaches - with which
  API key - are now asked of four interfaces in `org.frontcache.console.auth`, whose defaults are the
  console as it was: one `user` / `password`, permitted everything, every configured edge with the one
  `apiKey`. Every state-changing screen action names the permission it needs, and one that names none
  is refused (`403`), so an action added later cannot be open by omission. Two sign-in paths are
  reserved, `/login/sso` and `/login/sso/callback`; without a plugin they answer `404`.
  **A console config with a `users`, `sso`, `tenants` or `tenants-file` block and no plugin to read it
  now refuses to start** - it used to be ignored, which would have run such a console with less
  protection than its file asks for. Remove the block, or install the plugin it was written for.
  For plugin authors, as the extension point grew: a sign-in check is told whether the password came
  through the login form or an `Authorization: Basic` header, and may refuse a sign-in as throttled,
  which the console answers `429` (with `Retry-After`) rather than as a wrong password; screens hide
  the buttons a signed-in user may not use (the actions refuse them either way), the navbar shows the
  user's role when there is one, and a plugin's menu entry may be shown only to users holding a
  permission. With no plugin, nothing changes on screen.
