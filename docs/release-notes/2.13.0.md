# Frontcache 2.13.0 — release note

Docs index: [../doc-index.md](../doc-index.md) · All release notes: [README.md](README.md)

2.13.0 gives a node **plugins** (a plugin API, events after the fact, a path of their own under `/fc-x/`, plugins
dropped into a directory, plugin conditions in guard rules), **declared visitor types** in `bots.conf`, a
**`challenge`** guard action, a **`cookie-hmac:`** predicate and **honeypot rules** (`| trap`). No cache flush and no
config change is needed for a node that uses none of them, but read [Upgrading](#upgrading) first: **`/fc-x/` is now
the node's own**, a `client-type:` name the node does not know is **refused at load**, the request logs gain a
**last column**, and the console's realtime page reads **`/fc-dashboard.stream`**.

Everything that has landed since 2.12.0:

- **The console can call some edges with a key of their own.** A new optional `edges` list in
  `frontcache-console.conf`, beside `urls`:

  ```hocon
  frontcache.console {
    urls   = ["https://fc1.example.com/", "https://fc2.example.com/"]
    apiKey = "<the edges' key>"
    edges  = [ { url = "https://origin.example.com/", apiKey = "<the origin's key>", label = origin } ]
  }
  ```

  Each `edges` entry is called with its own `apiKey`, never the console-wide one, and the console-wide
  key is never sent to it - for a console that watches nodes of two key domains, an edge tier and the
  filter inside an origin application, say. Entries come after `urls` on every screen; the Edges screen
  shows them (with their `label`) and does not remove them, and never adds one of their URLs to `urls`.
  The list is read whole or refused whole: an entry without `url` or `apiKey`, an unknown key, or a URL
  that is in `urls` too or twice in `edges` stops the console at startup, with a message that never
  quotes a key. Nothing changes for a config without `edges`.

- **The console's realtime page reads `/fc-dashboard.stream`, no longer `/hystrix.stream`.** Every node since
  2.7 serves the stream at both paths, and still does - `/hystrix.stream` stays on the node for external
  Hystrix Dashboard / Turbine readers. What to check before upgrading the console:
  - a reverse proxy, firewall or `guard-rules.conf` in front of a node must admit the console to
    `/fc-dashboard.stream` and must not buffer it (the [front-door example](../../examples/front-door/README.md)
    and the install guide's nginx recipe already cover both paths). A rule naming only `/hystrix.stream` leaves
    that node's card empty, with no error on the page - the console logs the relay's failure.
  - a 2.6 node (or older) serves only `/hystrix.stream`, so its realtime card is empty on this console;
    its other screens are unchanged.

  A proxy URL that names the edge with either path (`/fc-dashboard-proxy.stream?origin=<edge>/hystrix.stream`)
  still resolves to that edge.

- **Plugins: a plugin API, a manifest, and events after the fact.** A node's extension point, the module SPI of
  2.11.0, is now a plugin SPI with its own small artifact, `org.frontcache:frontcache-plugin-api` (interfaces and
  value types only, compiled against `compileOnly`; every node carries it through `frontcache-core`). Nothing
  changes for a node without plugins - it serves, logs and exports exactly what it did, and `get-node-stats`
  reports an empty `plugins` list. For whoever writes or installs one:
  - **A plugin is found by its manifest**, `META-INF/frontcache-plugin.properties` in its jar (`id`, `class`,
    `version`, `plugin-api = 1`, `kinds`, optional `name` / `vendor` / `license` / `config`), and its jar sits
    where `frontcache-core` does: the server war's `WEB-INF/lib`, or a filter-mode application's class path. A
    `.properties` file has no trailing comments - everything after `=` is the value.
  - **The kinds are declared, then checked.** This release offers `observe` (events), `serve` (a path of its
    own, below) and `manage` (lifecycle, management actions, meters). A manifest that declares another kind, another `plugin-api` major or an id
    already taken, a class that cannot be loaded, a plugin that throws in `start`, and one that contributes
    something of a kind it did not declare are each logged and reported - and **the node starts without that
    plugin**.
  - **`observe` plugins receive events after the fact**, on a thread and a bounded queue of their own
    (`front-cache.plugins.<id>.queue`, default 10,000; a full queue drops and counts): `GuardMatched`
    (a rule rejected, redirected, or matched as a dry run), `RateLimitExceeded` (once per client and window, not
    once per refusal), `GuardSummary` (every 10 s: matches per rule, clients over the limit per bucket),
    `CircuitStateChanged`, `ConfigReloaded` (`guard-rules.conf`, `bots.conf`, `resilience.properties`, a
    plugin's config), `PluginStateChanged`, `OriginError` (an origin call failed, timed out, answered 5xx or was
    refused by its circuit), `FallbackServed` (a fallback answered instead of the origin), `CacheInvalidated`
    (`invalidate` / `purge`) and `RequestCompleted` - the request log's line for top-level requests, **sampled**:
    each plugin gets `front-cache.plugins.<id>.request-sample` of them (default `0.01`; `1.0` is every request,
    and the node WARNs at start that it is). A node nobody observes builds no event. Events never carry a cookie value,
    `Authorization`, the API key or a request body; the rate limiter's client address is carried, and
    `PluginContext.hashClientKey` is how a plugin sends it on without disclosing it.
  - **A plugin can have a config file**, `conf/<config>` as its manifest's `config` names it - a plain `.conf`
    name (HOCON), never one of the core's files or another plugin's. The node reads it before every start,
    resolves `${?ENV}` in it and hands it to the plugin, which accepts it whole or refuses it whole with every
    reason: a refused config is a plugin that does not start (the node starts, without it). To change one:
    - edit it on the node and call `reload-plugin-config?plugin=<id>` - a running plugin keeps the config it
      had when it refuses the new one; a plugin that failed on its config is started, no restart needed; and a
      plugin that accepts it is asked for its event listeners again, so a config can change what a plugin
      observes without a restart;
    - or write it with `set-config` and `file=plugin:<id>` - every `set-config` gate applies (an API key, and
      `front-cache.management.config-write`), and the plugin checks the content before anything is written;
    - or in the console: **Configs > Plugin Configs** lists the plugins with a config that the edges run, with
      the same editor and Save as the other Configs screens.

    `get-plugin-config?plugin=<id>` returns the file as it is. `get-node-stats` reports, per plugin, `config`,
    `configStatus` (`ok`, `absent`, `refused`), `configErrors` and when it was last accepted.
  - **Visible**: `get-node-stats` has `plugins` - each plugin's manifest facts, `state` (`started`, `failed`,
    `refused`, `stopped`) with the reason, and its delivered / dropped event and error counts - beside the
    older `modules` (the started ids). `/fc-metrics` exports `frontcache_plugin_state`,
    `frontcache_plugin_errors_total` and `frontcache_plugin_events_dropped_total` per plugin; a node without
    plugins exports none of them.
  - **For a 2.11 / 2.12 module**: `org.frontcache.module` is deprecated. A `FrontcacheModule` with only its
    `META-INF/services` file still runs, as a `manage` plugin, with a WARN at start - for one release. Move it
    to `org.frontcache.plugin.FrontcachePlugin` and give it a manifest. `ActionResponse` moved into
    `frontcache-plugin-api` with its package unchanged, so code using it compiles as before.
  - **`serve` plugins answer a path of their own, `/fc-x/<id>/`** - and no other. The node routes it after the
    guard rules (a `rate:` rule protects it like any other path) and before the cache: never cached, never sent
    to the origin, `Cache-Control: no-store` on every answer. A plugin sees a view of the request without
    `Authorization`, `Cookie` or any `x-frontcache-*` header, reads only the cookies its manifest names
    (`cookies = ...`), and answers through a narrow, buffered response - a header allowlist, a redirect held to
    the guard's own open-redirect rule, cookies its manifest names. A plugin that throws answers `503` for its own
    path, with nothing of what it wrote; more than `front-cache.plugins.<id>.max-concurrent` requests at once
    (default 32) answer `503` with `Retry-After`, and a body over `front-cache.plugins.<id>.max-body` (default
    64 KiB) `413`. The request log writes such a request with `plugin:<id>` in the is-cached column.
    `get-node-stats` reports, per serving plugin, `serves`, `cookies`, `challenges` and `served` /
    `serveRefused` / `serveFailed`; `/fc-metrics` exports `frontcache_plugin_serve_requests_total{outcome}`.
    Two more events: `ChallengeIssued` and `ChallengeResult` (below).

- **Plugins from a directory, plugin conditions in guard rules, and a kit for writing them.** Nothing changes for a
  node without them. For whoever installs or writes a plugin:
  - **Dropped-in plugins.** A plugin's jar (or jars) in `FRONTCACHE_HOME/plugins/<id>/`, enabled by name in
    `frontcache.properties` - `front-cache.plugins = <id>, ...` - and optionally pinned,
    `front-cache.plugins.<id>.sha256 = <the jar's SHA-256>` (comma-separated for several jars). A directory not listed
    is reported (`not-enabled`) and nothing of it is read; a jar that differs from its pin is refused. A plugin jar
    changes on restart. In **filter mode** a node reads a plugin directory only when `-Dfrontcache.plugins.dir` or
    `$FRONTCACHE_PLUGINS` names one. Each plugin gets a class loader of its own that shows it **only** the JDK, the
    plugin API, Typesafe Config, Jackson's annotations, slf4j and Micrometer - anything else it needs goes in its own
    jar (Jackson databind included), and two plugins may carry two versions of one library. `get-node-stats` reports
    each plugin's `source` (`bundled` / `dropped-in`), `directory`, `jars` and `pinned`.
  - **`ext:` - a plugin's condition in `guard-rules.conf` and `bots.conf`**, from a plugin of the new kind `decide`:
    `!ext:geo:country=DE,FR`. When the plugin has no answer (absent, refused the argument, threw, or switched off) the
    **rule does not match**, negated or not - so an `allow` rule naming one loads only with `| on-error=allow`, saying
    that the exemption then stops applying. Every call is timed: a plugin whose p99 over a minute is over
    `front-cache.plugins.<id>.decide-budget` (default `200us`) or that throws on more than 1 % of calls is switched off
    for five minutes. `get-node-stats` reports `predicates` and `decide*`; `/fc-metrics` exports
    `frontcache_plugin_decide_calls_total`, `_errors_total`, `_switched_off_total`, `frontcache_plugin_decide_p99_seconds`
    and `frontcache_plugin_decide_over_budget`. See [guard-getting-started.md](../guard-getting-started.md) §4.3.
  - **`client-ip:@lists/<file>` - lists that change while the node runs.** A `manage` plugin can replace
    `conf/lists/<name>.txt` (`PluginContext.writeList`: whole or refused whole, atomic, never a file without its own
    `# managed by plugin <id>` line) and every rule naming it sees the new list at once, with no reload. Under `lists/`
    only, a missing file is an empty list (a warning, not a skipped rule). Plugins also get a scheduler
    (`PluginContext.scheduler()`), whose tasks end when the plugin stops.
  - **A `client-ip:` list costs a request a few lookups, however long it is.** A `client-ip:` predicate used to
    compare the visitor's address with every entry of its list in turn, parsing the address again for each - harmless
    for the dozen blocks written by hand, not for a list a plugin keeps (a ban list of tens of thousands of addresses).
    The entries are now indexed by prefix length: one lookup per distinct prefix length in the list, the address parsed
    once. Every `client-ip:` rule benefits, `@file` lists and inline blocks alike; what matches is unchanged.
  - **The console's Plugins screen** (Community, `/plugins`, main menu): every plugin each edge reports - bundled or
    dropped in (directory, jar digests, pinned), kinds with a *request path* badge, state (`not-enabled` included),
    config and its last reload, counters, and a `decide` plugin's budget with an **over budget** badge. **Reload
    config** runs `reload-plugin-config` on one edge (`config.write`, off with `config-editing = false`, audited
    `plugin.config.reload`).
  - **For plugin authors**: a new test-scoped artifact, `org.frontcache:frontcache-plugin-testkit` - `PluginHarness`
    runs a plugin in-process with the node's kind checks, and a plugin's tests extend `PluginContract` to check its
    manifest, kinds, start/stop/start, every `ext:` predicate (never throws on an empty view, p99 under budget), its
    listeners, endpoint and configs. A template to copy, `examples/plugin-template/` (one shaded jar, a `sha256` task,
    a CI workflow), and two Community examples: `examples/plugins/debug/` (`/fc-x/debug/`: how the node sees your
    request and the guard's recent decisions about your address, loopback only by default) and
    `examples/plugins/crawler-feeder/` (keeps `lists/googlebot.txt` / `bingbot.txt` / `applebot.txt` current from the
    vendors' published ranges - a failed fetch keeps the old list - and adds the claimants a guard rule reports,
    `googlebot-claim | ua~(?i)googlebot ; !client-ip:@lists/googlebot.txt | reject:403 | dry-run`, once their
    reverse DNS is under the crawler's domain and resolves back to the address; checked off the request path, kept a
    week, an unconfirmed address never in its status - see its README).

- **`/fc-x/` is reserved - check your site has nothing there.** Every node now answers requests under `/fc-x/`
  itself, in server and filter mode alike: a plugin's path, or a one-line `404` (`no-store`) when no plugin owns
  it. Such a request no longer reaches the origin, so a page your application serves under `/fc-x/` is no longer
  reachable through Frontcache. Nothing else about routing changed.

- **`cookie-hmac:<name>` - a cookie a client cannot forge.** A new guard and `bots.conf` predicate, true when the
  cookie's value was signed with the node's secret and has not expired - what a rule that *exempts* visitors
  (those who passed a challenge, say) must decide on, since `cookie:` only tests presence. To use it, set
  `front-cache.visitor.cookie-secret` in `frontcache.properties` - at least 32 characters, the same on every
  node - and have whoever completes the challenge set the cookie: the value is `<expiry>.<mac>`, the MAC being
  base64url HMAC-SHA256 of `<name>|<expiry>` with that secret, which an origin's own challenge page can write. A
  node without the secret skips such a rule with an error at load. `front-cache.visitor.cookie-secret.previous`
  is accepted while a fleet rotates. See [guard-getting-started.md](../guard-getting-started.md) §4.1.

- **`challenge <provider> [else <action>]` - a new guard action.** A redirect to a challenge provider's page,
  served by a plugin under `/fc-x/<plugin>/` (with `return=` the visitor's path and query), logged with
  disposition `challenged`. It never redirects a non-GET (`429` with `Retry-After` instead), never acts on an
  `<fc:include>` or on `/fc-x/` itself, and never challenges a visitor already holding a pass from that plugin.
  **A Community node has no provider** - a provider is a plugin's - so there such a rule **acts as a dry run**
  (logged, request served as if the rule were not there, one error per reload saying why), or as its `else`
  action (`reject:` or `redirect:`) when the rule names one. The same `guard-rules.conf` is therefore safe on a
  node with or without the plugin. See [guard-getting-started.md](../guard-getting-started.md) §4.2.

- **`| trap` - a honeypot rule.** A new optional flag on a guard rule, for a path no visitor is ever sent to (a
  hidden, `nofollow` link to a path `robots.txt` disallows): `honeypot | uri~^/no-crawl/ | reject:404 Not Found |
  trap`. Such a rule matches a visitor's own requests only - never an `<fc:include>`, so a template that includes the
  path by mistake does not catch everyone who opens the page - and its guard log line names the address the node
  resolved through `front-cache.client-ip.trusted-proxies`, as a rate rule's does: `honeypot#203.0.113.7`, dry-run
  included (`honeypot:dry-run#203.0.113.7`). The line's client-IP column is the first forwarding header, which a
  scanner can write to frame someone else. Not accepted on an `allow` rule. A plugin observing `guard.matched` can
  put the address on a list for a while, and a rule of yours reading the list decides what it gets. Nothing changes
  for a rule without the flag; a node older than 2.13.0 refuses a rule with it (unknown flag), so roll the rule out
  after the nodes. See [guard-getting-started.md](../guard-getting-started.md) §4.4.

- **Hop-by-hop headers no longer reach the origin.** A node relayed every request header but `Connection` to its
  origin, so an h2c upgrade - `Upgrade: h2c` and `HTTP2-Settings`, which the JDK's `HttpClient` (at its default
  version) and `curl --http2` send on plain http - arrived without the `Connection` that came with it, and the origin
  answered `400` on every forwarded path. A node now also drops `Keep-Alive`, `Proxy-Connection`, `TE`, `Trailer`,
  `Upgrade`, `HTTP2-Settings` and `Proxy-Authorization` (a credential for a proxy, never for the origin) on origin
  and include calls. Nothing to do on upgrade. Browsers never sent these, so a site's pages were not affected; API
  clients and scripts on plain http were. Names a client lists in `Connection` are not dropped as well - that would
  let a client strip a header an upstream proxy added, such as `X-Forwarded-For`, before the origin reads it.
  **The other direction too:** an origin's `Connection`, `Keep-Alive`, `Proxy-Connection`, `TE`, `Trailer`, `Upgrade`,
  `HTTP2-Settings` and `Proxy-Authenticate` response headers were kept in the cache entry and replayed to every
  client - a `Connection: close` or `Keep-Alive: timeout=5` describing the origin's connection to the node, which the
  client never had. They are no longer stored or sent; an entry cached by an older node that still holds one is
  served without it, so the cache needs no flush.

- **Visitor types: `bots.conf` can declare types beyond `bot` and `guest`, each behaving like one of them.**
  A line `@type <name> like <bot|guest>` declares a type (at most 16; lower case, `[a-z][a-z0-9-]*`; `bot`, `guest`,
  `browser`, `all` and `none` are taken), and a rule classifies into it by naming it as its verdict:

  ```
  @type customer        like guest
  @type bot-whitelisted like bot
  customer           | cookie:hruc ; request-type:toplevel                | customer
  googlebot-verified | ua~(?i)googlebot ; client-ip:@lists/googlebot.txt  | bot-whitelisted
  ```

  **A declared type is its base everywhere it is not named** - in every stored entry, every page's `maxage`, every
  `client=`, every guard rule - so declaring one changes behaviour only where something names it, and needs **no
  cache flush**. Where it can be named:
  - `maxage="bot:30d, guest:1h, customer:0"` - a declared type the value does not name gets its base's TTL (an entry
    written before the type existed still serves it); `bot` and `guest` are unchanged - absent is not cached.
  - `<fc:include client="customer">` - customers only. `client="guest"` still reaches every type `like guest`, and
    two new forms: a comma list (`client="customer, captcha-passed"`) and exclusion (`client="!customer"`, everyone
    but customers; `client="guest, !customer"`). A name the node does not know is ignored with a warning, as any
    value but `bot` / `guest` was before.
  - `client-type:customer` in `guard-rules.conf`; `client-type:guest` matches customers too. **A `client-type:` name
    that is neither a root nor declared is now refused at load** (it used to load and never match) - check
    `guard-rules.conf` for one before upgrading. Declare a type and `reload-bots` before a guard rule names it.
  - the cache warmer's client type accepts a declared type.

  The built-ins stay on the roots (`no-user-agent` is `bot`, `default` is `guest`). The shipped `bots.conf` carries
  six example declarations, all commented out - `customer`, `captcha-passed`, `bot-whitelisted`, `bot-monitoring`,
  `ai-crawler like bot`, `ai-agent like guest` - with the warning that matters most: **one cached copy serves every
  type, so if the origin renders a page differently for a type, that type needs `:0` in that page's `maxage`**, or
  its render is served to everyone else. A type a guard rule exempts or favours should be decided on evidence a
  client cannot produce - `client-ip:` behind trusted proxies, or `cookie-hmac:`.

  **`no-store` makes that warning the type's rule instead of every page's**: `@type customer like guest no-store`. A
  request of a no-store type never writes an entry - whatever the page's `maxage`, page and include alike - and is
  still served the copy other visitors stored, per its TTL. A forgotten `customer:0` is then a missed cache hit, not
  a customer's render in a guest's page. Use it for every type defined by a session or tracking cookie (the shipped
  `customer` example has it). Two consequences: a soft-expired entry is a plain miss for such a request - fetched for
  it and not stored, the stale copy left for the next visitor - because a background refresh would carry its cookies
  to the origin and store the answer; and with `front-cache.include-fetch-target=edge` a fragment is stored by the
  node it loops back to, which honours `no-store` only when it adopts the page's type (a trusted peer). A declaration
  with any other word after the base is refused whole.

  Where the types show:
  - **the console's Visitor Types screen** has a types table above the rules - `bot`, `guest` and the declared
    types, each with what it behaves like, whether it is `no-store`, and the hits of the rules deciding it - from a
    new, additive `visitorTypes` array in `get-bots` (`name`, `base`, `noStore`, `hits`). An older console ignores it;
    an older node leaves it out and the screen shows no table for it.
  - **the Cache View lists an entry's expiry per type**: a row for each root and declared type with the stamp its
    requests resolve to, marked *inherited from guest* where the page did not name the type - not, as a list of
    stored keys would suggest, "not cached for customers" - and a stored key the edge no longer declares as never
    read. It replaces the bare list of dates, which did not say which type each one was.
  - **`frontcache_visitor_requests_total{type}`** on `/fc-metrics`: top-level requests by visitor type, once per
    page; a new label, `type`, bounded by the declarations (at most 18 at a time).

  What else changes, for every node, whether or not it declares a type:
  - **the request log and the failed-requests log gain a last column, `"<visitor-type>"`** - on every line, after
    whatever ended it before (the reason and status on the failed-requests log), and in the
    `front-cache.log-to-headers` trace header. It is the declared type, or the client type itself when none is
    declared; the client-type column keeps `bot` / `guest`. Positional consumers reading from the left are
    unaffected; the shipped logstash pipelines read it as an optional `visitor_type`.
  - **includes carry `X-Frontcache-Visitor-Type`** beside `X-Frontcache-Client-Type`, and the origin sees it on
    include fetches. It is honoured under the same conditions (a trusted peer, a request that arrived as an
    include) and only when this node declares the same type on the same base - otherwise the base alone is adopted.
    A client's copy is dropped; **a proxy that passes client headers through should strip
    `X-Frontcache-Visitor-Type`** as it strips `X-Frontcache-Client-Type`.
  - the plugin API (`plugin-api = 1`, additive): `RequestView.visitorType()` and `PluginRequest.visitorType()`
    (defaults answer `clientType()`), and a last `visitorType` component on `GuardMatched`, `ChallengeIssued` and
    `RequestCompleted`, whose previous constructors remain. `clientType` everywhere stays the root. A record
    pattern that deconstructs one of the three needs the new component.

  **Roll out in this order: nodes, then `bots.conf`, then pages.** A node before 2.13.0 reads an `@type` line as a
  User-Agent keyword that matches nothing and refuses every rule naming a declared type (those requests keep
  today's classification), ignores a declared type in a `maxage` list, and - the one that does not fail safe -
  treats `client="customer"` as no attribute and renders that fragment for every visitor. Rolling back, change
  pages first.

## Upgrading

No cache flush, and nothing to change in a config that uses none of the new features. Check these first:

- **`/fc-x/` is the node's.** A page your application serves under `/fc-x/` is no longer reachable through
  Frontcache - the node answers it (a plugin's path, or a `404`).
- **A `client-type:` name that is neither `bot` / `guest` nor declared in `bots.conf` is refused at load** - it used
  to load and never match. Check `guard-rules.conf` for one.
- **The request log and the failed-requests log gain a last column**, the visitor type. A parser reading from the
  left is unaffected; one anchored on the last column is not.
- **The console's realtime page reads `/fc-dashboard.stream`.** A proxy, firewall or guard rule in front of a node
  must admit it, unbuffered; a 2.6 node's realtime card is empty on this console.
- **A proxy that passes client headers through should strip `X-Frontcache-Visitor-Type`**, as it strips
  `X-Frontcache-Client-Type`.
- **Roll out in this order: nodes, then `bots.conf`, then pages and rules** - an `@type` declaration, a page naming a
  declared type and a `| trap` rule all need 2.13.0 on every node first. Rolling back, change pages first.
- **A 2.11 / 2.12 module** (`org.frontcache.module`) still runs, as a `manage` plugin with a WARN, for this release
  only. Move it to `org.frontcache.plugin.FrontcachePlugin` with a manifest.
- Hop-by-hop headers no longer reach the origin, nor a client from the cache - nothing to do.
