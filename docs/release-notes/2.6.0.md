# Frontcache 2.6.0 — release note

Docs index: [../doc-index.md](../doc-index.md) · All release notes: [README.md](README.md)

**Two things in this release are breaking changes: a container tag, and multi-domain
configuration.** Read the first two sections before upgrading. The Hystrix removal is the third big
change but needs no action from you — it is a dependency swap behind unchanged config and an unchanged
dashboard.

---

## The Frontcache server image no longer contains nginx

`pavlikovskiy/frontcache-server:2.6.0` is **Frontcache alone, plain HTTP on 9080**. Up to and
including 2.5.1, that tag was nginx + Frontcache listening on 80/443, and the Frontcache-only
variant was published separately as `-slim`. There is now one image, and it is what `-slim` was.

**If you run the container with `-p 80:80` or `-p 443:443`, that stops working on 2.6.0.** The
container listens on 9080 and terminates no TLS.

### What to do

| You run | Do this |
| --- | --- |
| `frontcache-server:<v>-slim` | **Nothing now.** 2.6.0 is published under the `-slim` tags too — same image, same behaviour, same port. **2.6.0 is the last release to carry them**, so move to the plain tag before 2.7.0; every existing `-slim` tag keeps resolving. |
| `frontcache-server:<v>` behind an ingress / ALB that already terminates TLS | Publish 9080 instead of 80/443. Nothing else changes. |
| `frontcache-server:<v>` as your public front door on 80/443 | You need a front door in front of it. See [examples/front-door](../../examples/front-door) — a two-container compose stack, or a script for a VM. |
| A pinned older tag | Nothing. No existing tag was deleted or rewritten; `2.5.1` is still `2.5.1`. |

**`latest` now points at 2.6.0** — that is, at a Frontcache-only image. No `latest` tag existed
before this release, so nothing that worked yesterday changed meaning under anyone; but from here
on `latest` follows the new shape. Pin an exact version anyway; that is what the pin is for.

### Also affected

- **`install-frontcache.sh` no longer has `--with-nginx`** (or `--origin-paths`). It installs
  Frontcache and the systemd unit. A host installed with `--with-nginx` on an older release
  **keeps its nginx** — the installer never removed nginx config, and upgrading does not touch
  `/etc/nginx`. To configure a front door on a new host, use
  [`examples/front-door/vm/configure-nginx.sh`](../../examples/front-door/vm).
- **`frontcache-server-<v>-nginx-site.sh` is no longer published.** Previously published versions
  of that artifact are untouched, so older installers still resolve it.
- **The published compose file publishes 9080**, not 80/443, and no longer sets `ORIGIN_PATHS` or
  the `KEYSTORE_*` variables.
- **`front-cache.http-port` / `front-cache.https-port` are now yours to set.** They are what
  Frontcache uses to rewrite redirects, so they must be the ports **clients** see. With a front
  door on 80/443, set them to 80/443 — the installer used to do this for you under `--with-nginx`.
  Get it wrong and everything works until something redirects, and then users land on `:9080`.

### Why

nginx was one of several front doors, but the only one baked into the product: the default image
*was* nginx, the installer could install nginx, and one of four published release assets was an
nginx template. That made the default artifact something other than the product, coupled the
front door to distribution internals (it read the Jetty demo keystore out of the bundle), and
meant improving the nginx config required cutting a release. It now lives in this
repository as a worked example, where it can be read, copied and changed freely — see
[examples/front-door](../../examples/front-door) and [docker.md](../docker.md).

## Multi-domain configuration is no longer supported

A node now serves **one site**. If `front-cache.domains`, or any `front-cache.domain.<domain>.*`
override, is set in `conf/frontcache.properties`, Frontcache logs the offending keys and **refuses
to start**.

Per-domain config directories are gone too. `conf/<domain>/bots.conf`,
`conf/<domain>/dynamic-urls.conf` and `conf/<domain>/fallbacks.conf` used to override the
top-level files for one domain; those subdirectories are no longer read, and a node that still
has one **refuses to start** rather than ignoring it silently. Move the entries into the
top-level `conf/bots.conf`, `conf/dynamic-urls.conf`, `conf/fallbacks.conf`. Per-domain fallback
*data* files under `fallbacks/<domain>/` move to `fallbacks/` alongside them.

### If you implement a plugin or use the client API

`org.frontcache.core.DomainContext` is gone, and the `domain` parameter went with it. Both
interfaces below are extension points (`front-cache.fallback-resolver.impl`,
`front-cache.cache-processor.impl`):

```java
// FallbackResolver
- WebResponse getFallback(DomainContext domain, String fallbackSource, String urlStr);
+ WebResponse getFallback(String fallbackSource, String urlStr);

// CacheProcessor
- void putToCache(String domain, String url, WebResponse component);
+ void putToCache(String url, WebResponse component);
- void removeFromCache(String domain, String filter);
+ void removeFromCache(String filter);
- void removeFromCacheAll(String domain);   // removed; removeFromCacheAll() is the only flavour
- void putToCacheImpl(String domain, String url, WebResponse component);   // CacheProcessorBase
+ void putToCacheImpl(String url, WebResponse component);

// FrontCacheClient
- boolean putToCache(String domain, String key, WebResponse webResponse);
+ boolean putToCache(String key, WebResponse webResponse);
```

`WebResponse.getDomain()` / `setDomain()` are gone too. `getFallbackConfigs()` still returns
`Map<domain, …>` — one entry, so the console needs no change.

### Management API and the L2 index

- **`invalidate` with `filter=*` now always empties the whole node.** It used to be domain-scoped,
  which meant entries pushed in by index replication — stamped with the *source* edge's domain —
  walked straight past it and kept being served. That is how one edge kept serving ~336k replicated
  pages after an "invalidate all". The `all-domains=true` parameter that worked around it is gone;
  `*` does what it says.
- **`put-to-cache` no longer requires a `domain` parameter.** One sent by an older client is
  accepted and ignored, so a mixed-version replication pair keeps working. The response no longer
  carries a `domain` field, and every management response now ignores unknown JSON properties — so a
  *newer* client reading an *older* node's response does not fail either.
- **`get-cache-state` drops the `cached-entries-L2.<domain>` counter.** `cached-entries`,
  `cached-entries-L1` and `cached-entries-L2` are unchanged.
- **The L2 Lucene index has one fewer stored field.** Old indexes still open and read fine, but
  their entries carry a `domain` field nothing looks at. The index is pure cache — dropping
  `cache/l2-lucene-index` on upgrade costs one cold period and nothing else.

Unaffected, despite the similar names:

- `front-cache.default-domain` — this node's own public hostname. Still used, still recommended.
- `front-cache.site-key` — the management API's shared secret. Per-*domain* site keys
  (`front-cache.domain.<d>.site-key`) are gone; the node's own key is not.
- `front-cache.origin-host` / `origin-http-port` / `origin-https-port` — the single origin.
- Multi-*node* clustering, and index replication between nodes. Both untouched.

### If you set `front-cache.domains`, read this even if you do not upgrade

Serving several domains from one node was never sound, and the failure mode is a **cross-domain
content leak that exists in every release up to and including 2.5.1**:

- **Shared cache.** L2 cache entries are keyed by the request **path only** — scheme, host and port
  are stripped. A request for `/page.htm` on domain A and a request for `/page.htm` on domain B are
  the same cache entry. Domain B is served domain A's page, without its own origin ever being
  contacted. Verified on a two-domain node with two distinct configured origins.
- **Shared circuit breaker.** Circuit breakers are keyed by command name only, so one domain's
  failing origin opens the breaker for **every** domain on the node: healthy sites start serving
  fallbacks because an unrelated site is down.
- **Collapsed metrics.** Command metrics are keyed by command name too, so the dashboard attributes
  all traffic to whichever domain registered first and shows nothing for the others.

If you are running a multi-domain node, treat the cache as cross-contaminated: invalidate
everything, and split the domains across nodes.

### What to do

Run one Frontcache node per site — a separate process or container each, with its own
`FRONTCACHE_HOME`:

```properties
# conf/frontcache.properties, per node
front-cache.default-domain=www.example.com
front-cache.origin-host=origin.example.com
front-cache.origin-http-port=80
front-cache.site-key=<this node's key>
```

Then delete every `front-cache.domains` and `front-cache.domain.*` line. Removing the keys is a
config edit and a restart.

Failing closed rather than ignoring the keys is deliberate: they ask for per-domain origin
routing, and a node that silently sent every domain to one origin would be a worse outcome than one
that does not start. What a one-site node looks like in each topology is in
[deployment-usecases.md](../deployment-usecases.md).


## Netflix Hystrix is gone — the resilience layer runs on Resilience4j

**Nothing to configure.** `conf/hystrix.properties` keeps its name and every one of its keys, the
command names on the dashboard are unchanged, `/hystrix.stream` is still the endpoint, and its JSON is
field-for-field what it was. The console needs no change. Upgrade and it keeps working.

What changes is the dependency tree. These six artifacts, all unmaintained, all previously on the
runtime classpath of every origin call, are gone:

```
com.netflix.hystrix:hystrix-core:1.5.18            last release Nov 2018
com.netflix.hystrix:hystrix-serialization:1.5.18   last release Nov 2018
com.netflix.archaius:archaius-core:0.4.1           last release 2014
commons-configuration:commons-configuration:1.8    last release 2012
commons-lang:commons-lang:2.6                      last release 2011
io.reactivex:rxjava:1.2.0                          1.x EOL Mar 2018
```

In their place: `resilience4j-circuitbreaker`, `-timelimiter` and `-bulkhead` 2.4.0 (each declaring
only `resilience4j-core` and `slf4j-api`) plus an explicit `HdrHistogram` 2.2.2. Verify with
`./gradlew :frontcache-core:dependencies --configuration runtimeClasspath`.

Circuit-breaker thresholds, sleep windows, timeouts, semaphore limits and thread-pool sizes are
translated key-for-key, including the two Resilience4j defaults that differ from Hystrix and would
otherwise have changed behaviour silently: the half-open probe count is pinned to 1 (Resilience4j
defaults to 10, which would send ten concurrent probes at an origin that had just recovered) and
bulkhead waits are pinned to zero so a rejection stays a rejection instead of becoming a queued wait.

### Four behaviour changes worth knowing about

**The console's thread-pool panel works now.** It has never rendered. Hystrix keys thread pools by pool
name alone, and the stream filtered pool frames by comparing that name against the caller's domain -
`"OriginHitsPool".equals(domain)` - which is false for every domain that can exist, so the frames never
left the server. A thread pool is a node-level resource; it is no longer filtered by anything.

**A slow cache read returns its value instead of being discarded.** `Cache-Hits` and `Input-Requests`
are semaphore-isolated but carry `execution.isolation.thread.timeoutInMilliseconds`. Under Hystrix that
budget was half-enforced, which we only established by measuring it: at the budget the caller was handed
the fallback, but the call itself ran to completion on the caller's thread and its finished work was
thrown away — so a cache read slower than 1.5 s returned `null`, the engine read that as a miss, and it
re-fetched from the origin. The budget is now *reported* rather than enforced: an overrun logs a `WARN`
and increments a counter (`rollingCountBudgetOverrunObserved`, a new field on the dashboard JSON), the
call returns its real value, and neither the error percentage nor the circuit breaker moves. This also
removes a latent defect on requests over 20 s, where `FC_Total`'s fallback wrote the servlet response
from the Hystrix timer thread while the request thread was still writing it.

**`fallback.isolation.semaphore.maxConcurrentRequests` is no longer enforced.** It is still parsed and
still reported on the dashboard, so existing config round-trips, but it bounds nothing: a call only
reaches its fallback while already holding an execution permit, so concurrent fallbacks are bounded by
`execution.isolation.semaphore.maxConcurrentRequests` before this limit could apply. A node with the key
set logs a `WARN` once at startup, because the alternative is an operator tuning a number that does
nothing.

**`/hystrix.stream` answers `401` for a missing or wrong `x-frontcache-site-key`.** It used to answer
`200` and stream empty frames — an authorization failure that looked like an idle node. `503` now means
only what it says: shutting down, or the connection cap is reached. If you drive the endpoint through the
console's proxy, note that the proxy now propagates the upstream status instead of turning it into an
empty `200`.

### New: Prometheus / OTLP metrics export

Optional, off by default, and additive - the SSE stream and the console are unaffected either way.

```
front-cache.metrics.export=none|prometheus|otlp|both     # default none
front-cache.metrics.otlp.url=http://collector:4318/v1/metrics
front-cache.metrics.otlp.step=60s
front-cache.metrics.otlp.headers=Authorization=Bearer ...
```

With `prometheus`, a scrape endpoint appears at `/fc-metrics`:

```
frontcache_command_events_total{command="Cache-Hits",event="success"} 3.0
frontcache_command_latency_seconds{command="Cache-Origin-http",quantile="99"} 0.031
frontcache_threadpool_rejections_total{pool="OriginHitsPool"} 0.0
frontcache_resilience4j_circuitbreaker_state{name="Cache-Origin-http",state="closed"} 1.0
```

Every series is named `frontcache_*` and labelled by command, event, quantile and pool - and by nothing
else. Nothing is labelled by request URL: on a page cache the URL space is unbounded, so a per-URL label
is a way to take down a Prometheus server rather than an observability feature.

Two things to know before enabling it:

- **`/fc-metrics` answers only on `front-cache.management.port` when that is set**, the same rule as
  `/hystrix.stream`. A scrape endpoint is unauthenticated by convention, so the connector is the access
  control. If you use guard rules, allow it - Frontcache warns at startup when a rule would block it.
- **OTLP needs `front-cache.metrics.otlp.url`.** Without it, OTLP export stays off rather than logging a
  delivery failure on every push. Header values are treated as secrets and never logged.

This is the only part of the release that adds dependencies: Micrometer 1.17.1 (`-core`,
`-registry-prometheus`, `-registry-otlp`) and `resilience4j-micrometer` 2.4.0, plus their transitives.
They are only *loaded* when export is enabled, but they are on the classpath either way.

Cache metrics - L1/L2 hit ratio, eviction rate, index size - are not exported yet. They are the series
most operators will want, and they are a separate piece of work.

### What kept its Hystrix name, and why

The package `org.frontcache.hystrix`, the `FC_*` class names, `conf/hystrix.properties` and the
`/hystrix.stream` URL are all unchanged. That is deliberate for this release: it keeps the diff to
behaviour, and it means no config edit, no dashboard change and no nginx rule change on upgrade. A
reviewer grepping the jar for "hystrix" will still find those names — the library is what left, and the
dependency listing above is the check that matters. The rename is planned for a later release, with the
old config file name and the old endpoint kept working.


## Upgrading

Nothing beyond the two sections above requires action.

- **Archive / installer**: unchanged procedure. `install-frontcache.sh --version 2.6.0` carries
  your config across, and rollback is still a symlink flip.
- **Config**: no config file changed shape, but multi-domain keys are now rejected — see above.
  `conf/hystrix.properties` is read as before, by Resilience4j instead of Hystrix. The container still
  seeds only *missing* files into an existing `conf` volume.
- **Cache**: the L2 index is pure cache; drop it or keep it.
