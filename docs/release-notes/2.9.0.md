# Frontcache 2.9.0 — release note

Docs index: [../doc-index.md](../doc-index.md) · All release notes: [README.md](README.md)

**Most of this release is one story.** A production edge showed `Input-Request` at **~1200/s
against ~11/s of real client traffic**. Chasing that number found a cache-key bug that had been
making a class of `<fc:include>` fragments *permanently* uncacheable, and four more faults on the
way — two of them things that had been quietly broken since they were written.

Alongside it, six things that are not that story:

- **The console authenticates.** It had no authentication at all, while holding the api-key that
  authorizes cache invalidation across the fleet. One user, no roles, and the bundle ships
  `admin`/`admin` — **change it**. See [Console authentication](#the-console-authenticates-now).
- **Guard redirects were putting the origin's private hostname into URLs handed to browsers** —
  18.9% of one edge's login redirects were wrong. See
  [Guard redirects](#guard-redirects-were-leaking-the-origins-hostname).
- **`maxage` can give each visitor type its own TTL** — `maxage="bot:30d, guest:1d"`. Naming a
  prefix used to force the other type out of cache entirely. See
  [a TTL per visitor type](#a-ttl-per-visitor-type).
- **`conf/bots.conf` classifies on more than the User-Agent now**, and reloads without a restart.
  One behaviour change to know about: bare keywords match case-insensitively. See
  [Bot classification](#bot-classification-confbotsconf-takes-rules).
- **Five resilience command keys were renamed, and two became one.** Your `resilience.properties`
  keeps working — see [Command keys](#resilience-command-keys-renamed).
- **Two renames and one removal — and one of them is a config key you must edit by hand**, plus the
  fix for a client-type bug the renaming exposed. See
  [Renames and removals](#renames-and-removals); the short version is the box below.

The console also gained a **Visitor Types** screen, and its Configs tabs now show the config files
as they sit on disk rather than a parsed summary of them — see
[the console screens](#console-the-config-screens-show-the-files).

| | before | after |
|---|---|---|
| requests at nginx | 1183.1/s | **11.1/s** |
| — fragment fetches | 1193.3/s | **1.7/s** |
| include resolutions | 1221.6/s | 832.1/s (all in-process) |
| HTTP fetches per include resolution | ~1.0 | **0.002** |
| `error.log` growth | ~2 GB/day | silent |

The node now serves *more* include resolutions than before while making **1/500th** the HTTP
requests. **None of that** required a config change — but the renames below do.

> [!IMPORTANT]
> **This upgrade is not a drop-in.** Four things must be changed by hand, and **three of them fail
> silently** — a node that misses them starts, serves traffic, and is wrong:
>
> 1. **Rename `front-cache.site-key` to `front-cache.api-key`** in every `frontcache.properties`.
>    There is no fallback. A node still using the old name has **no API key at all** — its management
>    API, dashboard stream and `/fc-metrics` answer anyone who can reach a connector.
> 2. **Rename `siteKey` to `apiKey` in `frontcache-console.conf`.** The console is the one component
>    that *does* fail loudly here: it refuses to start.
> 3. **Flush the cache** (`invalidate` with `filter=*`) after replacing the artifact, and change any
>    `browser` client-type token in your pages and `guard-rules.conf` to `guest`.
> 4. **Set a console password.** The console authenticates now, but an existing
>    `frontcache-console.conf` has no `user`/`password` and therefore keeps running **unauthenticated**
>    — it warns on every startup, and that is the only notice you get. A fresh bundle is protected,
>    with the published default `admin`/`admin`, which it also warns about.
>
> Full detail in [Renames and removals](#renames-and-removals) and
> [Console authentication](#the-console-authenticates-now).

Beyond those, four things change behaviour without any config edit, and all four are in
[What to do](#what-to-do). Two of them are worth reading even if you skip everything else:

- **Cache-missing includes are now fetched from your origin instead of from your own front door.**
  New key `front-cache.include-fetch-target`, default `origin`, with `edge` as an escape hatch.
- **Guard rules containing a regex alternation were being silently skipped.** They now load. If you
  have any, your node starts enforcing rules it has been ignoring.

**If you subclass `IncludeProcessorBase`**, three `protected` methods gained a parameter, and the
renames move one class and several method names — see
[If you extend Frontcache in Java](#if-you-extend-frontcache-in-java). The three reflection-loaded
extension point *interfaces* — `CacheProcessor`, `IncludeProcessor`, `FallbackResolver` — are
unchanged from 2.8.0. Every HTTP wire format is unchanged too, including the credential a caller
sends: only the *property that configures it* was renamed, so agents, consoles and peer nodes need
no coordination.

How requests flow through the command wrappers, and what each command key means, is in
[resilience-command-flow.md](../resilience-command-flow.md).

## The cache-key bug

**A `<fc:include>` whose URL carried an empty query parameter could never hit cache — ever.**

The two legs of an include disagreed about that parameter:

- **The probe** looked up the raw include URL: `…/fc/recent-updates-add.htm?locale=zh&id=`
- **The fetch** went out through `FCUtils.buildRequestURI`, which re-serialises the query and drops
  any parameter with no value. So the entry was stored under `…?locale=zh`.

The key being probed had never existed and never would. Every request re-fetched the fragment, over
the CDN, from a node that already had it cached:

```
probe   ?locale=zh&id=   miss - nothing is ever stored under this
fetch   ?locale=zh       the empty parameter is gone by the time it reaches the wire
store   ?locale=zh       what the serving node receives, and stores
probe   ?locale=zh&id=   miss again, for the life of the entry
```

33 fragment URLs on one node were generating **608 origin fetches per second** this way, one of them
170/s on its own.

**The fix** is `FCUtils.canonicalizeURL` — one normaliser, applied to both legs, idempotent so it is
safe on a path that may already have applied it. A unit test pins it, and it is now the
single definition of "the cache key for a URL that is fetched through `buildRequestURI`".

**No cache migration.** Entries were always *stored* under the canonical key; only the lookup was
wrong. Nothing is orphaned, and previously unreachable entries simply become reachable.

## Soft refresh no longer empties the cache, or stampedes

`CacheProcessorBase.doSoftInvalidation` had two defects that fed each other:

1. **It removed the entry before refetching.** Soft refresh exists to keep serving the stale value
   while a fresh one is fetched. Removing it first meant serving *nothing* for a full origin round
   trip — and a refresh that *failed* left the key empty, exactly when the stale copy matters most.
2. **No single-flight.** Every request arriving during that window queued another refresh, and each
   one removed the entry again. One expiry started a herd that grew with request rate.

Both fixed: a per-key in-flight claim (losers serve the stale entry and return — nobody waits),
released in the task's `finally` so the claim covers the whole run rather than just the submit, and
the removal deleted. A unit test covers it; three of its five cases fail against the old code and the
other two guard against over-broad single-flighting.

## New: includes are fetched from the origin

Until 2.9.0 a cache-missing `<fc:include>` was fetched over HTTP **against the `Host` header** — out
to the CDN and back in at the front door of the node already serving the page, which then fetched
the origin and cached the result on the way back through. The code said so in its own comment:
`// recursive call to FCServlet`.

It is now fetched from `front-cache.origin-host` directly, and the requesting side caches the result
itself.

```properties
# origin (default) | edge (pre-2.9 behaviour)
#front-cache.include-fetch-target=origin
```

**The cache key does not move.** An entry is still keyed on the public URL
(`https://www.example.com/fc/x.htm?locale=en`); only the URL that goes on the wire changes. So this
does not orphan a warm cache and does not create a second key per fragment — and switching back to
`edge` does not either.

What it removes, per cache miss: a WAN round trip to reach yourself, a TLS handshake, and a request
parse. What it removes structurally: includes stop landing on the front door, where they hold a
concurrency permit, occupy a container thread, and can be rate-limited by whatever proxy sits in
front. A post-invalidation stampede no longer doubles its own work.

**Filter mode is included, and works differently.** There the origin *is* the app the filter is
installed in, so the fetch necessarily re-enters the filter — what changes is that it goes to
`front-cache.origin-host` (normally `localhost`) instead of out to the CDN and back. To stop the
re-entry storing a second copy under the address it arrived at, the fetch is marked
`x-frontcache-dynamic-request` and this side keeps sole ownership of the single public key.
**`front-cache.origin-host` and `front-cache.origin-http-port` must therefore be correct in filter
mode** — they already had to be, since soft invalidation/refresh has always used them, but a wrong
value used to fail silently (soft-expired entries just stopped refreshing) and now fails loudly.

**Rolling back needs no code change:** set `front-cache.include-fetch-target=edge`.

## `Input-Request` now counts client traffic only

The dashboard's headline figure counted client requests **and** the node's own includes coming back
round, because a cache-missing include arrived at the front door as an ordinary request. Fixing the
keys removed almost all of the volume but none of the miscounting: an include that misses still has
to fetch, and in filter mode or a chained topology it re-enters however includes are routed.

`FC_Total` now picks its command key from the request type `init()` has already computed — the same
classification the request log prints as `toplevel` / `include` / `include-async`, derived from
whether the caller sent `x-frontcache-request-id`. No new header, no new plumbing. `toplevel` stays
`Input-Request`; an include becomes `Include-Request`.

**Your `resilience.properties` needs no edit.** A brand-new command key would otherwise fall through
to the built-in defaults — `THREAD`, `maxConcurrentRequests=10`, `timeout=1000` — and work fine right
up until it began shedding into fallback fragments above 10 concurrent calls. So `Include-Request`
**inherits `Input-Request`, property by property**, legacy `hystrix.*` prefix included. An explicit
`Include-Request` stanza still overrides, per property.

**What the split does change:** a command key owns its own bulkhead and circuit breaker. Includes and
client requests now get one each instead of sharing — an include storm can no longer consume the
permits visitor requests need, and a failing include path no longer trips the breaker serving
visitors. The cost is that **total concurrency across the two is now the sum**. If your
`Input-Request.maxConcurrentRequests` was sized as a hard ceiling on everything, set
`Include-Request` explicitly.

Unit tests cover both halves: the four classification cases, and that an un-updated
file inherits rather than falling back to the built-ins.

**Keep the counter after it reads zero.** With includes fetched from the origin, `Include-Request`
goes to ~0 on a standalone node — and that is the point. It is an assertion, not a capacity plan:
filter mode, a chained topology, and the `edge` escape hatch all still route includes through the
front door, and with one counter there is no way to distinguish "includes no longer reach the front
door" from "includes reach it and are being counted as client traffic again", which is the original
bug. It costs one dashboard tile and no config.

## Guard rules: `|` is both the field separator and regex alternation

Found in a node's `error.log` while looking for something else:

```
ERROR o.frontcache.guard.GuardRuleEngine - Skipping guard rule (guard-rules.conf:119):
    invalid regex in 'uri~^(/[a-z]{2})?/ccc/(recent': Unclosed group near index 25
```

The rule on that line is fine. `GuardRuleParser` split the line on `"\\|"`, so a condition
containing `(recent|user)` was cut at the alternation and `Pattern.compile` received
`^(/[a-z]{2})?/ccc/(recent`. The parser is deliberately tolerant per line — one bad rule is skipped
and the file keeps working — which is exactly what made this invisible.

On the node where it was found: **5 of 19 rules refused, every one of them an anti-scraper deep-paging
redirect** — the rules written as the defence against the traffic flood that started the whole
investigation. Dead since the day they were written, costing nothing measurable until the traffic
they were written for arrives.

`GuardRuleParser.splitFields` now treats `|` as a separator only where a regex cannot be using it:
outside any `(...)` group, outside any `[...]` character class, and not backslash-escaped. Group
nesting is counted, not merely detected. Fields come back byte-identical and nothing is unescaped, so
`\|` still reads as a literal pipe to the regex engine. An unbalanced bracket still refuses the rule,
but now says so instead of complaining that a line which visibly has three fields does not.

```
that node's guard-rules.conf, through the real parser:
  before: 14 parsed, 5 refused
  after:  19 parsed, 0 refused
```

The test for this uses the real config lines; its first four cases fail against the old
splitter.

**On upgrade, rules you have been running without start being enforced.** Check `get-guard-rules`,
which reports what the node is actually running rather than what the file says.

## Fallbacks work during the first three seconds after start

The dashboard showed `Input-Request` 24% failed while `Cache-Hit`, `Cache-Miss` and
`Cache-Bypass` all showed **zero** failures — a command failing without any of its downstream commands
failing. Every exception was the same:

```
java.lang.RuntimeException: FallbackResolver is not initialized.
```

The engine starts the resolver on a background thread behind a deliberate three-second sleep, because
fallbacks sourced from URLs cannot be fetched before the node is listening. But
`FallbackResolverFactory.getInstance()` **threw** for that whole window — and its callers are only
ever code that is already handling a failure. So for three seconds after every restart, a failing
fragment took the whole page down instead of degrading, precisely when a cache is least able to
absorb it.

Nothing about the sleep required the throw. Creating the resolver reads `conf/fallbacks.conf` from
disk and needs no server at all; only the origin warm-up needs the node up. The two are now separate:

- `getInstance()` creates the resolver on demand and never throws, so file-based fallbacks answer
  from the first request. The instance is `volatile` and published only once fully constructed — it
  had been a plain static assigned *before* `init()` ran, so a racing thread could see a half-built
  resolver.
- `init(client)` still runs the origin warm-up, behind its own flag. That flag matters:
  `FrontCacheIOServlet` calls `init` on **every** `get-fallback-configs`, so an unguarded warm-up
  re-fetched every URL-sourced fallback each time the console polled. It is set in a `finally`, so a
  warm-up that throws is attempted once rather than on every later poll, and cleared by `destroy()`,
  which is what makes the servlet's destroy-then-init a real reload.
- `FrontCacheEngine` creates the resolver synchronously during init and leaves only the warm-up
  deferred, so a bad `fallbacks.conf` line is logged at startup instead of on the first failure.

Six cases cover it, including 32 concurrent first callers sharing one resolver.

## Request log: three lines corrected

The format is unchanged. What changed is which lines exist.

- **A cache-missing include is still logged exactly once.** It used to be logged by the engine when
  the loopback arrived; with the loopback gone, the requesting side writes that line itself, against
  the public URL and with the real byte count. Watch the `dynamic` marker on include legs after
  upgrading: it must stay in step with `Cache-Miss`.
- **A combined batch's envelope is no longer logged as an include leg.** It never was one —
  `logCombinedInclude` writes a line per member, which is the accounting that matches what the page
  actually used. The envelope line added one phantom include per batch: eleven of them in a single
  end-to-end run. Nothing broke; "includes per page" simply read high.
- **A bypassed request that Frontcache itself marked dynamic is no longer logged twice.** Whoever set
  the flag owns the line.

**And a log line can no longer fail the request it describes.** An **async** include is resolved
fire-and-forget after the top-level response has completed, by which time the container has recycled
the servlet request — and Jetty does not answer null for a recycled request, it throws
`NullPointerException: … ServletApiRequest.getRequest() is null`. That escaped as a `Throwable` out of
the include, which then resolved a fallback for a fragment it had **already fetched successfully**.
`RequestLogger` now reads the method and headers through tolerant accessors, writing `-` for an
unreadable method exactly as guard-rule logging already did. Four such failures in one end-to-end run
before the fix, none after.

## Guard redirects were leaking the origin's hostname

**`${url}` and `${url:enc}` in a guard redirect echoed whichever host the request arrived under.**
On one production edge that put `origin.hobbyray.com` — the private origin name — into the `return=`
of a login redirect, and therefore into browsers' address bars, crawler indexes, and the URL the app
sends a visitor to after they sign in.

One day of logs on that node, 113,405 arrivals at `/login.htm?return=…`:

| what `return=` pointed at | count | |
|---|---|---|
| `https://www.hobbyray.com` | 91,968 | correct |
| `http://www.hobbyray.com` | 10,948 | **wrong scheme** |
| `https://origin.hobbyray.com` | 10,487 | **wrong host** — the reported bug |
| `http://fc-us.hobbyray.com` | 2 | wrong host *and* scheme — the node's own name |

**18.9% were wrong, and the reported host bug was only half of it.** The scheme was broken the same
way one field over, and more often.

### The distinction the code was missing

A node is reachable under several names — the CDN's, an internal alias, its own hostname, a bare IP
— and it had one accessor for all of them. But "the Host this request arrived under" and "the name
we are willing to put in a URL we hand a browser" are different questions, and only the second has a
single right answer.

They are now separate:

| | reads | used by |
|---|---|---|
| `RequestContext.getPublicHost()` | `front-cache.default-domain` | `${url}`, `${url:enc}`, `${host}`, `FCUtils.transformRedirectURL` |
| `RequestContext.getFrontCacheHost()` | the arriving `Host` | `host~` / `host:ip` predicates, the cache key, the URL column of both log lines |
| `getPublicProtocol()` | `front-cache.public-scheme`, else `X-Forwarded-Proto` **from a trusted peer**, else the connection | the same URL-emitting paths |
| `getFrontCacheProtocol()` | the connection | the cache key |

**Neither half may drift into the other**, and the log column is the reason: normalizing the URL
column of the request log would make the fix unverifiable, because that column is the canary you
check it with.

`X-Forwarded-Proto` is honoured only from a peer in `front-cache.client-ip.trusted-proxies` — a
client that could set it would be choosing the scheme of a URL Frontcache vouches for.

### What to do

| You have | Do this |
| --- | --- |
| Guard rules using `${url}`, `${url:enc}` or `${host}` | **Set `front-cache.default-domain` to your public hostname** if it is not already. Unset, blank, or left at the `default-domain` placeholder means the node falls back to the arriving Host — the old behaviour — rather than emitting `https://default-domain/…`. |
| A TLS terminator in front of Frontcache | **Set `front-cache.public-scheme=https`**, or make sure the terminator is listed in `front-cache.client-ip.trusted-proxies`. Without one of those, `${url}` carries the scheme of the plain-HTTP backend hop. |
| An origin that builds its own absolute URLs | Optional: `front-cache.origin.forward-public-host=true` sends `X-Forwarded-Host` / `X-Forwarded-Proto` to the origin so the app can build public URLs itself. |

`front-cache.default-domain` is also an allowed redirect target in its own right now, and
`GuardRuleEngine.sanitizeTarget` re-checks the host **after** placeholders expand — the load-time
check in `GuardRuleParser` can only see the static string, which is what let an expanded `${url}`
through in the first place.

The placeholders themselves, and every predicate that can appear beside them, are in
[guard-getting-started.md](../guard-getting-started.md).

## Resilience command keys renamed

**Five command keys changed name, and two of them became one.** A command key is not an internal
label: it owns a circuit breaker, a bulkhead and a time limiter, it is the `<key>` in
`resilience.command.<key>.*`, it is the `name` on a dashboard card, and it is the `command` label on
every `frontcache_*` metric series.

| 2.8.0 | 2.9.0 | |
|---|---|---|
| `Input-Requests` | `Input-Request` | |
| `Include-Requests` | `Include-Request` | |
| `Cache-Hits` | `Cache-Hit` | spelling only — it is still every cache lookup, hit or miss |
| `Origin-Hits` | `Cache-Bypass` | says what it is — the origin call for a request that never consults the cache |
| `Cache-Origin-http`<br>`Cache-Origin-filter` | `Cache-Miss` | **two keys combined into one** |

The thread pool was renamed with them:

| 2.8.0 | 2.9.0 | |
|---|---|---|
| `OriginHitsPool` | `OriginPool` | `resilience.threadpool.<pool>.*` |

`Cache-Hit` is the only one of the five where nothing but the spelling moved — it was the last key
left in the plural, and the command behind it is unchanged. The pool is shared by `Cache-Miss` and
`Cache-Bypass`, and is named after
what it is for rather than after either command — the old name was after the rarer of the two paths
(`Origin-Hits`, now `Cache-Bypass`), so it pointed at the one that does not fill the pool.

### Your `resilience.properties` keeps working

**Each new key inherits its old name's settings, property by property**, the same mechanism
`Include-Request` already used, with the legacy `hystrix.*` prefix included. **The pool key does
too.** So an un-edited file configures the commands and the pool it always configured, and this is
an edit you can make at your leisure.

That is not politeness. Renaming a command key with no fallback would drop it onto the built-in
defaults — `timeout=1000`, `maxConcurrentRequests=10` — on every node whose file predates the
rename. For an origin call tuned to ten or twenty seconds, that is not a metrics change; it is an
outage under load. The pool is worse still: a `resilience.threadpool.<pool>.coreSize` that resolves
to nothing falls to `threadpool.default.coreSize`, or on a file that never set one to the built-in
**10** — every origin call on the node capped at ten threads, having changed nothing.

Until you do edit it, the dashboard and `/fc-metrics` show the **new** names while your file says
the old ones. That is confusing to read, which is the reason to get to it.

### `Cache-Miss`: read this before you edit

The two old keys named the **transport** — a socket to the origin, or the filter chain of the app
Frontcache is installed in. That is a property of how the node is deployed, not of what the command
does; both are "the origin call behind a cache miss", and an operator tuning one always wanted the
same number in the other.

> [!NOTE]
> **On a filter-mode node this is a behaviour change, and only there.** A standalone node only ever
> used the http key. A filter-mode node uses the filter chain for the page's own origin call and
> HTTP for its include fetches (`fetchOverHttp` is always HTTP, never the chain) — so it had two
> independent breakers over the same origin and now has one.
>
> Sharing is the more correct answer: it is one origin, and a breaker that sees all of its failures
> opens on evidence the split version was throwing away. But the **concurrency permits are shared
> too**, so if you sized those two stanzas as separate ceilings, set `Cache-Miss` deliberately.

`Cache-Miss` inherits from `Cache-Origin-http` — the key every deployment mode used. **If you tuned
`Cache-Origin-filter` differently, that value is the one that is lost**, and you must set
`resilience.command.Cache-Miss.*` explicitly.

### `conf/hystrix.properties` is no longer read

The config file was renamed in 2.7 (`hystrix.properties` → `resilience.properties`), the old name
was read as a fallback for one release with a warning that said it would go, and **this is that
release.**

> [!WARNING]
> **If your `FRONTCACHE_HOME/conf/` still contains only `hystrix.properties`, rename it.** A node
> that starts without a readable `resilience.properties` runs every command on built-in defaults —
> `timeout=1000ms`, `maxConcurrentRequests=10` — which is invisible until load arrives and then
> looks like an origin problem rather than a config one.

The node still *looks for* the old file, purely to tell you: an **error** naming the fix when it is
the only one present, a warning when it sits beside a live `resilience.properties`. The
`get-resilience-configs` management action lost the same fallback, in step — it exists to show you
the file the node is actually using, so the two must not disagree.

**The `hystrix.*` KEY PREFIX is untouched and stays supported indefinitely.** It was always a
separate contract on a separate schedule; renaming the file is the entire migration, and the keys
inside it can stay exactly as they are. The repo's own filter-mode e2e node is the proof: its
`resilience.properties` is deliberately full of `hystrix.command.*` keys.

The installer and the Docker conf-seeder **do the rename for you**, and both changed direction to do
it. They used to leave a carried-over `hystrix.properties` in charge and demote the shipped default;
now they move your file onto the current name and put the shipped default beside it as
`resilience.properties.new`. Your settings are what takes effect either way — but only the new
behaviour is still true now that the fallback is gone.

### Dashboards and scrapes

- **Anything pinned to a command name needs repointing** — a Grafana query on
  `frontcache_command_*{command="Input-Requests"}` or `{command="Cache-Hits"}`, a dashboard panel,
  an alert rule. The config file keeps working through the inheritance above; a metric label does
  not inherit, so a panel naming an old key reads **zero**.
- **A filter-mode node's two origin cards become one.** The console pins the circuit cards in the
  order a request travels - `Input-Request`, `Include-Request`, `Cache-Hit`, `Cache-Miss`,
  `Cache-Bypass` - and lists every superseded spelling at the position of the name that replaced it,
  so a console reading a mixed fleet keeps a stable layout while nodes upgrade. A command the CSS
  does not name sorts after those five rather than ahead of them.
- **A thread-pool panel or `frontcache_threadpool_*{pool="OriginHitsPool"}` query needs repointing**
  to `OriginPool`.
- The dashboard stream JSON did not change shape. Only the `name` values did.

## Renames and removals

Three names change. They are grouped here because they share a property: **the old spelling is not
accepted anywhere, and nothing refuses to start over it** (with one exception, the console). A node
that misses these comes up healthy and behaves wrongly.

That was a deliberate choice, not an oversight. Every one of these could have carried a deprecated
alias, and none does — the cost is a hand edit at upgrade time, and the benefit is that no
half-renamed config survives into the next release to be discovered later.

### Renamed: `front-cache.site-key` is now `front-cache.api-key`

> [!WARNING]
> **A node whose `frontcache.properties` still says `front-cache.site-key` has no API key.** It
> starts, serves traffic normally, and answers the management API, the dashboard stream and
> `/fc-metrics` to anything that can reach a connector. There is no warning.

The credential itself is untouched. Callers still send `Authorization: Bearer <key>`, the deprecated
`x-frontcache-site-key` header is still accepted, and the value is the same string it was — so
**agents, consoles and peer nodes need no coordinated upgrade**. Only the property that configures
the node moved.

The concept was renamed everywhere it is spelled:

| Was | Now | Notes |
| --- | --- | --- |
| `front-cache.site-key` | `front-cache.api-key` | the node's own config. **No fallback** |
| `siteKey` in `frontcache-console.conf` | `apiKey` | the console **refuses to start** on the old name — HOCON's `getString` throws on a missing key |
| `frontcache-site-key.conf` on the classpath | `frontcache-api-key.conf` | read by `FrontCacheAgentCluster` / `FrontCacheCluster`. Silent if missed |
| `FC_SITE_KEY` | `FC_API_KEY` | Docker compose, `.env`, the console entrypoint |
| `org.frontcache.core.SiteKey` | `org.frontcache.core.ApiKey` | plus `FCUtils.isAuthorizedApiKeyHeader`, `FrontCacheEngine.isNodeApiKey` |

**Two spellings deliberately did not move**, because each is a fixed string that something *older*
sends, and renaming it would simply stop accepting it:

- the deprecated **`x-frontcache-site-key` header** — still accepted, still warning once per node;
- the retired per-domain **`front-cache.domain.<domain>.site-key`**, which exists only so a node can
  detect it in a pre-multi-domain-retirement file and refuse to start.

### Retired: `front-cache.management.port`

**Removed, with no replacement.** A leftover `front-cache.management.port=443` in your config is
ignored — the node does not complain, and nothing about its behaviour depends on the line any more.

It was never an access control. The check compared `request.getServerPort()`, which the Servlet
specification derives from the **Host header** — so any caller who could reach any connector could
send `Host: whatever:443` and satisfy it. It answered "which of this node's connectors should serve
management traffic", and that question belongs to your reverse proxy, which can actually enforce the
answer.

**`front-cache.api-key` is now the only thing guarding the management API, the dashboard stream and
`/fc-metrics`** — which is why the rename above matters as much as it does. If you were relying on
the port check for isolation, restrict `/frontcache-io`, `/fc-dashboard.stream` and `/fc-metrics` at
the proxy instead.

Two consequences:

- `org.frontcache.core.ManagementPort` and `org.frontcache.resilience.FcDashboardStreamSecurityServlet`
  are **deleted**. The latter existed only to apply this check to the SSE stream; both shipped
  `web.xml`s now name `org.frontcache.resilience.stream.FcDashboardStreamServlet` directly. A
  **customer `web.xml` still naming the old class fails at deploy** with `ClassNotFoundException`.
- **The documented health check still works, for a different reason.** `GET
  /frontcache-io?action=get-cache-state` locally still returns `200` with an *access denied* body —
  now because the request carries no API key rather than because it arrived on the wrong port. A
  `200` still proves Jetty, the webapp and the engine are up, and still needs no credential.

### Renamed: the `browser` client type is now `guest`

`FCHeaders.REQUEST_CLIENT_TYPE_BROWSER = "browser"` became
`FCHeaders.REQUEST_CLIENT_TYPE_GUEST = "guest"`. **The value moved, not just the constant** — and
that value is a contract in four places, none of which fails loudly:

| Where | Was | Now |
| --- | --- | --- |
| Include markup | `<fc:include client="browser">` | `client="guest"` |
| Component TTL | `maxage="browser:30d"` | `maxage="guest:30d"` |
| Guard predicate | `client-type:browser` | `client-type:guest` |
| Request log, last column | `browser` | `guest` |

An un-updated `client="browser"` attribute is ignored, as if absent. An un-updated `browser:` maxage
prefix now **caches for both client types** instead of one — the opposite of the split it asked for
— though it does log a warning naming the value and the two valid ones. An un-updated
`client-type:browser` guard rule simply stops matching.

> [!WARNING]
> **Flush the cache after upgrading** — `invalidate` with `filter=*`.
>
> `WebResponse` is stored in the L2 Lucene index as JSON, so **every entry already in your index**
> has `expireTimeMap` keys `{"bot", "browser"}`. Read back for client type `guest`, such an entry has
> no matching key: `FCUtils.isWebComponentCacheableForClientType` logs an error and returns false, so
> that URL calls the origin — and because the save path requires the same flag, **it is never
> re-cached**. It is not removed either, so the stale entry persists and the URL serves from origin
> indefinitely. One flush at upgrade time avoids all of it.

### Fixed: `maxage="guest:30d"` cached for bots too

Renaming the token surfaced a bug that had been in `WebResponse.setExpireTime` since it was written.
The prefix's whole purpose is the split — *this* TTL for that client type, and **not cacheable** for
the other, because a page worth caching for a crawler is often exactly the page you must not serve a
signed-in visitor from cache.

The second branch tested `REQUEST_CLIENT_TYPE_BOT` — the same constant as the branch above it — so
it was unreachable. A `guest:` prefix (a `browser:` prefix, before this release) fell through to the
no-prefix default and cached for **both** client types: a fragment marked for guests only was also
served to crawlers from cache.

**Nothing caught it because every maxage fixture in the repo, unit and e2e, used `bot:`.** The guest
half of the split had no coverage at all. It does now, at both levels — a unit test
for the parse, and end-to-end tests for a page and for a fragment inside one, each
asserting the half the defect inverted:
that a crawler is **not** served the entry a guest just cached.

The unrecognized-prefix branch also stopped being silent. Behaviour there is unchanged — an unknown
prefix still caches for both, since refusing would take pages out of cache on upgrade — but it now
logs a warning naming the offending value, which is what a page still saying `browser:` will produce.

## If you extend Frontcache in Java

**No interface changed.** `CacheProcessor`, `IncludeProcessor` and `FallbackResolver` are identical to
2.8.0, and so is `FcHttpClient`.

**Source-incompatible renames**, all of them compile errors rather than silent behaviour changes:

| 2.8.0 | 2.9.0 |
| --- | --- |
| `org.frontcache.core.SiteKey` | `org.frontcache.core.ApiKey` |
| `FCUtils.isAuthorizedSiteKeyHeader(request)` | `FCUtils.isAuthorizedApiKeyHeader(request)` |
| `FrontCacheEngine.isNodeSiteKey(String)` | `FrontCacheEngine.isNodeApiKey(String)` |
| `FCHeaders.REQUEST_CLIENT_TYPE_BROWSER` | `FCHeaders.REQUEST_CLIENT_TYPE_GUEST` (value `"browser"` → `"guest"`) |
| `org.frontcache.core.ManagementPort` | **deleted** — the check is retired |
| `org.frontcache.resilience.FcDashboardStreamSecurityServlet` | **deleted** — use `org.frontcache.resilience.stream.FcDashboardStreamServlet` |

`FrontCacheClient` / `FrontCacheAgent` constructors are **source-compatible**: only the parameter
*name* changed (`siteKey` → `apiKey`), which Java does not bind on. `AccessDeniedActionResponse` lost
its `AccessDeniedActionResponse(int port)` constructor along with the port it named; the JSON it
produces is unchanged in shape.

If you **subclass `IncludeProcessorBase`** — rather than implementing `IncludeProcessor` directly —
three `protected` methods gained one parameter, because an include now carries two URLs: the public
one it is keyed, logged and fallen back on, and the one that actually goes on the wire.

| Method | 2.8.0 | 2.9.0 |
| --- | --- | --- |
| `callInclude` | `(String urlStr, Map, FcHttpClient, RequestContext, String, String)` | `(String publicURL, String fetchURL, Map, FcHttpClient, RequestContext, String, String)` |
| `getIncludeFromCache` | `(String urlStr, Map, FcHttpClient, RequestContext, String, String, long)` | `(String publicURL, String fetchURL, Map, FcHttpClient, RequestContext, String, String, long)` |
| `fetchIncludeFromOrigin` | `(String urlStr, Map, FcHttpClient, RequestContext, String, String, long)` | `(String publicURL, String fetchURL, Map, FcHttpClient, RequestContext, String, String, long)` |

`getIncludeFromCache` uses `fetchURL` for exactly one thing — the soft refresh, which is a fetch.
Everything else in it keys, logs and serves on `publicURL`. **Never pass the fetch URL where the
public one belongs:** that rebases the cache key onto the origin host, orphaning every existing entry
and leaving two keys per fragment depending on which path filled it.

**If you override `init(Properties)`, call `super.init(properties)`** — that is what reads
`front-cache.include-fetch-target`. An override that does not will keep `origin`, the default, so
nothing silently changes transport either way.

## Bot classification: `conf/bots.conf` takes rules

`bots.conf` was a list of User-Agent substrings, and `FrontCacheEngine.getClientType()` was nine
lines: scan the header, first substring wins, no match means `guest`. It could not be reloaded
without restarting the node, and the one signal it read is the one signal entirely under the
caller's control.

It now takes **rules, in the guard-rules format**, alongside the bare keywords:

```
# name          | condition                                        | client type
partner-feed    | client-ip:203.0.113.7                             | guest
headless        | ua~(?i)(headlesschrome|phantomjs|puppeteer)       | bot
fake-googlebot  | ua~(?i)googlebot ; !client-ip:@bot-networks/googlebot.txt | bot
no-js-proof     | request-type:toplevel ; !cookie:hruc              | bot | dry-run

# bare lines still work, and still mean "User-Agent substring"
Googlebot
bingbot
```

Predicates are AND-ed with `;`, negated with `!`, and evaluated **top to bottom, first match wins** —
so a `guest` rule above a `bot` rule is an exemption, exactly as `allow` is in `guard-rules.conf`.
Available: `ua~<regex>`, `ua-contains:`, `client-ip:<cidr|@file>`, `cookie:`, `header:`, `uri~`,
`query~`, `url~`, `host~`, `host:ip`, `method:`, `request-type:`. `ua~`, `ua-contains:` and
`client-ip:` are new and work in `guard-rules.conf` too.

Two predicates are **refused** in `bots.conf`, each with a message naming the alternative:
`client-type:`, because classification is what computes the value it would read; and `rate:`,
because it counts, and classification runs for every request including every include — it would
spend a visitor's budget once per fragment of their page. Rate-based reactions belong in
`guard-rules.conf`, which reads the classification back through `client-type:`.

### What the client type is, and is not

It is **not** a judgement about the client, and nothing here rewards or punishes anyone. It selects
a **behaviour profile**, chosen per URL by whoever writes the page: a different TTL
(`maxage="bot:30d"` vs `maxage="guest:5m"`), a cached response vs. an origin call, whether an
`<fc:include client="...">` fragment is resolved at all. Guard rules read the same value through
`client-type:`, but that is one consumer among several and not the reason the classification exists.
So the question a rule answers is *"should this client get the cached page or a freshly rendered
one?"*, not *"is this client welcome?"*.

There are still exactly two values, and **there cannot be a third**. The client type keys the
`expireTimeMap` of every response already stored in the L2 index, so a new value would leave every
existing entry without a key for it — and an entry with no key for the current client type is never
served and never re-cached. That is the same mechanism that makes the `browser` → `guest` rename
elsewhere in this release a flush-the-cache upgrade.

### Bare keywords are now case-insensitive

The shipped file lists `Googlebot`; a crawler announcing `googlebot/2.1` was classified `guest`,
because the match was `String.contains()`. Nobody noticed, because the failure mode is a page
rendered fresh from origin rather than an error.

**This is a deliberate behaviour change with no compatibility flag.** After upgrading, a node
classifies as `bot` a small amount of crawler traffic it previously called `guest` — which is what
the file always meant. Nothing else observes the difference: the client type is not part of the
cache key, so **no entry moves and no flush is needed** for this.

If you really want a case-sensitive match, write it as a rule with an explicit regex and no `(?i)`:
`mycrawler | ua~MyCrawler | bot`.

### Per-rule hit counts, and a reload

`get-bots` now returns the rules in evaluation order, each with a hit count, and the console renders
them as a table — the Guard Rules screen with two columns renamed. That screen was **Configs / Bot
Config** in this release; it moved to a top-level **Visitor Types** tab afterwards, and
`/bot-configs` now shows the raw `bots.conf` instead. The counter semantics are the same ones:

- only the rule that **decided** counts; a rule shadowed by a broader one above it sits at zero,
  which is the most useful thing that column says;
- a `dry-run` rule counts and evaluation continues past it — measuring a rule before it acts is the
  point of dry-run;
- the built-in `default | (always) | guest` row counts the traffic no rule claimed, which is the
  denominator for reading every row above it;
- counters are in-memory and reset on restart and on reload.

Two rules that were hard-coded are now visible rows: `no-user-agent` (first; switch it off with
`front-cache.bots.empty-user-agent-is-bot=false`) and `default` (last).

**`action=reload-bots`** re-reads the file without a restart, beside `reload-guard-rules` and
`reload-fallbacks`. A line that fails to parse — bad regex, unknown predicate, unparseable CIDR, a
missing `@file` — is skipped with an ERROR and every other line keeps working.

`botKeywords` still means exactly what it did (the bare keyword lines, nothing else) and the new
`botRules` arrives beside it, so a console older than this release renders the list it knows and a
newer console reading an older edge falls back to the same list.

### `client-ip:` and the trusted-proxy list

`client-ip:` resolves through `ClientIpResolver` — **not** `FCUtils.getClientIP()`, which believes
thirteen client-supplied headers. If it read that, a client could put itself inside any block the
file names, including a `guest` exemption, by sending one header.

The consequence is that `front-cache.client-ip.trusted-proxies` matters here for the same reason it
matters for rate limiting: with it empty (the default), only the socket peer is visible, so behind
nginx or a CDN every `client-ip:` rule sees the proxy's address for every request. The node WARNs at
startup when a `client-ip:` rule is loaded and the list is empty.

`@file` handles published crawler ranges: `client-ip:@bot-networks/googlebot.txt` reads one address
or CIDR per line from a file under `conf/`, so an ops cron job can refresh the vendor's ranges
without touching the rules file.

### Includes are classified with their page, not against it

An `<fc:include>` that re-enters Frontcache is a separate request, and would be classified on its
own evidence — which is not the page's evidence. Its socket peer is the sibling node rather than the
visitor, and an async include is resolved after the servlet request has been recycled, so it may see
no cookies at all. A User-Agent-only file agreed by accident (the UA survives the hop); a rule
reading cookies or the client IP does not. Page and fragment would then read different branches of
the same `expireTimeMap`, and the fragments would quietly stop being cached — with nothing in the
log but a client-type column that disagrees between the two lines.

So the node serving the page sends its decision on the include fetch, as
**`X-Frontcache-Client-Type`**, and the receiving node adopts it instead of classifying. Three
conditions, all required:

- the socket peer is in `front-cache.client-ip.trusted-proxies`;
- the request arrived as an include (a top-level request is a client's, whoever relayed it);
- the value is `bot` or `guest` — anything else is ignored with a WARN rather than stored.

**With no trusted proxies configured — the default — nothing is ever adopted** and every request is
classified on its own, so keep `request-type:toplevel` on any rule that reads cookies or the client
IP until you set that list. If the proxy you trust passes client headers through verbatim (nginx
does, by default), have it **strip `X-Frontcache-Client-Type`** — as it should already be stripping
`X-Frontcache-Client-IP`. Frontcache does its half: an inbound value is dropped rather than relayed
onward with our own address as the peer.

Adopted requests are decided before the rules run, so no rule counts a hit for them. That is the
intended accounting, not a gap — the same reasoning as the rate limiter's `scope=toplevel`: the
visitor was classified once, when their page was requested, and counting their fragments would count
that visitor again once per fragment.

### Considered and dropped: reverse-DNS verification

Forward-confirmed reverse DNS is the only signal that truly *verifies* a crawler, and it is the only
one that would need a DNS cache, a background executor, two TTLs and a rule semantic for "the answer
is not known yet" — all of which must be right before the first request benefits.
`client-ip:@bot-networks/googlebot.txt` catches the same impostors with a byte-prefix compare and no
network call anywhere near a request. Dropped, with no stub, no unused cache and no property left
behind; the design is recorded in the proposal if the measurement ever says otherwise.

### What to do

Nothing, to keep working: an existing `bots.conf` parses unchanged, and the only behaviour change is
the case-insensitive keyword match described above. When you want more:

- add rules, always `dry-run` first, and read the hit counts on the console's Bot Config screen
  (**Visitor Types** in a console newer than this release) before letting one decide anything;
- set `front-cache.client-ip.trusted-proxies` before writing a `client-ip:` rule — and before
  relying on client-type propagation to includes, which is off until you do;
- keep `request-type:toplevel` on any rule reading cookies or the client IP;
- `front-cache.bots.rules.enabled=false` falls back to bare keywords only, if a rule set ever needs
  taking out of service without editing the file.

The predicate vocabulary is shared with guard rules — see
[guard-getting-started.md](../guard-getting-started.md) for each predicate in full.

## A TTL per visitor type

`maxage` could say "cache this for bots", or "cache this for guests", or "cache this for everyone".
It could not say **"30 days for bots and 1 day for guests"**. Naming a prefix forced the *other*
visitor type to no-cache:

```jsp
<fc:component maxage="1d" />        <%-- crawlers re-render the long tail daily --%>
<fc:component maxage="bot:30d" />   <%-- and now no human search result is cached at all --%>
```

A search-results page wants neither. Crawlers hit thousands of them and would happily take a
month-old copy; a person should not see one older than a day. Now it can say so:

```jsp
<fc:component maxage="bot:30d, guest:1d" tags="search-regular|en" />
```

The rule is one line, and the old forms are the same rule with one entry: **a visitor type the
value does not name is not cached.** `bot:30d` was never a special form — it is a one-entry list.

| value | bot | guest |
| --- | --- | --- |
| `1d` | 1d | 1d |
| `bot:30d` | 30d | not cached |
| `guest:5m` | not cached | 5m |
| `bot:30d, guest:1d` | 30d | 1d |
| `bot:forever, guest:1h` | forever | 1h |

Whitespace around the commas and colons is yours. `bot:30d, bot:1h` warns and the first wins, the
same first-match-wins as `guard-rules.conf` and `bots.conf`. An unknown visitor type **inside a
list** (`bot:30d, browser:1d`) warns and is ignored, leaving the type it meant uncached — different
from an unknown prefix as the *whole* value (`browser:30d`), which still caches for both, because
that is what an un-updated page produces and narrowing it would take pages out of cache on upgrade.

### What the split actually means

Read this before you set one, because the obvious reading is wrong on most pages.

**The cache key has no visitor-type dimension.** There is one cached copy carrying two expiration
stamps, and whichever visitor type re-renders it resets both. So:

> **The shortest TTL sets how often your origin renders. The longer ones say which visitor types
> never have to trigger a render.**

On a page with steady human traffic, crawlers get content no older than the guest TTL and contribute
**zero** origin renders — they ride along on the copy the humans already paid for. On a long-tail
page with no human traffic, which is the SEO case the feature exists for, nothing resets the entry
and it genuinely ages to the full bot TTL.

That is better than either thing you could write before: `1d` gives the same freshness and lets
crawlers force a daily re-render of every long-tail page; `bot:30d` fixes that and takes every human
search off the cache. The split is the only one of the three where origin renders scale with human
traffic and crawler traffic is free.

### One bug this exposed, fixed here

When an entry expired, the node deleted it — on the strength of an assumption that had always held:
when two visitor types had different expirations, one of them was no-cache, and a no-cache type
never reaches the expiry check at all. With two live TTLs it does. A guest arriving at T+25h was
deleting the copy that stayed valid for crawlers for another 29 days.

Usually invisible, because the next lines call the origin and put the entry straight back. Not
invisible when the write back is refused — **a fallback served because the origin is down**, a 5xx,
an empty body. Then the entry is simply gone and every crawler goes to the dead origin, because one
human visitor happened to arrive during the outage.

An entry is now deleted only once **no** visitor type can still be served from it — the same
`max(T_bot, T_guest)` the time-based purge already used. Both the top-level path and the include
path carry the check.

### Upgrading

**No flush for this one**, and no wire-format change: no new `expireTimeMap` key, so entries written
by an older node read correctly on a new one and the other way round. (2.9.0 asks you to flush once
anyway, for the `browser` → `guest` rename — that covers it.)

**Nodes before pages.** A page emitting `bot:30d, guest:1d` to a node older than this release splits
on the first colon, tries to parse `30d, guest:1d` as a duration, fails, and caches the page for
**neither** type. It fails safe — nothing wrong is ever served — but the page drops out of cache,
and on a partially-upgraded fleet that shows up as an origin-load spike on exactly the pages you
were trying to help. Relatedly, an unparseable `maxage` is now logged at `WARN` rather than `INFO`;
it was always a config error and it always failed by taking the page out of cache.

`maxage` remains a literal attribute (`rtexprvalue` false), so a page cannot choose its split per
request. That is deliberate: with one shared entry, an origin that emitted `bot:30d` to crawlers and
`guest:1d` to everyone else would thrash — each write sets the other type to no-cache, so the page
re-renders on every alternation, which is strictly worse than not caching it.

The `maxage` attribute and the rest of the include syntax are in
[jsp-tags.md](../jsp-tags.md).

## The console authenticates now

The console had **no authentication at all**. That was not a theoretical gap: anyone who could
reach `:7080` could empty the cache of every node in the fleet, dump keys, start a replication run,
add or remove edges, and read every config file the fleet holds. The nodes are protected by
`front-cache.api-key` — **the console holds that key and spends it on the caller's behalf**, so an
unauthenticated console was a credentialed proxy in front of an authenticated fleet.

One user, no roles, in the file the console already reads:

```hocon
frontcache {
    console {
        urls = ["https://fc-us.example.com:443/", "https://fc-eu.example.com:443/"]
        apiKey = your-api-key

        user     = admin
        password = admin      # CHANGE THIS
    }
}
```

Everything is behind it: the screens, `/edges-status.json`, the SSE relay at
`/fc-dashboard-proxy.stream`, and the static assets.

### There is a login page, and a Sign out

A browser signs in on the console's own page — logo, two fields, one error message — and carries a
session afterwards. It replaces the browser's native credential dialog, which is what the first cut
of this feature used, and it brings the one thing HTTP Basic cannot have: **Sign out**, top right of
every screen beside the user name.

**The credential did not change.** Same single `user`/`password` in the same file, same comparison,
same rules below for a console that has neither. What changed is the screen in front of it.

**`curl` and anything already automated keep working, unchanged.** HTTP Basic is still accepted on
every request, so a script, a healthcheck or a `curl -u admin:… http://console:7080/realtime` behaves
exactly as before. What changed is the *refusal*: a signed-out **page navigation** now gets a `302`
to `/login`, while everything else still gets the `401` with `WWW-Authenticate` it always got. (A
`WWW-Authenticate` sent to a browser navigation would open the native dialog on top of the new page,
which is the whole thing the page exists to replace.)

Details worth knowing before you upgrade a console:

| | |
|---|---|
| Session | In memory, 8-hour timeout, cookie `FCSESSIONID` (`HttpOnly`, `SameSite=Lax`, cookie-only — never in a URL). **Restarting the console signs everyone out**, which is how a changed password takes effect. |
| `session-cookie-secure` | New, default `false`. Adds `Secure` to the session cookie. **Set it when the console is reached over HTTPS**, including through a TLS-terminating proxy — the console cannot detect that for itself, and the attribute is fixed at startup. Left off behind HTTPS the cookie is merely not protected; turned on behind plain HTTP the login page accepts the password and comes straight back, because the cookie is never sent. |
| A left-open dashboard | The realtime page keeps its own session alive through the 10-second edge poll — but that poll **skips while the tab is hidden**, so a console parked in a background tab does expire, and the next click goes to the login page. |
| An expired session | The page notices and goes to the login screen, remembering where it was. Previously a stale-credential state left the dashboard showing "retrying …" indefinitely. |
| Sign out | `POST` only, and session-only. A caller sending Basic on every request has nothing to end. |
| A non-ASCII password | Now works through the form as well as through Basic — the console had no request-encoding filter, so a form POST decoded as ISO-8859-1. The same fix stops the Configs editor writing mojibake to a node's disk. |

Nothing to do on upgrade beyond deciding about `session-cookie-secure`. What the console is and
how to run it: [console-dashboards.md](../console-dashboards.md).

### No credentials means the console still runs, loudly

**A `frontcache-console.conf` written before this release has neither key, and that console keeps
serving.** It is a monitoring tool; a version of it that refuses to start until someone finds and
edits a file would be at its worst exactly when it is needed, and the thing it protects was already
reachable five minutes ago.

What you get instead is a line on every startup — at `WARN`, because the shipped `fc-logback.xml`
drops `info` from stdout and an unprotected console must not be a silent one:

```
WARN  Console authentication is OFF - no 'user'/'password' in frontcache-console.conf.
      Anyone who can reach this port can invalidate the cache of every configured node.
```

and, on a fresh bundle that still has the shipped password:

```
WARN  Console authentication is ON, but the password is still the shipped default.
      Change 'password' in frontcache-console.conf.
```

A correctly configured console prints **nothing** about authentication. Silence means protected.

One state is a startup failure rather than a warning: `user` set without `password`, or the reverse,
or either one empty. That cannot come from an un-migrated file — only from a typo — and resolving a
typo to "unprotected" is the worst available answer.

| `frontcache-console.conf` | result |
|---|---|
| neither key (every config predating this release) | runs, unauthenticated, `WARN` every start |
| both keys, password changed | authenticated, silent |
| both keys, password still `admin` | authenticated, `WARN` every start |
| one key without the other, or either empty | **refuses to start**, naming the missing one |
| neither key **and** `auth-required = true` | **refuses to start** |

### What it does not fix

A login is not a network boundary. The session cookie is a bearer token, and on the Basic path —
which `curl`, the container healthcheck and any existing script still use — the password crosses the
wire on every request, base64-encoded, which is encoding, not encryption. **This makes the console
safe to leave running; it does not make it safe to publish.** Terminate TLS in front of it, or keep
it internal.

There is deliberately no lockout or throttle on the login form. A `sleep` on a failed attempt pins a
container thread per attempt, so a scanner would take the console down with it; a per-IP counter has
no IP it can trust behind a proxy. The comparison is constant-time and the guidance stays "do not
publish this port".

For more than one operator, an authenticating reverse proxy remains the better answer: one shared
password has no accountability — nothing in a log can say *who* flushed the cache — and no
revocation short of changing it for everybody.

What this does and does not protect, alongside the node's own api key:
[security.md](../security.md).

## Console: cross-origin state changes are rejected

Turning authentication on is what makes CSRF **reachable**: the browser attaches cached Basic
credentials to a cross-site request by itself, and they are not cookies, so `SameSite` does not
apply. A page an authenticated operator had open in another tab could have made their browser
invalidate the fleet's cache.

Two changes, no token store:

- **`add-edge` and `remove-edge` are `POST`.** They changed console state over `GET`, which made them
  reachable from any page — an `<img src="…/remove-edge?edge=…">` would have been enough. The
  console's own UI submits forms now; a `GET` returns **405**.
- **A state-changing request whose `Origin`/`Referer` is present and cross-origin is rejected with
  403.** Authentication runs first, so an unauthenticated caller gets a 401 and learns nothing about
  the second check.

**A request with neither header is allowed** — `curl` sends neither, and an operator's script has to
keep working. This stops a browser being used as a confused deputy and stops nothing else. The
scheme is deliberately not compared either: a console behind a TLS-terminating proxy sees `http`
while the browser sends `https`, and comparing schemes would reject every state change on exactly
the deployments careful enough to use TLS.

## Console: the config screens are editable

Every **Configs** tab has an **Edit** button to the right of the edge tab strip. It makes the text
area editable and reveals **Save to `<node>`**, **Save to all `<n>` nodes** and **Cancel**. Save
writes the file on that node and applies it, without a restart.

Still the raw file, and still a text area: a commented-out rule and a line the parser skipped are
visible in the file and invisible in any table of entries, which is the whole reason these screens
render the file. A form-based editor would have lost that.

| tab | writes | applied by |
|---|---|---|
| Fallback Config | `conf/fallbacks.conf` | `reload-fallbacks` |
| Bot Configs | `conf/bots.conf` | `reload-bots` |
| Dynamic URLs Config | `conf/dynamic-urls.conf` | `reload-dynamic-urls` **(new)** |
| Resilience Configs | `conf/resilience.properties` | `reload-resilience` **(new)** |
| Guard Configs | `conf/guard-rules.conf` | `reload-guard-rules` |

`conf/frontcache.properties` is **not** editable, and that is deliberate: it holds
`front-cache.api-key`, so a console editing it could lock itself out of the node it is editing;
`FCConfig` has no live re-read, so "applied" would mean a restart; and a typo in it is a node that
does not serve.

### It is refused before it is written

A save is dry-parsed first, and **one bad line refuses the whole file** — nothing is written, and
every bad line comes back with its line number:

```
bots.conf was NOT written - 1 line(s) cannot be used
line 133: 'browser' is not a client type in 'broken-verdict | ua~x | browser'
          - expected 'bot' or 'guest' ('browser' was renamed to 'guest' in 2.9.0)
```

Each of these loaders is deliberately tolerant — a line it cannot use is logged and skipped, and the
rest of the file keeps working. That is right at startup and wrong as the only feedback a Save button
gives, because the result is a node running configuration that does not match its own config file.
The cost of not knowing is on record: `|` being both the field separator and regex alternation left
[5 of 19 guard rules dead](#guard-rules--is-both-the-field-separator-and-regex-alternation) on a
production node, and nothing said so.

One consequence worth knowing: a file that **already** contains a bad line cannot be saved until that
line is fixed too. The message names it.

### Two nodes cannot silently overwrite each other

The console sends a hash of the text it rendered; the node refuses the write if the file changed
since, and hands back what is on disk so you can see what you were about to overwrite. On a
plain-`http` console that is not on `localhost` the browser has no `crypto.subtle`, so the check is
skipped — and the result line says so rather than implying it happened.

### Before it writes

- The previous content is copied to `conf/<file>.backup-<yyyyMMdd_HHmmss>`, the naming
  `backup-index` already uses. The newest 10 per file are kept.
- The replace is atomic (temp file in the same directory, then a rename). A half-written
  `guard-rules.conf` is a node with no guard rules.
- Submitted CRLF is normalized to LF. HTML form submission converts a text area's line breaks to
  CRLF, so without this the first Save — **with no edit at all** — would rewrite every line ending in
  the file. A trailing newline is deliberately *not* added, for the same reason: saving must not
  change a byte you did not change.

### Two things `reload-resilience` cannot do quietly

`conf/resilience.properties` had no live reload at all before this: it is read once into a cached
singleton, and the Resilience4j objects and thread pools built from it are cached again. Command
settings — timeouts, breaker thresholds, sleep windows, bulkhead permits, the legacy `hystrix.*`
prefixes and the key-inheritance chain — all come back. Two things do not, and both are reported in
the result rather than left to be inferred:

- **Circuit state is reset.** An open breaker closes and every rolling window restarts at zero, so
  the realtime page shows a step change. A breaker whose configuration just changed has no
  meaningful history anyway.
- **A changed thread-pool `maxQueueSize` is not applied.** It selects the queue *type* at
  construction — below 1 means a queue that rejects instead of buffering — and a running executor's
  queue cannot be replaced. `coreSize`, `maximumSize` and `keepAliveMinutes` *are* applied in place,
  on the same executor, so in-flight origin calls are not disturbed.

### Save to all nodes asks first

It writes the same text to every configured edge, one at a time, and reports **per node** — each is
a separate machine, so a partial result is the normal outcome. It confirms first, because config
files legitimately differ between nodes: this project's own e2e fleet keeps one node on the
pre-2.9.0 resilience key names and a bare-keyword `bots.conf` on purpose, and "Save to all nodes"
would flatten exactly that.

### Who may write

Both ends check, and both refuse by default in the state an un-migrated config file produces:

| | |
|---|---|
| **The node** | `set-config` refuses unless `front-cache.api-key` is set — stricter than every other management action, which serves an un-keyed node openly. An un-keyed node is usually un-keyed by accident (an upgrade that left `front-cache.site-key` in the file), and remote configuration of how a node handles requests is not what that mistake should enable. `front-cache.management.config-write=false` turns writes off outright. |
| **The console** | No `user`/`password` means no Edit button, whatever `config-editing` says. An unauthenticated console is readable by anyone who can reach the port; it must not also be a fleet configuration tool. |

There is one console login and no roles, so "who changed this file" is answerable only from the
node's log line — it logs the file, the byte count and the backup name on every write. Per-operator
attribution is a reverse proxy in front of the console, which is already the console's answer to
having more than one operator.

`POST /save-config`, so it falls under
[`SameOriginFilter`](#console-cross-origin-state-changes-are-rejected) — the most consequential POST
the console has.

### Also fixed here: two edges on one host shared a tab

The Configs screens collected their per-edge fan-out into a map keyed by the edge's display name, and
that name is the URL with the scheme and everything from the first colon stripped off. So
`localhost:8080` and `localhost:9080` were both `localhost`, and **one of the two tabs silently
disappeared from the page.** Read-only that cost a tab; with a Save button on it, an edit addressed
by name would have gone to whichever edge won. Edges are identified by URL now, and every write is
addressed by URL.

The five near-identical controllers, JSPs, model classes and callers behind these screens are one of
each. All five URLs are unchanged, `/hystrix-configs` included.

## Upgrading

**Do these before starting the node — none of them warns you if you skip it:**

1. In every `frontcache.properties`, rename `front-cache.site-key` to `front-cache.api-key`, and
   delete `front-cache.management.port` if present.
2. In `frontcache-console.conf`, rename `siteKey` to `apiKey`. (The console will tell you — it
   refuses to start otherwise.)
3. Grep your pages and `guard-rules.conf` for the `browser` client type — `client="browser"`,
   `maxage="browser:..."`, `client-type:browser` — and change it to `guest`.
4. If a `web.xml` of yours names `FcDashboardStreamSecurityServlet`, point it at
   `org.frontcache.resilience.stream.FcDashboardStreamServlet`.
5. Set `front-cache.default-domain` to your public hostname, and `front-cache.public-scheme=https`
   if a TLS terminator fronts the node — otherwise guard-rule `${url}` keeps emitting the host and
   scheme the request arrived under.
6. If `conf/` still has a `hystrix.properties` and no `resilience.properties`, **rename it**. The
   keys inside need no change. (The installer and the Docker seeder do this for you.)
7. In `frontcache-console.conf`, add `user` and `password` — or decide deliberately not to, and
   expect the "authentication is OFF" warning at every console start. On a fresh bundle, change the
   shipped `admin`/`admin`.

**Then:**

8. Replace the artifact.
9. **Flush the cache once:** `invalidate` with `filter=*`. Entries written before the upgrade key
   their TTLs on the old client type and will otherwise never be re-cached.
10. Confirm the management API still answers with your key, and that a request *without* it is
   refused — that is the check that catches a missed step 1.
11. Load the console once and confirm it asks for the password you set — that is the check that
    catches a missed step 7.
12. If you use guard rules with alternations, compare `get-guard-rules` before and after — the count
   should go up, and those rules will start firing.
13. Repoint any monitor, Grafana query or alert naming a renamed command key — `Input-Requests`,
   `Include-Requests`, `Cache-Hits`, `Origin-Hits`, `Cache-Origin-http`, `Cache-Origin-filter` — or
   the renamed pool `OriginHitsPool`, and add `Include-Request` beside `Input-Request`.
14. Update `resilience.properties` to the new command and pool keys when convenient. Deciding
    `Cache-Miss` is the one that needs a thought on a filter-mode node.
15. Watch the include hit rate. It should rise, and origin traffic should fall.
16. If includes misbehave, set `front-cache.include-fetch-target=edge` and reload — that restores
    2.8.0 behaviour exactly, with no code rollback.
17. Look at the console's **Visitor Types** screen once. Bare keywords now match case-insensitively,
    so a little crawler traffic moves from `guest` to `bot`; the hit counts tell you how much, and
    which keywords are earning their place. No cache flush is needed for this one.
18. Fix anything scripted against `add-edge` / `remove-edge`: they are `POST` now.
19. Only once every node is upgraded, start using `maxage="bot:30d, guest:1d"` on pages that want a
    different TTL per visitor type. Nodes first — a pre-2.9.0 node cannot parse it and drops the
    page out of cache. No extra flush; step 9 covers it.
20. Decide who may edit config from the console, before anyone finds the Edit button. On a node
    whose `conf/` comes from git, Ansible or an image, set
    `front-cache.management.config-write=false`. On a console that should stay read-only, set
    `config-editing = false`. And on any node still without `front-cache.api-key`, set one — that is
    the only management action which refuses an un-keyed node.
21. If you use the console's Save, upgrade the nodes before you rely on it. A node that predates it
    answers a ping; the console reports that as a refusal naming the file, so nothing is lost — but
    the save did not happen.

**Verified:** `frontcache-core` 687 unit tests, `frontcache-console` 105, and the 195-test
end-to-end suite, all green, on the shipped defaults and again with the escape hatch set. The two
client-type regressions were confirmed
to fail without their fix, in both standalone and filter mode. The visitor-type TTL split is pinned
on both paths that can evict an entry — one per path,
each confirmed to fail with its own fix reverted, since the e2e suite structurally cannot catch this
one: there the origin is up, so a wrongly deleted entry is put straight back by the refetch. The command-key rename inheritance is
covered end-to-end as well as in unit tests: the e2e filter node's `resilience.properties` is
deliberately left on the pre-2.9.0 key names, so the suite fails if that fallback ever regresses. The
same trick now covers the bots.conf format: the e2e standalone node's file uses the rule format while
the filter node's is left bare-keyword-only. The three new raw-config actions are asserted on both
e2e nodes to return the file — comments intact — rather than the parsed view.

The console's authentication was exercised against a live node: 401 with no credentials and the
correct challenge, 200 with them, 401 on a wrong password, 401 on the static assets and the SSE
relay, 403 on a cross-origin POST, 405 on the old `GET /remove-edge`, and real SSE frames relayed
through both filters — which is the one that matters, since a filter missing `async-supported`
breaks the realtime page and nothing else. The unit tests pin that a config file with no
`user`/`password` parses to "no authentication" rather than throwing, which is the upgrade path.

Editing a config from the console was driven through a real browser against a live node, because the
two failure modes that matter are only reachable that way. Saving a file **unchanged** through the
actual form leaves it byte-for-byte identical with no CR bytes introduced and no backup taken — the
CRLF trap, which no unit test can reach because it is form submission that converts the line
endings. And a file changed on disk behind an open tab refuses the save and hands back what is on
disk, rather than overwriting it. A bad `client-type` was refused with its line number, and the
happy path was confirmed on disk and in the node's reloaded rules. On the e2e side both node types
run the round trip, the refusal, the conflict, and the two new reloads; the round-trip test uses
`bots.conf` because the standalone node's copy **ends without a trailing newline**, which is the
case a helpful normalizer would break.
