# Frontcache 2.11.0-RC — release note

Docs index: [../doc-index.md](../doc-index.md) · All release notes: [README.md](README.md)

Everything that has landed since 2.10.0:

- **A second-layer node can refuse traffic that skipped its edge.** In a chained deployment
  (browser → edge → second layer → app) the second layer is usually reachable some other way as well,
  and what comes in that way skips every guard rule and rate limit on the edge. A new shared secret,
  `front-cache.edge-token`, is sent by every node on its origin calls. A new guard predicate,
  `edge-token`, tells the next node whether a request carried it. Off unless configured. See
  [the edge token](#the-edge-token-only-my-edge-may-call-me).
- **Fixed: a guard redirect could not send a request to the same path on another host.**
  `redirect:301 https://www.example.com${uri}${query}` was refused at load. The parser read
  everything up to the first `/` as the host, placeholders included. See
  [the redirect fix](#fixed-a-placeholder-right-after-the-host-in-a-redirect-target).
- **Fixed: `action=reload` took the node down.** It left the node with no configuration and no engine,
  so every later request failed until a restart. It now rebuilds the engine as it was meant to. See
  [the reload fix](#fixed-actionreload-took-the-node-down).
- **Frontcache is open source: Apache-2.0, source included.** The product source is now public, in the
  same repository as the documentation. `LICENSE` is the full Apache License 2.0 text (it was a link),
  and every bundle, jar and image now also carries a `NOTICE`; each bundle carries
  `THIRD-PARTY-NOTICES.txt`, listing every library in it with its licenses and notices. The Maven POMs
  name `Apache-2.0`. See [Community is Apache-2.0](#community-is-apache-20).
- **The cache warmer and the console's cluster request rate are no longer in the Community bundles.**
  They moved to Frontcache Pro: separate, commercially licensed modules that plug into a node and
  a console. **Both shipped free in 2.10.0, so for a Community installation this is a removal**: see
  [What to do](#what-to-do) and [What left the Community bundles](#what-left-the-community-bundles).
- **Metrics export stays in Community.** Prometheus / OTLP export (`/fc-metrics`) is part of every
  bundle, as it has been since 2.6.0.

Nothing existing changed on the wire or in a config file, and there is no cache flush. A node with no
`front-cache.edge-token` sends nothing new and accepts nothing new. The node answers the `warmer-*`
actions with a ping, as a node that predates them does. See [Upgrading](#upgrading).

## The edge token: only my edge may call me

### What it is for

In one production chain the second layer took **71%** of its top-level traffic from clients that
had never passed through the edge. They reached it under the public hostname the edge itself uses to
reach the origin, and nothing on the wire set that traffic apart:

- the edge's `x-frontcache-request-id` can be forged, and is absent on its bypassed calls (POSTs,
  `dynamic-urls.conf` matches);
- `X-Forwarded-Host` can be forged;
- an IP allowlist depends on addresses that change. The one in that deployment's own docs was
  already stale.

### How it works

```properties
# frontcache.properties - THE SAME VALUE on every node of the chain
front-cache.edge-token=<a long random value, e.g. openssl rand -hex 32>
# optional, during a rotation: also accepted, never sent
front-cache.edge-token.previous=<the old value>
```

- **Sent** as `x-frontcache-edge-token` on every call the node makes **to its
  `front-cache.origin-host`**: page misses, include fetches, soft refreshes, bypassed requests, and a
  `fallbacks.conf` init URL that names the origin.
  - It is **never** sent to another host. With `include-fetch-target=edge`, an absolute
    `<fc:include>` and a fallback init URL can point anywhere, and a shared secret must not follow
    them there.
- **Never relayed.** A node drops an inbound `x-frontcache-edge-token` and sends its own, so a
  client's copy stops at the first Frontcache it reaches.
  - In filter mode the app itself still sees the raw request, header included.
- **Checked once per request**, constant-time, against the current and the previous value. The
  result is the `edge-token` guard predicate.

One token per chain, sent and accepted by every node, is the whole model. There is no direction to
configure, and a compromised node is answered by rotating the token.

### The rules

On the second layer, in `guard-rules.conf`, below your exemptions:

```
direct-get   | !edge-token ; method:GET | redirect:301 https://www.example.com${uri}${query}
direct-other | !edge-token              | reject:403 Use https://www.example.com
```

- `method:GET` on the redirect is required, not decoration:
  - a 301 makes a browser re-send a POST as a GET;
  - without it the load-time loop check refuses the rule. It cannot know the redirected request will
    come back through the edge carrying the token, so it reads it as a rule that redirects to a URL
    its own condition matches.
- The redirect target needs its host in `front-cache.guard-rules.allowed-redirect-hosts`, or set as
  `front-cache.default-domain`.
- Anything that legitimately reaches the second layer without passing through the edge (a GSLB
  health check on `/fc-ping.jsp`, the console or agent on `/frontcache-io`, the dashboard stream, a
  Prometheus scrape) needs an `allow` rule **above** these. The node warns at startup when one is
  missing, as it does for any rule.
- `edge-token` is **refused**, so the rule is skipped with an `ERROR` like any unparseable rule, in
  three cases:
  - **on a node with no token**: `!edge-token` would match every request, and a redirect of every
    request to the public host is a loop through the edge. The console's Save refuses such a file
    for the same reason;
  - **in `bots.conf`**: the token identifies the hop, not the visitor;
  - **with an argument**: it is written `edge-token` or `!edge-token`, nothing else.

### Rolling it out

1. Set `front-cache.edge-token` on the **second layer** and restart it. Nothing is enforced yet.
2. Set the same value on **every edge** and restart them. Each now sends it. An edge not yet
   restarted just sends nothing, which is harmless while no rule enforces.
3. Add the two rules on the second layer **with `| dry-run`**, then reload
   (`action=reload-guard-rules`, or Save on the console).
4. Watch the Hits column on the console's **Guard** tab for the second layer, and
   `frontcache-failed-requests.log` (`direct-get:dry-run`). Hits should be the direct traffic only. If
   they track the node's whole `Input-Request`, an edge is not sending the token. Do not go on.
5. Drop `| dry-run`. The second layer's `Input-Request` falls to what its edges forward. Refused and
   redirected requests return before the command and are not counted in it.

**Rotating:** set the new value as `front-cache.edge-token` and the old one as
`front-cache.edge-token.previous` on the second layer first, then move every edge to the new value,
then remove `.previous`.

The startup log says what a node does with the token, and never what the token is:

```
Edge token configured: sent as x-frontcache-edge-token on every origin call, and accepted on inbound requests (guard-rules.conf predicate 'edge-token')
```

A token shorter than 32 characters is warned about, not refused.

### What it does not do

- **It only guards what reaches Frontcache.** A filter-mode second layer sees only the URLs its
  filter is mapped to. Anything else on that host (static locations, other servlets) needs the same
  restriction at the reverse proxy or the CDN (with nginx behind Cloudflare, keyed on
  `CF-Connecting-IP`).
- **It is as private as the hops it crosses.** A plaintext hop between an edge and its origin carries
  the token in the clear, as it carries visitors' cookies.

## Fixed: a placeholder right after the host in a redirect target

```
redirect:301 https://www.example.com${uri}${query}
```

is the natural way to send a request to the same path on another host. It was refused at load with
`redirect target host 'www.example.com${uri}${query}' is not allowed`, because
`GuardRuleParser.checkRedirectTarget` took everything up to the first `/`, `?` or `#` as the host. A
`${` now ends the host too, since no hostname contains one.

Nothing is loosened: the host before the placeholder must still be allowed, and
`GuardRuleEngine.sanitizeTarget` still re-checks the host of the **expanded** target on every
request. A target whose entire host is a placeholder (`https://${host}/…`) is still refused at load,
since there is no host to check there.

## Fixed: `action=reload` took the node down

The `reload` management action destroys the engine and builds a new one. Destroying it also cleared
the node's `frontcache.properties` and `dynamic-urls.conf` from memory, and nothing re-reads them. Both
files are read once, at startup. So the rebuild failed with a `NullPointerException`, the action
returned an error, and the node was left with no engine: every request after that tried to build one
and failed the same way, until a restart.

The same teardown also closed the cache and the include processor: the in-memory L1 cache, the Lucene
writer, and the thread pools for soft refreshes and includes. The new engine would have been handed
those same closed objects, because they are shared by the whole process. This could not happen while
the first failure stopped the rebuild, but fixing only the first failure would have left a node that
answered requests on top of a cache that no longer worked. Both are fixed:

- a reload no longer clears the configuration;
- a reload keeps the cache and include processors, and only a shutdown closes them. They are built from
  `frontcache.properties`, which a reload does not re-read, so rebuilding them would apply nothing, and
  the L1 cache now survives a reload.

**What `reload` re-reads is unchanged:** `guard-rules.conf`, `fallbacks.conf` and `bots.conf`, and it
rebuilds the HTTP client. To apply a change to `frontcache.properties`, restart the node. For
`dynamic-urls.conf` there is `action=reload-dynamic-urls`, and for `resilience.properties`
`action=reload-resilience`.

## What left the Community bundles

The cache warmer's orchestration and the console's cluster request rate moved out of the Community
bundles into Frontcache Pro, which is commercially licensed. Pro is a set of jars that plug into a
Community node and console through two interfaces found with `java.util.ServiceLoader`:
`org.frontcache.module.FrontcacheModule` on a node, `org.frontcache.console.plugin.ConsolePlugin` in the
console. Both interfaces are in the Apache-2.0 core, and the build refuses a Community bundle that
carries a Pro class.

On a node and console with no plug-in, which is every Community installation:

| | Community |
|---|---|
| `warmer-*` | answer a ping — the "unknown action" answer every older node gives |
| `get-node-stats` | `modules: []` |
| `/fc-metrics` | serves, with no `frontcache_warmer_*` series |
| the console | no Cache Warmer entry, no cluster line; a `clusters`, `cache-warmer` or `usage-dir` key in `frontcache-console.conf` is ignored with one `WARN` at startup |

What an operator can also observe:

- A module can never stop a node: one that fails to load or to start is logged at `ERROR` and the node
  starts without it. Its management actions then answer with a ping, as on a node that predates them.
  A console plugin that fails to load is likewise logged, and the console starts without it.
- A module cannot take over a management action the core answers, and a console plugin cannot add a page
  that skips sign-in: its screens sit behind the same filters as every other.

The request path does not go through the module interface at all: the warm-request handling the warmer
relies on (`x-frontcache-warm*`, the synchronous refresh) stays in the core, so a node serves the same
bytes with or without a plug-in — and `warmer/warmer.sh` works on Community. The console's single-user
sign-in, the management API key and metrics export are, and stay, Community.

The source is public, and the paperwork says which license it is under. Nothing a node or console does
changed.

APIs and logback are dual- or multi-licensed; the bundles redistribute them under their EPL-2.0 or Apache-2.0
terms), and the build now refuses a bundle with a library that offers none of them.

The vendored console assets — Bootstrap 3 and jQuery 2 (MIT) — and `bin/frontcache`, which keeps the
Apache Software Foundation's header from the Tomcat script it came from, are listed in `NOTICE`.

## Upgrading

**Nothing is required, unless you use the cache warmer or console clusters.** A 2.11.0 node with an
unchanged `frontcache.properties` behaves as 2.10.0 did: it sends no edge token and accepts none, and no
existing guard rule changes meaning.

1. **If you use the cache warmer or `frontcache.console.clusters`**, decide before upgrading: both are
   gone from the Community bundles ([What left the Community bundles](#what-left-the-community-bundles)).
   The console warns once at startup about a `clusters` or `cache-warmer` key it no longer reads, and
   `warmer/warmer.sh` is the warmer that remains.

Optional, for a chained deployment: [roll the edge token out](#rolling-it-out).

Mixed versions are safe in either order:

- A **2.10.0 edge in front of a 2.11.0 second layer** sends no token, so its traffic matches
  `!edge-token`. That is why step 4 above is a dry-run: it shows exactly this before anything is
  refused.
- A **2.11.0 edge in front of a 2.10.0 second layer** sends a header the older node forwards to the
  app and otherwise ignores.
- A **2.11.0 console reading 2.10.0 nodes** reads them as it did. A **2.10.0 console reading 2.11.0
  nodes** shows "not available on this node" on its Cache Warmer screen, as it does for a node that
  predates the warmer.

**Verified:** `frontcache-core` 755 unit tests (3 for the module boundary: `CoreBoundaryTest`, one of
which skips with no plug-in beside the core; 3 for the reload fix: `FrontCacheEngineReloadTest`; 32 for the
edge token: `EdgeTokenTest`, `OriginEdgeTokenTest`, `EdgeTokenPredicateTest`, and the redirect-target cases
in `GuardRuleParserTest`; and that a node with no module exports no plug-in series, in `FcMetricsExportTest`),
`frontcache-console` 125 (7 for the plugin boundary: `ConsoleBoundaryTest`, `ConsoleWithoutPluginsTest`), the
console's JavaScript tests (3, `fc-dashboard.test.js` new), and the 211-test end-to-end suite (9 new in
`StandaloneEdgeTokenTests`, 5 in `CommunityEditionTests`; 4 skipped: the `@Ignore`d `cacheRefreshSoft` pair
on each node), all green; and `verifyDist` finds no Pro code in either bundle. `check` now also fails on a
source file with a missing or wrong license header, and on a bundled library under none of the allowed
licenses — each checked by breaking it once.
